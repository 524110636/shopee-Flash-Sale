> **用途**：账号、邀请码、试用限制、店铺绑定、防破解校验、安全加固、统计上报、接口表、CORS。
> **何时读**：改后端行为、排查「登不上」「试用到期」「绑定失效」「权限不对」类问题。
> **来源**：原 `AGENTS.md` 与 `CLAUDE.md` 的 Backend 相关段，合并双方独有信息。

## 注册与登录

### 认证流程

1. 用户用 邮箱/用户名 + 密码 + **邀请码** 注册 → 后端校验邀请码（一次性）→ 返回 6 位验证码
2. 用户输入验证码 → **手动点击**验证按钮（自动提交已移除）→ 账号激活（`isActive=1`）
3. 登录 → 返回 JWT（7 天有效，payload 含 `trialUsed`、`autoModeEnabled`、`trialEnabled`）
4. 扩展把 JWT 存 `chrome.storage.local` 的 `backendAuth` 键
5. 后续所有 API 调用自动带 `Authorization: Bearer` 头
6. 收到 401 → 自动清 auth 并回到登录界面
7. 注册需勾选同意《使用条款及免责声明》（`agreedToTerms`）

**注册标识**：邮箱格式与纯用户名（`/^[a-zA-Z0-9_.-]+$/`）都接受。

### 使用条款及免责声明

- 注册表单有必勾选 checkbox；未勾选时注册按钮 disabled，点验证码区域也提示需先勾选
- 链接文字弹出 Modal，内容约 1500 字（标准 EULA 模板 + 虾皮特定免责：自动化操作风险、店铺降权、流量下降、API 时效等）
- **注册与验证都改为手动点击按钮**，移除验证码自动提交 —— 防止绕过条款

### 首次部署

新部署没有管理员账号和邀请码（鸡生蛋问题：注册要邀请码，只有管理员能生成）。执行一次 seed：

```bash
cd backend
# 先在 .env 里设置 INIT_ADMIN_EMAIL、INIT_ADMIN_PASSWORD、JWT_SECRET
npm run seed
```

从 `INIT_ADMIN_EMAIL`／`INIT_ADMIN_PASSWORD` 建管理员，按 `INIT_INVITE_CODES`（默认 5）生成初始邀请码。**幂等**，可重复执行。初始化完成后从 `.env` 移除 `INIT_ADMIN_*`。

**为什么必须幂等**：部署脚本可能被重跑（容器重启、手动补跑）；不幂等会建出重复管理员或刷出一堆无用邀请码。

## 邀请码

- **一次性邀请码**：管理员在独立管理网站的「邀请码」页生成，替换了旧的全局 `REGISTER_KEY`
- 格式 `INV-xxxxxxxx`（8 位随机 hex），批量生成数量可配置（1–20）
- 注册时校验：查 `invite_codes` 表，`is_used=0` 才有效；使用后标记 `is_used=1, used_by=<userId>, used_at=now`
- 同一邀请码不可重复使用；已使用的不可删除
- 管理员可查看所有邀请码及使用状态（使用者邮箱、使用时间）
- 前端注册表单字段名「注册密钥」→「邀请码」

**表结构** `invite_codes`：`id`、`code`(UNIQUE)、`is_used`、`used_by`、`created_at`、`used_at`。

**为什么改成一次性**：全局密钥一旦泄漏，任何人都能无限注册；一次性码可追溯发放对象，泄漏面可控。

## 试用限制

### 字段与默认值

- `users.trial_used`（默认 0）、`users.trial_enabled`（默认 1）

### 行为

- `trial_used >= 1` 且 `trial_enabled = 1` 的**非管理员**用户再次操作 → **403**，后端实际返回文案：
  > 如需继续使用，请联系管理员升级套餐。升级后即可畅享无限限时特卖，快速增长店铺业绩。

  （`backend/src/routes/stores.ts` `/validate`）
- 管理员（`role=admin`）不受试用限制，`trial_used` 也不自动递增
- 独立管理网站显示试用状态，提供「重置试用／标记已用」按钮与「关闭试用／开启试用」按钮（红/绿）
- JWT payload 含 `trialUsed` + `trialEnabled`；`checkAdmin()` 返回时同步到 storage

### 试用永久关闭（`trialEnabled`）

管理员在独立管理网站的用户列表点「关闭试用」→ `trialEnabled = 0`。该用户后续所有操作**跳过**试用检查，也不会自动标记 `trialUsed`。适用于已升级套餐的用户。

### 校验与消耗分离（v1.14.0）

- `/validate` **只做只读检查**（读 `trialUsed` 状态），**不再标记试用**
- `POST /api/stores/consume-trial` 在操作**成功后**由 `background.ts` `consumeTrial()` 独立调用，标记 `trialUsed=1`
- 所有操作路径（手动 enable、向导加入、定时开售、自动模式、复制流程）最终走 `runEnableLoop` → `consumeTrial()`，fire-and-forget 不阻塞操作

**为什么分离**：早期 `/validate` 顺手标记，导致「用户点了但因活动未开始而失败」也照样扣掉唯一的试用机会。

### `consumeTrial()` 调试

`consumeTrial()` 检查 `response.ok`（fetch 不抛非 2xx 异常），失败时从响应体提取错误；所有结果写入 `_consumeTrialLog` storage 键（`status`／`consumed`／`error`／`ts`）。popup 控制台可读——**原因**：指纹浏览器里看不到 Service Worker 日志。

### 试用到期通知

任何操作触发 403 试用错误时，`trialExpiredBanner` Zustand 状态设值，`App.tsx` 顶部渲染红底横幅（图标 + 升级引导 + 关闭按钮）。

**5 个检测点**：`checkBackgroundStatus`、`executeCopy` instant/scheduled 路径、`runOneDaySkuAndEnable` 异常、`scheduleEnableForFlashSale` 异常。

**Wizard 就地显示**：`checkBackgroundStatus` 检测到试用错误且 `oneDaySkuFlow.phase === 'starting_flash_sale'` 时，同步把 `oneDaySkuFlow` 置为 failed，错误直接显示在向导界面，用户无需向上滚动。

### 操作点覆盖

文档旧述「9 个操作点」（`enable`／`copy`／`auto_mode_enable`／`scheduled_copy`／`scheduled_enable`／`wizard_flow`／`scheduled_copy`(alarm)／`scheduled_copy_enable`／`scheduled_enable`(alarm)）。

**实测更正**：`validateShopAccess` 现有 **13 处**调用 —— `background.ts` 12 处（含 `auto_mode_create`、`wizard_create`）＋ `store.ts` 中 `createNewFlashSaleAndAdd` 的调试立即创建路径 1 处。

## 店铺绑定

- **`shop_id` 是稳定绑定锚点**（来自 `GET /api/v2/login/`），SPC_CDS 只用于调接口
- `store_bindings` 表有 `shop_id`、`account_id`、`shop_username` 用于稳定识别
- 同一 `shop_id` + 同一用户 = 自动更新 SPC_CDS（会话续期，无需重新绑定）
- 不同 `shop_id` = 若还有容量，显示琥珀色「当前店铺未绑定」提示；「绑定当前店铺」按钮内联出现
- 每个用户有 `users.max_stores` 限额（默认 1，管理员可调）
- `StoreStatus` 组件显示当前数量 vs 限额，以及 `shop_id`／`shopUsername`
- **绑定按钮的显示条件**：在绑定列表底部检测当前店铺是否已绑定，且 `activeBindings.length < maxStores`（还有剩余容量）时，显示「绑定当前店铺」按钮
- 管理员可通过独立管理网站的「绑定管理」页强制解绑任意店铺
- 提取 SPC_CDS 后调用 `GET /api/v2/login/?SPC_CDS=xx` 获取店铺信息
- `App.tsx` 的 `isCurrentStoreBound`：**先比 `shop_id`**，旧记录回退比 `spcCds`

### 自动刷新绑定

当 `fetchShopInfo` 或 `refreshStoreBindings` 检测到 SPC_CDS 变了但 `shopId` 仍匹配某绑定，会静默调用 `bindCurrentStore()` 更新后端的 SPC_CDS。`isAutoRefreshingBinding` 标志显示蓝色同步卡片（「正在同步店铺信息...」）替代琥珀色「当前店铺未绑定」警告。

**为什么需要**：指纹浏览器（速销易）每次重启都会轮换 SPC_CDS，不然用户每天都要手动重绑。

### `/validate` 匹配顺序

先按 `spcCds` 匹配；找不到时回退按 `shopId` 匹配，并在找到时自动更新 SPC_CDS。

### 传 shopId 的调用点

`enable`、`auto_mode_create`、`auto_mode_enable`、`scheduled_copy_enable`、`scheduled_enable`、`wizard_flow`、`wizard_create`。

## 防破解校验

所有关键操作（开限时特卖、复制活动、自动模式、定时复制）执行前，调用 `POST /api/stores/validate` 校验：

1. 店铺绑定是否仍有效
2. 用户账号是否激活
3. **试用限制（只读检查）**

校验在后端执行，**无法通过修改前端代码绕过**。

- `validateShopAccess()` 是 `background.ts` 中的内联函数，从 storage 读 `backendAuth` + `backendUrl`，URL 不存在时回退默认值
- 含 `[bg:validate]` 日志：开始校验 → 请求 URL → 后端响应 → 通过/失败
- 验证失败按注入点分别处理：`return` 错误 / `throw` / 停自动模式 / `log` + `return`

**为什么必须放后端**：前端代码用户随手可改，只有服务端校验才算真约束。

## 安全加固

### 客户端

- `backend-api.ts` `request()` 所有错误路径均 `throw`，**绝不返回假成功数据**；`!response.ok` 检查在 `response.json()` 之前；Content-Type 守卫防止非 JSON 响应被误解析；网络错误不暴露 `_baseUrl`
- `loadAuthFromStorage()` 用 `isValidJwtStructure()` 检查 JWT 结构（3 段 base64url，payload 含 `userId`／`email`／`role`／`exp`／`iat`），失败则清 storage
- `isLoggedIn()` + `getAuthUser()` 检查 `isTokenExpired()`（`payload.exp * 1000 < Date.now()`）

**为什么**：宽容降级（出错也返回空数组/假成功）会让「后端挂了」表现成「功能正常但没数据」，用户和开发者都被误导。

### 启动认证

`checkAuthOnStartup()` 用 `checkAdmin()` 的返回值作为 `autoModeEnabled`／`trialUsed`／`trialEnabled` 来源（**不是** storage 数据）。区分 401（清 auth）与网络错误（设 `backendUnreachable` 标志）。外层 catch 不再静默吞错。

### 绑定加固

`refreshStoreBindings()` 遇 401 时同步清理 `isLoggedIn`／`authUser`／`storeBindings`。`bindCurrentStore()` 错误消息脱敏（不返回 raw `e.message`）。

### 后台验证缺口闭合

- `wizard_create` alarm handler 与 `handleAutoModeCreate()` 加入 `validateShopAccess()` 调用
- `SCHEDULE_COPY`／`scheduled_copy_enable`／`scheduled_enable` 中 `spcCds` 缺失时 abort 并返回错误（旧代码仅 `console.warn` 跳过）
- `runEnableLoop()` 调用从 fire-and-forget `.catch()` 改为 `await` + try/catch，`_enableParams` 移除放到 await 之后

### 服务端

- `backend/src/routes/auth.ts` `/check-admin` 的 `isAdmin` 从 DB 查 `users.role`（以数据库当前值为准，不用 JWT claim）
- `backend/src/middleware/auth.ts` 的 `adminMiddleware` **按 token 的 `userId` 查库**，确认账号存在、`is_active=1`、当前 `role='admin'` 才放行
- `backend/src/utils/jwt.ts` 启动时检查 `JWT_SECRET` 是否为 `.env.example` 的硬编码值，**匹配则拒绝启动**

**为什么 adminMiddleware 必须查库、不能只看 token 的 role**：token 是**签发时的快照**；账号被删除、被停用（`is_active=0`）或被撤销管理员权限后，旧 token 在有效期内仍然通过验签。只看 `payload.role` 会把这些已失效身份当成管理员放行。JWT 本身是验签的（`jwtVerify`），问题不在伪造，而在**信任层级**——权限这类可变状态必须以数据库当前值为准。

**为什么拒绝用示例密钥启动**：用示例密钥签发的 token 谁都能伪造；宁可起不来也不要带着假密钥对外服务。

### 401 错误信息透传

`backend-api.ts` `request()` 在 401 时先 `response.json()` 读取后端的 `error` 字段（如「邮箱或密码错误」），有则用后端消息，无则回退「认证已过期，请重新登录」。所有 401 路径均调用 `clearAuth()`。

### IP 回退（VPN 用户）

`tryFetch()` 包装主请求，网络错误时用 `_fallbackUrl`（来自 `VITE_BACKEND_FALLBACK_URL`，如 `http://43.99.86.228:5724`）重试。

**为什么**：曾有 Cloudflare DNS A 记录丢失导致域名解析到保留地址，VPN 用户完全连不上；IP 直连可绕过 DNS。

### 后端端口占用自动处理

`backend/src/index.ts` 的 server 监听 `error` 事件；遇 `EADDRINUSE` 时**打印明确错误并退出（exit code 1）**，不自动杀掉占用端口的进程。

**为什么不再自动 kill**：同机上可能有其他人的服务；自动 `kill-port` 会误杀无关进程。需要释放端口时由操作者手动执行 `npx kill-port <PORT>`（见 [10-环境与命令](10-环境与命令.md#端口排查)）。

## 统计上报

- Background SW 用 `reportAnalyticsEvent()`（fire-and-forget `fetch()`）
- 从 `storage.local` 读 `backendAuth` + `backendUrl`，POST 到 `/api/analytics/events`
- 事件：`enable_loop`（开卖循环完成）、`copy_flow`（复制流程）、`auto_mode_round`（自动模式每轮）、`auto_mode_stop`（自动模式停止）
- 错误静默忽略

**为什么静默**：统计是辅助信息，不应因为上报失败影响主流程；但这也意味着**不能把统计数据当作操作是否成功的证据**。

## 事件明细脱敏

`GET /api/admin/analytics/events` 的 `eventData` **不原样透传**，按事件类型白名单输出标量字段（`backend/src/routes/admin.ts` 的 `EVENT_DATA_FIELDS`）：

| 事件类型 | 允许输出的字段 |
| --- | --- |
| `enable_loop` | `totalSkus`、`successSkus`、`failedSkus`、`rounds` |
| `auto_mode_round` | `round`、`totalRounds`、`flashSaleId` |
| `auto_mode_stop` | `currentRound`、`totalRounds` |
| `copy_flow` | `flashSaleId`、`hasSkuOverrides`、`source` |

未列入的类型返回 `null`，嵌套对象与数组一律丢弃。管理网页把 `null` 显示为「无可展示明细」，不显示原始 JSON。

**为什么查表必须用 `Object.hasOwn`**：`eventType` 来自上报接口，可以是任意字符串。若写成 `EVENT_DATA_FIELDS[eventType] ? ... : null`，`constructor`、`__proto__`、`toString` 这类名字会命中对象**继承**来的成员，绕过判断；随后对非数组值做 `for...of` 会抛 `TypeError: allowed is not iterable`，接口返回 500。由于不带 `type` 过滤的列表要遍历全部记录，**一条这类脏数据就能让整张事件明细读不出来**。管理网页的 `EVENT_LABELS` / `EVENT_DATA_LABELS` 是同类查表，也必须只用自身条目（见 `AnalyticsPage.tsx` 的 `lookup()`），否则 React 会试图渲染函数而崩页。

**为什么必须脱敏**：上报接口接收任意 `eventData`，历史数据里可能有 token、Cookie 之类的内容；原样透传会让管理页面直接显示凭据。新增事件类型时**必须同步在这里加白名单**，否则该类型的明细在管理页面不可见（这是有意的失败方向：宁可看不到，也不泄露）。

## 弹窗策略（v1.15.0）

管理网站「弹窗管理」发布的通知与强制升级，扩展每次打开时读取。**发布策略与业务权限校验完全分离**：策略接口绝不参与 `/validate` 或后台任务是否放行。

### 数据模型：多条记录 + 每模式一个生效槽

| 表 | 作用 |
| --- | --- |
| `popup_policies` | **多条独立记录**（管理员可连续新建）。每行一条，带自己的草稿字段与生效快照字段。**草稿类型 `mode` 与生效快照类型 `published_mode` 分开存** |
| `popup_active_slots` | 每模式**一行**：指向当前生效的记录（`active_record_id`），并保存该模式**全局递增**的发布计数 `revision` |
| `popup_assets` | 图片元数据；字节落在 `POPUP_ASSETS_DIR`（默认 `backend/data/popup-assets`） |
| `popup_views` | 查看统计：一行 = 「某登录账号看过某条记录」。唯一索引 `(record_id, user_id)` |

**为什么查看统计要单独一张表、并用唯一索引去重**：同账号重复打开、多设备、StrictMode 重复 effect、并发上报都会重复请求。用「记录表加一列自增计数」在并发下会多计；唯一索引让 SQLite 自己保证只算一位。统计与弹窗内容发布是两条互不影响的生命周期，分开后统计出错不会影响弹窗展示。

**为什么要 `mode` 与 `published_mode` 分开**：管理员可以改草稿类型（勾选/取消「强制更新」），但**已发布快照的类型不会因为改草稿而变**。若只看 `mode`，一条「先按强制发布、再改成通知草稿」的记录会被两个生效槽同时认领 —— 公开接口两模式都返回它，而且通知槽返回的条目缺少 `requiredVersion`，扩展的严格校验会判整份响应非法（B3）。

**为什么不用「记录表加一个 is_active 布尔」**：两条并发发布之间没有互斥，可能出现两条都 active。单行槽位 + 事务写天然只有一条生效。

**为什么 `revision` 放在槽位而不是记录上**：它是**每模式全局递增**的计数，撤回与「发布另一条记录」都要产生更大的修订号。若绑定在记录上，新记录会从 1 开始，**已被用户确认过的旧修订号会把它吞掉**（用户再也看不到新通知）。

### 发布与撤回的联动规则

- **发布**：同一事务里写生效快照（含 `published_mode`）→ **先释放本记录可能占着的其他类型槽** → 再把新类型槽指向它 → 递增槽位 `revision`。第一步不能省，否则改过类型的记录会同时占两个槽。
- **撤回**：只清生效快照的展示字段；`published_revision` 与 `published_mode` **保留**。清槽时按「实际挂着本记录的槽」定位，**不依赖草稿 `mode`**（草稿可能已被改过类型）。
- **状态判定**：`published_revision > 0` 就是「曾经发布过」→ 不在生效槽时显示**已撤回**；只有从未发布过才是**草稿**。不能看「当前有没有生效快照字段」，否则主动撤回会被误显示成草稿（B4）。
- **公开读取双层校验**：槽指向的记录，其 `published_mode` 必须与槽类型一致，否则返回 `null`。

### 查看统计的计数口径

「查看」= 该条生效弹窗**在真实扩展界面里被显示并成功上报**。不是「请求过策略接口」「管理端预览」「点了确认或下载」。

上报要计数必须同时满足四条，缺一不可（都在 `backend/src/utils/popup-views.ts`）：

1. 该记录 `published_revision > 0`（从未发布的草稿不能被刷人数 —— 否则知道 `recordId` 就能给未公开草稿造数）；
2. `published_mode` 与上报的 `mode` 一致（否则一条记录会给两个类型计数）；
3. 该记录**此刻确实占着这个类型的生效槽**（撤回后记录行还在、累计人数要保留，但它已不在生效槽上；只看前两条会让撤回之后晚到的上报继续加人）；
4. 上报的 `revision` 必须**恰好等于该生效槽当前的全局 `revision`**，且必须是正的安全整数。

**为什么第 4 条比对的是「生效槽 revision」而不是记录自己的 `published_revision`**：槽位的 revision 才是公开接口发给客户端、用户实际看到的那一个。用记录自己的发布次数会漏掉「同类型另一条记录发布后槽位前进了、但本记录自己的次数没变」这种情况，旧修订就能一直刷人数。两者在单记录场景恰好相等，所以只有比对槽位 revision 才既覆盖真实场景又不误伤。

**为什么必须拒绝缺失／零／负数／小数／不存在的修订**：这些值都不可能是服务端发出去的；接受它们等于「任何已登录账号只要知道 `recordId` 就能给任意生效记录加人」。拒绝是**温和**的 —— 返回 `counted:false`（`reason: bad-revision` / `stale-revision`）而不是错误状态，扩展侧不因此登出或清缓存。路由里**不要**把缺失的 revision 兜底成 0，那会让校验层再也分辨不出来。

- 人数**必须 JOIN `users`** 统计，与明细列表用同一个 JOIN。查看表里的行在账号被删除后会留下（统计不随账号删除清理），若人数只数查看表的行，会出现「说 2 位、明细只有 1 条」。
- 首次查看时间由服务端记；重复上报**不刷新**它（否则「首次查看」会漂移）。
- 撤回／替换／改草稿／重启服务都**不清空**累计；页面文案注明「累计去重，含历史发布」。
- 统计表在初始化时用 `CREATE TABLE IF NOT EXISTS` + `CREATE UNIQUE INDEX IF NOT EXISTS` 增量建立，**不删表不重建**，重复执行不丢已有统计。

### 撤回不删记录，也不误撤别的记录

撤回只清**该记录**的生效快照展示字段，记录本身保留（列表里变「已撤回」）。定位生效槽用**实际挂着本记录的槽**，而不是草稿 `mode` —— 否则会误撤同类型另一条正在生效的记录，或漏撤改过类型的记录。这两点都有专门用例覆盖。

### 增量迁移（幂等，不删库重建）

旧版是「每模式一行、mode 唯一」。初始化时检测到旧结构（`popup_policies` 没有 `record_id` 列）就走迁移：新建表 → 把旧行搬成 `legacy-<mode>` 记录 → 修订号原样写入生效槽 → 换名。

- 旧草稿、生效快照、图片元数据都不丢；
- 修订号**不回退**，避免已读记录吞掉新通知；
- 重复执行安全（第二次检测不到旧结构直接返回）。

### 上传与清洗红线

- 图片类型按**实际字节签名**判定（PNG／JPEG／WebP），**不相信** 上传声明的 `Content-Type` —— 改个扩展名就能绕过。
- 单张 ≤ 5 MiB；每条正文最多 5 张自有图片；正文 UTF-8 ≤ 100 KiB。**新建接口也要过这套上限**（空白窗口允许空标题空正文，但不能靠新建接口塞超长正文）。
- 落盘文件名用随机 hex，**用户文件名一律丢弃**（含 `../` 会越界写到目录外）。
- 富文本用 `sanitize-html` 白名单清洗（在 `backend/src/utils/popup-policy.ts`），**不允许**用自写正则替代 —— `<img onerror=` 的引号／大小写变体可以绕过正则。
- 链接只允许 http(s)；图片只允许 `/popup-assets/` 自有路径或 http(s)；`style` 只允许 `color`、`background-color`、`text-align`。
- 强制升级必须同时填 `requiredVersion`（Chrome 合法的 1～4 段数字）与 http(s) `downloadUrl`；**保存草稿时二者可空**（避免管理员先写正文时草稿存不下去丢内容），只在**发布**时强制校验。

## CORS

`backend/src/index.ts` 的 Hono CORS middleware 用函数动态返回 origin（`origin` 回调）：

```ts
origin: (origin) => {
  if (!origin) return '*';
  if (origin.startsWith('chrome-extension://')) return origin;
  if (origin === 'https://seller.shopee.tw') return origin;
  return null;
}
```

**准确表述**：**不是**完全无通配符 —— 请求**不带 `Origin` 头**时返回 `*`（`backend/src/index.ts` 的 CORS `origin` 回调）。带 Origin 时才逐字返回 `chrome-extension://<id>` 或 `https://seller.shopee.tw`。

Hono **不支持** `chrome-extension://*` 这类静态通配符。

**影响**：无 Origin 头的请求（如服务端发起的 curl、部分代理）会拿到通配符，但这些请求本来也不带浏览器凭据；浏览器扩展发起的请求都会带 Origin，走精确匹配分支。
