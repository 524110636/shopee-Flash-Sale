# 08 关键设计决策

> **用途**：当初为什么这么做。保留背景与取舍，**不自动升格为强制红线**。
> **何时读**：想改某个已定型的设计、疑惑「为什么不用更简单的写法」。
> **来源**：原 `AGENTS.md` 的 Critical Design Decisions（39 条）。

编号沿用原文，方便与历史文档对照。前 9 条为「架构级」决策，原文已带原因；10–39 条为「版本演进」决策。

## 决策 01 — 开卖循环跑在 background Service Worker

`runEnableLoop` 在 `background.ts`，不在 popup。popup 构建 items、用 `storage.local` 存参数、发 `START_ENABLE`；background 回发 `ENABLE_PROGRESS`／`ENABLE_COMPLETE`。循环在 popup 关闭后继续。用 `_enableRunning` 标志 + `try/finally` 防并发。

**为什么**：开卖一批可能几百个 SKU、要重试十几轮，跑几分钟到几十分钟；放在 popup 里，用户一关弹窗循环就死，开卖到一半停住、部分 SKU 上了特卖部分没上，店铺活动数据不一致。`_enableRunning` 必须在 `finally` 复位，否则一次异常后永久锁死，之后点开启毫无反应。

## 决策 02 — 数据加载仍在 popup

用 `browser.scripting.executeScript({ world: 'MAIN' })`（经 `injectedFetch()`）。background 版的 `injectedFetch` 按 URL 找卖家标签页（不是激活标签页），因此用户切标签页时循环仍能跑。

**为什么**：虾皮页面有 CSP，普通 `fetch` 打不通它的内部接口，必须注入到页面主世界执行；background 版按 URL 找标签页而不是「当前激活标签页」，否则用户切到别的标签页就会中断循环。

## 决策 03 — SPC_CDS Cookie 提取的多域降级链

`browser.cookies.get()` 按顺序尝试：`seller.shopee.tw` → `shopee.tw` → `www.shopee.tw` → `cookies.getAll({ domain: '.shopee.tw' })`。

**为什么**：虾皮在不同登录入口把 SPC_CDS 写在哪个域不固定，单一域取不到就会报「未连接」，用户以为插件坏了。降级链是让「换个入口登录」也能用。

## 决策 04 — 全部业务逻辑在 Zustand store

`store.ts` 是唯一真相来源；React 组件是薄包装。

**为什么**：同一份状态被多个面板（主界面／自动模式／向导）读写，若各组件各存一份，会出现「这边改了那边不刷新」；集中一处才能保证关弹窗再开、进度不丢。

## 决策 05 — 乐观 UI 更新

`isEnabling` 在 `START_ENABLE` 响应前就置 true，按钮立即变化。重开时 `checkBackgroundStatus` 直接读 `storage.local` 的 `_enableProgress`，不发消息。

**为什么**：MV3 下 `sendMessage` 的响应经常拿不到，若等响应再改按钮，用户会以为没点上而反复点，导致重复提交。直接读 storage 是为了让「关掉弹窗再打开」仍能看到真实进度，而不是显示成没在跑。

## 决策 06 — 基于 storage 的通信

MV3 下 `browser.runtime.sendMessage` 的响应即使成功也可能返回 `undefined`。关键流程（`EXECUTE_COPY`）与状态检查（`GET_ENABLE_STATUS`）改用 `browser.storage.onChanged` 或直接读 storage。content script 也用 `storage.onChanged` 作为 `_enableProgress`、`_copyCountdown` 的备用通道。

**为什么**：曾因此出现「复制成功了但界面卡在等待」，用户重复点导致建出多个活动。凡关键流程一律以 storage 为准，消息只当通知。

## 决策 07 — 复制流程用 `get_shop_flash_sale_item/` 手工复制

源商品配置经 API 拉取，再通过 `set_shop_flash_sale_items/` 应用到新活动。`from` 参数的 Referrer 头方案（服务端自动复制）在 fetch API 环境不可靠。

**为什么**：试过用 Referrer 头让服务端自动复制，在扩展的 `fetch` 环境下不稳定（时好时坏），会出现「新活动是空的」；手工拉取再提交虽多一次请求，但结果确定。

## 决策 08 — 行内操作用统一按钮模式

所有文字式链接（`underline hover:underline`）改为 `<Button variant="outline" size="sm">` + 紧凑自定义尺寸（行内 `h-5 px-1.5 text-[10px]`，常规 `h-6 px-2 text-xs`）。

颜色语义：绿=正面（应用、保存）、红=破坏性（删除、停止）、蓝/主色=导航（复制、查看）、中性=取消/关闭。自定义 class 覆盖 `size="sm"` 默认的 `h-9`。

选中/高亮态用**品牌 token** `border-l-4 border-l-shopee-brand bg-shopee-brand-light/50`，与 `ProductCard` 的已修改项指示一致。

> 早期措辞写的是 `border-l-blue-500 bg-blue-50/50`；那些工具类现已不再使用，项目已迁到品牌 token。

## 决策 09 — 陈旧商品状态防护

`loadFlashSaleProducts` 在源活动商品数为 0 时（提前返回）清空 `products`、`productIds`、`inputText`，防止上次查询的残留。`CopyConfirmPanel` 的 `handleOpenView` 无论当前 `products.length` 多少都重新加载源商品。

**为什么**：不清空的话，切换到空活动会显示上一个活动的商品，用户会以为复制成功了。

## 决策 10 — SKU 直定价格（v1.4.0）

`SkuOverride.promoPrice` 允许直接指定限时价（如 8 元），绕过整数折扣率的两次取整损失。构建 `EnableItem` 时 `override?.promoPrice ?? Math.floor(price * rate / 100)`。

与 `discountRate` 互斥：设折扣%时清空 `promoPrice`，反之亦然。

## 决策 11 — 模板编辑与分组折叠（v1.5.0）

`TemplateEditDialog` 按商品 ID 分组展示 SKU 覆盖参数，主商品行为可折叠行（▶/▼），展开后显示子 SKU 编辑行。支持全部展开/收起、行内快捷添加 SKU、底部全局新增。每页 8 个商品，超出自动分页。`updateTemplate` 支持部分更新（合并已有字段，自动设 `updatedAt`）。

## 决策 12 — 复制活动数据一致性（v1.6.0）

`loadFlashSaleProducts` 正常 API 路径新增 `get_shop_flash_sale_item/` 调用获取每个 SKU 的实际 flash sale 参数。`promoPrice` 直接用 `configItems[].promotion_price`。`fetchProducts` 完成后反推 `discountRate` 填入每个 SKU 覆盖参数。复制数据加载路径同理。

## 决策 13 — `enterCopyMode` 不再自动选择模板（v1.6.0）

`selectedTemplate` 默认 `null`。

**原因**：避免首个模板的 `discountRate=60`／`flashSaleStock=200` 等默认值通过 `executeCopy` → `_copiedSaleData` 污染全局输入框显示。用户需手动选择模板。

## 决策 14 — `SkuTable` 的 `key` prop（v1.6.0）

共 6 处渲染点，4 处带 `key`。带 key 时切换商品 React 销毁旧实例创建新实例，内部 `priceEditValues` 等状态归零。

改动**未带 key**的两处（`AutoModePanel.tsx`、`ProductViewModal.tsx`）时要留意可能的状态残留。当前未加，非笔误。

## 决策 15 — 复制时段默认选择（v1.6.1）

`CopyConfirmPanel` 的 `useEffect` 默认选中 `slots[0]`。移除了「当前时间+2 小时」最近时段启发式算法 —— 该算法可能跳过第一场选到第二场。

## 决策 16 — 定时任务两阶段 alarm 分离（v1.6.1）

`scheduled_copy` alarm（活动开始前 5 分钟）仅创建空活动并保存 `_enableParams`，同时创建 `scheduled_copy_enable` alarm（活动开始后 5 分钟）执行 `runEnableLoop`。

`TRIGGER_SCHEDULED_COPY_NOW` 手动触发路径同样遵守：若活动已开始超过 5 分钟则立即执行 enable，否则安排定时 alarm。

**原因**：旧代码在创建空活动后立即调用 `runEnableLoop`，因活动未开始 API 拒绝提交导致全部 SKU 失败后终止。

## 决策 17 — `_copiedSaleData` 缓存一致性验证（v1.6.1）

`loadFlashSaleProducts` 找到缓存后、使用前，先调 `get_shop_flash_sale_item_id_list` 取当前活动实际商品 ID 列表，与缓存商品 ID 做 `Set` 双向对比。不一致则删除该活动条目并重置 `copiedData=null`，回退正常 API 路径；一致则继续用缓存。

**原因**：修复「用户手动替换商品 ID 后界面仍显示旧复制商品」。

## 决策 18 — SKU 覆盖提示与详情搜索（v1.6.2）

`App.tsx` 在「开启限时特卖」标题与全局参数输入行之间显示覆盖提示。统计仅基于当前 `products` 中实际存在且命中 `skuOverrides` 的 SKU，避免显示过期缓存。

点击「查看」打开父弹窗，可按商品标题、商品 ID、SKU 名称、SKU ID 搜索。父弹窗保持打开，点「查看 SKU」时只打开 `SkuTable` 子弹窗。父弹窗 `z-40`，`SkuTable` `z-50`。

## 决策 19 — 复制活动全量固化 SKU 覆盖（v1.6.2）

`executeCopy()` 在保存复制参数前遍历当前 `products.modelList`，为**没有显式覆盖**的 SKU 也写入一条 `skuOverrides[key]`。因此复制源活动在新活动展示时视为所有 SKU 都已手动编辑，不会被后续全局折扣行覆盖。`loadFlashSaleProducts()` 读旧 `_copiedSaleData` 时也补齐缺失覆盖项。

## 决策 20 — 异步按钮统一反馈（v1.6.3）

点击后 100ms 内文案切 loading，按钮 `disabled` 防重复点击，请求完成后 `finally` 恢复。

涉及按钮：清除缓存、重新获取 SPC_CDS、停止、手动触发定时任务、应用模板、删除模板、保存模板。开启限时特卖通过按钮切换（🚀 开启 → ⏹ 停止）提供即时反馈。

## 决策 21 — 按钮四色语义体系（v1.6.3）

蓝 outline=普通操作、绿实心=主确认、红 outline=停止/危险、灰=次要/取消。危险操作禁止用蓝色。

## 决策 22 — 低频操作折叠（v1.6.3）

「清除缓存」从 header 移到底部折叠区、「手动触发定时任务」从启用区移入折叠区。用 `<details>` + `<summary>` 实现，默认收起。

**设计历史**：当时的方案是摘要文字写「高级操作」，并且折叠区**仅在 `isConnected` 为 true 时**渲染。

**当前实际**：折叠区的摘要文字是「**更多**」（后续决策 28 把两个折叠区合并为一个「更多」入口），且**未使用 `isConnected` 门控**。以源码为准。

> 追溯当时的门控设计原意**不属于本轮范围**；此处只记录「设计历史 vs 当前实际」的差异，不构成业务改动或新增前置。

## 决策 23 — 当前活动上下文展示条（v1.6.3）

`Separator` 后新增上下文条。样式用**品牌 token**（`bg-shopee-brand-light border border-shopee-brand/15` 等，不再是 `bg-blue-50 border-blue-200 ...`）。文案不含「当前活动：」前缀，直接展示 `{name} · MM/DD HH:mm ~ HH:mm · {status} · N 个商品`。`name` 为空时回退 `活动 #{id}`。

仅在 `flashSaleId` 存在且非 `copyMode` 时显示，位于商品列表上方。

## 决策 24 — 编辑痕迹强化（v1.6.3）

商品列表区域顶部（`div.max-h-48` 容器内顶部）新增汇总行：`已手动编辑 X 个商品 / Y 个 SKU` + 「查看详情」按钮（复用 `overrideDetailOpen` 弹窗）。仅当 `overrideSummary.skuCount > 0` 时显示。SKU 输入框 `placeholder` 显示全局默认值作为来源提示。

## 决策 25 — 复制流程步骤提示（v1.6.3）

`CopyConfirmPanel` 顶部三步提示：`● 选择源活动 → ● 选择目标时间 → ○ 创建复制任务`。前两步加粗，第三步灰色。纯展示，不控制流程。

## 决策 26 — 错误提示就近化（v1.6.3）

`CopyConfirmPanel` 的「查看」按钮旁新增 `viewError` 状态，失败时红色文字紧邻按钮显示。其余操作已有 inline 提示（`applyMessage`、`saveSuccess`、`importMessage`、`slotsError`）。

## 决策 27 — 定时任务存活状态检测（v1.6.4）

新增 `GET_SCHEDULED_STATUS` 消息。后台 handler 从 storage 读 `_scheduledCopy` 参数并用 `chrome.alarms.get('scheduled_copy')` 检查 alarm 是否仍注册，返回 `ScheduledTaskStatus`。

`checkScheduledCopy` store 方法增强为自动查询 alarm 状态；popup 用琥珀色卡片展示源活动名、目标时间、定时器存活状态、剩余时间倒计时、「刷新状态」按钮。

触发时机：popup 打开、创建定时任务成功后、检测到 `_copyTaskStatus` 变化时。

## 决策 28 — 布局信息分层重组（v1.6.4）

主界面按信息优先级重组为「上下文→操作→低频」三层：

- **首屏**：当前活动上下文条 + 定时任务状态卡作为信息群置于 Header 正下方
- **中层**：活动列表（紧凑折叠头）+ 商品列表 + 开启限时特卖参数区连为一体，删除无意义的 `Separator`
- **底层**：「更多」折叠区（`<details>`）收纳所有低频功能：商品 ID 输入、获取商品信息、加载列表、模板管理、手动触发定时任务、清除缓存
- 删除原有的两个独立折叠区（高级操作 + 商品ID区），统一为一个「更多」入口

## 决策 29 — 主界面与自动模式曾用 CSS 3D 翻转（v1.7.0）

v1.7.0 用 `perspective`、`transform-style: preserve-3d`、`rotateY(180deg)`、`backface-visibility: hidden` 实现整页翻转。

> 原文写「`autoModeView` state 控制正反面切换」；**实测字段已改名为 `autoModeActive`**（`store.ts` 的 `AppState` 自动模式字段段）。
>
> **2026-10-12 已去掉翻转**：改为根层 `page`（`'home' | 'flash-sale'`）控制首页／工作页，工作页内用手动／自动页签切换。
> 原因：翻转要求两张「面」都在同一容器里绝对定位，隐藏面仍然占据布局且能接收键盘焦点；
> 新增功能首页后这种方式无法同时表达三级层级，也不满足「隐藏区域不得拦截首页交互」的要求。
> 旧符号 `perspective`／`rotateY`／`backfaceVisibility` 在 `App.tsx` 中已无命中。

## 决策 29b — 首页／工作页两层 + 隐藏而不卸载（2026-10-12）

`App.tsx` 用根级 `page` 状态表示「首页 / 限时特卖」，`autoModeActive` 只表示工作页内是手动还是自动页签。

隐藏的工作区**保持挂载**，用 `hidden` + `inert` + `aria-hidden="true"` 同时做到三件事：
不占布局、不被 Tab 进入、不被读屏读到。这样手填参数、向导时间输入、SKU 编辑草稿无需逐一提升到全局 store。

入口处的绑定提示写在根层（顶栏下方），因此「未绑定 / 同步失败」在任何页面都可见。
工作页内的绑定/身份门控**照旧拦截业务操作**：首页只负责「能查看工具」，不代表业务放行。

**手动页也要隐藏而不卸载**（2026-10-13 规划方返工 R1 补正）：最初只有自动页包了这层，
手动业务区还是 `!autoModeActive && (...)` 条件渲染，结果切到自动页再回来，
`ProductList` 的搜索框、`TemplateManager` 的模板命名、`SkuTable` 的 SKU 编辑草稿全被清空。
现在手动区、自动区、以及全部根级工作弹层共用同一个 `WorkPageLayer`。

## 决策 29b-2 — 根级弹层必须归属页面（2026-10-13）

「手动修改的商品和 SKU」详情弹层（`overrideDetailOpen`）此前渲染在根级且不在隐藏层里。
用键盘或鼠标返回首页后，**弹层继续盖在首页上**，遮罩还会拦住鼠标点击（规划方返工 R3 复现）。

规则：**任何属于工作页的弹层/浮层都要包进 `WorkPageLayer`**，与页面一起隐藏；
隐藏时保留挂载，所以再次进入工作页还能接着编辑，不清草稿。

配套：`SkuTable` 在列表里按商品打开时必须带 `key={product.itemid}`（`selectedFailedProduct` 与向导的
`wizardEditProduct` 两处）—— React 复用组件实例而不换 key 时，`useState` 里的编辑草稿会串到另一个商品上。

## 决策 29c — 弹窗高度不用视口单位（2026-10-13）

根容器：`w-[500px] min-h-[500px] max-h-[600px] overflow-y-auto`。

**曾经的错误做法**：`h-[600px] max-h-[95vh]`。Chrome 扩展弹窗的视口高度**由内容决定**，
一旦用 `vh` 就形成「内容高度 → 视口高度 → max-height → 内容高度」的循环，实际表现是弹窗被压成一条（用户 2026-10-13 复现并附截图）。

**为什么保留 `min-h-[500px]`**：纯自适应时，内容少的页面（如空任务列表）弹窗会明显偏矮、每次开关高度跳动；
固定下限 + 600px 上限，既稳定又在内容多时只在根容器内滚动，顶栏 `sticky` 始终可见。

## 决策 29d — 功能图标用 lucide 组件，不用 emoji（2026-10-13）

`FeatureDefinition.Icon` 是 `lucide-react` 的 `LucideIcon` 组件（限时特卖用 `Zap`），
渲染为 `<svg class="lucide …">`，**禁止 emoji 字符串**。

**为什么**：emoji 的字形与宽度随系统字体变化，会撑破两列卡片对齐，也无法统一颜色；
SVG 图标可跟随主题色并可设置 `aria-hidden`。`lucide-react` 本来就是仓库依赖（v1.14.0），**未新增任何包**。

## 决策 30 — 自动模式模板活动沿用链（v1.7.0）

启动时使用用户选择的模板活动，每轮完成后自动把 `sourceFlashSaleId` 更新为当轮刚创建的活动 ID。第 N+1 轮沿用第 N 轮活动的商品+库存，实现链式传递，确保库存数据随售出自动递减。

## 决策 31 — 自动模式场次选择（v1.7.0）

`TimeSlotModal` 调虾皮 API（`get_time_slot_id/`）取本月所有可用场次，按 `start_time` 升序排列，显示实时状态。用户选择后在 `AutoModePanel` 蓝色信息条展示。启动时自动验证场次合法性（是否存在、开始时间是否变更、是否已开始），失败则拒绝启动。`scheduleNextRound` 第一轮优先使用用户选定场次。

## 决策 32 — 自动模式两阶段 alarm（v1.7.0）

`auto_mode_create` 在目标时间前 N 分钟触发创建空活动 + 保存数据；`auto_mode_enable` 在目标时间后 delay 分钟触发执行 `runEnableLoop`；`auto_mode_heartbeat` 定期更新状态保证 popup 可见最新进度。

## 决策 33 — 自动模式调试模式（v1.7.0）

「⏩ 加速调试」checkbox，激活后 `scheduleNextRound` 跳过真实场次时间，伪造 `fakeTargetTime = now + advanceSec + 3`，使定时调度在数秒内触发。底部调试状态条显示剩余秒数。

## 决策 34 — 跨轮次库存自动刷新（v1.7.0）

`handleAutoModeEnable` 每轮传递商品参数前通过 GraphQL 重新拉取最新 `normalStock`／`totalNormalStock`／`originPrice`，同步写回 `status.enableParams.products` 和 `_copiedSaleData`。

**原因**：确保每轮使用最新实际库存，而非轮次开始时的一次性快照。

## 决策 35 — `_copiedSaleData` 缓存库存刷新（v1.7.0）

`loadFlashSaleProducts` 缓存路径（产品 ID 验证通过后）不再直接 `return`，而是追加 `await fetchProducts()` GraphQL 调用，把新鲜库存合并入缓存商品，再 `set({ products })`。

**原因**：确保两个「查看商品」入口都显示实时库存。

## 决策 36 — `SkuTable` 批量编辑框（v1.7.0）

表格上方新增浅蓝底批量编辑行：`折扣% | 活动库存 | 限时价 | 限购数量`。输入数值后 `onBlur` 或 `Enter` 自动应用到当前商品所有 SKU。限时价批量编辑时同步清空折扣%字段（互斥设计）。适用于手动模式与自动模式。

## 决策 37 — 动态「已编辑」标记（v1.7.0）

`AutoModePanel` 维护 `editedProductIds: Set<string>` 状态；`SkuTable` 新增可选 `onEdit` prop。仅当用户点开商品并**实际修改**参数后，商品才显示蓝色左边框 + 「已编辑」badge。加载初始状态全部无标记。

**切换模板时同时清空 `selectedSlot` 与 `editedProductIds`**（`handleSelectTemplate`）—— 旧模板选定过场次、也编辑过商品，不清空会把上一个模板的场次和编辑痕迹带进新模板，用户看到「已选场次」其实是错的、被标记为已编辑的商品也可能是别的模板的。

**为什么**：自动模式会跳过未编辑的商品参数，改用一个「安全默认」；标记让用户知道哪些真的会被按自定义值提交。

## 决策 38 — 自动模式红色日志信息栏（v1.7.0）

日志卡片顶部红底信息栏（`bg-red-50 border-red-200`），运行中显示：选择场次、场次状态、模板商品数、当前轮次/总轮次、当前阶段。未启动时显示「自动模式未启动」。

## 决策 39 — 自动模式错误参数重试阈值调整（v1.7.0）

零进展僵局检测阈值从 5 轮提升到 **10** 轮，低失败僵局检测阈值从 3 个 SKU 提升到 **5** 个。

**原因**：适配自动模式下参数传递的延迟 —— 阈值太低会在正常的慢响应时误判为僵局并终止整个循环。

## 决策 40 — 一键修复搬到 background，进度与结果由后台持久化（2026-10-13）

`runOneDaySkuAndEnable` 原名副其实地"整个循环在 popup"。用户实测：最小化再打开弹窗，进度条不见了 —— **不只是显示消失，修复本身也停了**，剩余商品不再被处理。

改造后：popup 只写商品快照与归属锚到 `_oneDaySkuRepairRequest` 并发一条短消息；background 校验通过后**先持久写 `accepted`** 再异步跑 `runOneDaySkuRepairTask`；popup 用 `storage.onChanged` + `syncOneDayRepairTask` 只读同步。

**为什么不能只恢复进度条**：只把状态读回来显示、不恢复执行，会得到一条**永远不会动的假进度条**，比不显示更糟 —— 用户会以为还在修而一直等。所以执行、进度、完成结果（含最新商品/SKU 与折扣率）三者都必须由后台负责。

**为什么结果也要在后台准备**：原循环的最后一步是在 popup 里 `fetchProducts()` 再进入 `editing_params`。只把循环搬走、结果仍靠 popup 取，用户一直关着弹窗就会丢掉完整商品/SKU —— 首次使用流程（modelList 为空）尤其明显。

**关键取舍**：

| 决定 | 原因 |
| --- | --- |
| 写请求前先落检查点 | 中断后能说清"哪些商品可能已经被改"，而不是笼统失败 |
| 保存失败即停（`RepairCheckpointSaveError`） | 无记录地改商品是不可接受的 |
| 心跳拆成独立键 `_oneDaySkuRepairHeartbeat` | 心跳与进度是两条并发写路径；同键写会出现「心跳读到 running → runner 写 completed → 迟到心跳写回 running」的回退 |
| 迟到写入前读权威记录（`canAdvanceTask` + `RepairStaleWriteError`） | 浏览器关闭时执行者仍活着，它最后那次写入曾把 `interrupted` 改回 `running` 并清空结果，用户看到"还在跑"却没有执行者 |
| 中断判定不看心跳新鲜度 | MV3 每个扩展只有一个 worker，"本实例没有执行者"就等于"没有执行者"；再等宽限只是延迟写证据 |
| 中断复检走 `chrome.alarms` 而非 `setTimeout` | worker 被回收会带走定时器，中断永远标不上 |
| 中断不自动重放 | 重放会重复发布、重复移除折扣 —— 重复改动用户商品 |
| 结果按 `taskId` + `_oneDaySkuRepairApplied` 幂等应用 | 重开弹窗不得覆盖用户后填的价格/库存/限购；标记写独立键，popup 不整对象回写权威记录 |
| 界面归属分 `match`／`mismatch`／`unknown`（`verifyRepairOwner`） | 写请求必须 fail-closed；界面若也 fail-closed，冷打开时身份还在取回中，用户**自己的**结果会被一直挡在门外 |
| 补上 `validateShopAccess` | 旧 popup 循环缺这一步；无人看守的写操作不能没有服务端校验 |
| 有界保活（20 秒一次短调用） | 长任务需要越过 30 秒空闲回收；不做常年保活、不加权限 |
| **归属按"现读身份"核对，而不是启动快照** | 修复期间用户可能登出/换号；拿快照比对等于永远认为"一致"（第二轮复现） |
| **修复与开卖双向互斥** | 两条流程会改同一批商品；只在启动口把关不够，开卖每轮写请求前也要复核 |
| **恢复异常记为"结果未知"而非"失败"** | 商品可能已经发布成功；退回初始状态会让用户以为没改过 |
| **诊断只为定位，不承载业务** | 只留最近 20 条脱敏字段，不建历史任务系统、不记凭据 |

**副作用（需知）**：已过期／未绑定账号现在会在**修复前**就被拦下，而不是等到提交时。修复过程中登出或换号会**立即停止**后续写请求（已发出的那一步无法撤销，但会留下证据与说明）。

## 决策 41 — 一键修复的启动互斥与"参数绑定"（2026-10-13 BR 复验）

规划方复现出两类"看起来成功、实际没有生效"的启动问题：

1. 两个并发启动**都**回复 `success: true`，但只有一份真的在跑；
2. 另一个窗口覆盖了共享参数键后，旧的"一键修复"按钮再点一次，会拿**别人的商品**去改。

修法（都不引入队列、不取消别人的任务）：

- **同步占锁**：`handleStartOneDayRepair` 一进来就同步置 `_repairStarting`，任何 `await` 之前完成，再做异步准备；第二个调用立即得到忙态。
- **参数绑定**：`requestId` 随消息传入，必须与 `_oneDaySkuRepairRequest` 快照里的 `requestId` 一致，否则拒绝。
- **拒绝原因落 storage**：写进 `_oneDaySkuRepairStartError`。popup 里可能已有别的 `onMessage` 监听者先应答（拿到 `false`），此时消息返回值不可信，只有 storage 里的原因能保证用户看到真实失败。
- **同店铺写任务互斥（双向）**：`findSameShopWriteConflict()` 在修复启动前拒绝与自动模式/开卖冲突；`findActiveRepairConflict()` 在 `START_ENABLE` 与 `runEnableLoop` **每轮写请求前**反向拒绝。第一轮只在单向（修复 ← 其它）做了保护，第二轮回合实测"修复进行中仍能启动开卖并发出写请求"，因此补上反方向与循环内复核。

## 决策 42 — 身份锚必须"现读"，界面就绪判定分两层（2026-10-13 BR 复验）

第二轮独立复验证实：修复过程中把 `backendAuth` 从账号 1 换成 2，后续发布/恢复**仍在发出**。原因是 `getRepairAuthUserId()` 返回的是启动消息缓存的 `_repairAuthUserId`，从不读当前认证。

- **修法**：`getRepairAuthUserId()` 改为 `async` 现读 `storage.backendAuth`；`isSameOwner` 在"任务记了账号但当前读不到账号"（登出/切换中）时也返回 `false`。
- **取舍**：界面套用结果仍需要区分"确认不一致"与"还没读回来"——前者不套用并明确提示，后者保持原状态、身份就绪后再同步一次。所以写路径用 fail-closed 的 `isSameOwner`，界面用三分的 `verifyRepairOwner`。
- **就绪判定两层**：后台任务结果（`resultProducts`）与 popup 当前已加载商品任一有可编辑 SKU 即放行；两处都没有（0 SKU / 旧空 models）就禁用"下一步"并提示待加载。这是"不放行空数据"与"后台读不到但用户其实能编辑"之间的折中。
- **阶段不被复位**：`nextFlowPhaseAfterApply` 保证已进入选场次/提交的用户不会因再同步被退回编辑参数。

## 决策 43 — 互斥要覆盖"每个写入口"，参数必须即时落盘（2026-10-13 按用户实际操作复验）

用户在真实界面上复现出两个与设计假设有关的问题：

**其一，互斥只做了"开卖"一侧不够。** 修复进行中时点「复制」仍能成功发出 `set_shop_flash_sale`（关闭活动 555 + 创建新活动）。复制比开卖危险：它会**主动关闭进行中的活动**。根因是只在 `START_ENABLE`／`runEnableLoop` 加了守卫，`EXECUTE_COPY`、`COPY_FLASH_SALE`、`executeScheduledCopyFlow` 三条复制入口都没加。

修法：把"修复是否在跑"提为共用判据 `findActiveRepairConflict()`，在所有会写店铺的入口的**首个副作用之前**调用；反向补 `_copyExecuting` 让复制的实际执行期间挡住新修复。判据必须包含 `_repairStarting`（启动已受理、异步准备未完成的窗口），否则只看 storage 会漏。

**其二，界面看起来改成功了，实际没存。** 用户把折扣填成 37，控件显示 37，但 `flashSaleCache` 仍是 80，关闭重开回到 80。根因是 `setDiscountRate` 等 setter 就是一行 `set({...})`，**只改内存**；只有 `setSkuOverride` 调了 `saveCache`。

修法：所有全局参数 setter 都落盘。取舍是每次按键都写一次 storage —— 参数输入量小、无网络，代价可接受；换来"填了就不会丢"，比省几次写更重要。

**为什么之前没发现**：此前只用「预种缓存已是 37」证明"重复应用不覆盖有效缓存"，没有从界面真实输入走一遍。这说明**验收必须走真实输入链路**，预种终态只能证明幂等、不能证明保存。

## 决策 44 — 只保存"证据"，不代用户做补偿（2026-10-13 复验补充）

多折扣商品上「活动 99 移除成功、活动 100 失败」时，原实现只写一个 `discountRemoved: false`，把已成功的部分覆盖成"都没动"。用户无法判断该去核对哪一份折扣。

修法：逐活动记录 `discountRemovals: [{promotionId, name, status}]`，并在**每个成功副作用后立即落盘**（检查点带 `promotionId`/`outcome`），使中断/后续失败都不能抹掉前面已确认的结果。同样地，恢复折扣请求抛传输异常时记为"结果未知"而非"失败"，并保留"商品已发布"这一事实。

**取舍**：只增加证据字段，**不新增自动补偿或回滚**。理由是可核对的信息足够让用户人工处理（活动名、活动 id、已确认/未知状态），而自动化回滚会在不了解平台真实状态时再次改动商品，风险大于收益。

## 决策 45 — 「未知」自成一类，既不是成功也不是失败（2026-10-13 第四轮返工）

第三轮为"移除折扣异常"加了错误捕获，却把 `unknown` 写成了 `failedName: null`（即"没有失败"），调用方据此认定"全部移除成功"并继续发布、恢复折扣、最后报完成。规划方从界面复现：**移除请求网络错误后，后台仍继续改了商品**。

修法：`removeFromDiscounts` 返回 `{ failedName, failedStatus }`，`failedStatus` 区分 `failed`（平台明确拒绝）与 `unknown`（请求发出但结果不明）。**两者都停止本商品**，但提示不同：未知是"请到折扣活动页面人工核对"，平台拒绝是"请手动关闭折扣活动后重试"。

**为什么未知也必须停**：后续步骤（发布、恢复折扣）都以"折扣已移除"为前提。前提不确定还继续写，等于用不确定的状态去改真实商品；停下来只损失一次重试，继续则可能把折扣和价格改成不一致的状态。

**留下的教训**：给异常路径加"捕获"时，必须同时定义**捕获之后这个状态属于哪一类**。把"结果未知"折叠进"没有失败"，就制造了一个比原来更隐蔽的缺陷 —— 原来会停下来，改完之后反而继续写。

## 决策 46 — 补读成功要在"开放编辑之前"完成一次应用（2026-10-13 第四轮返工）

第四轮复现：结果首次读取失败 → 重开时补读成功 → 界面可编辑、但**没有写已应用标记**。用户把折扣填成 31（缓存确实是 31），关闭重开时因为"还没 applied"又套用了一次结果，折扣被重置回任务默认的 80。

修法：补读成功后**立即**走一次 `applyRepairResult`（写标记 + 初始化商品/折扣率），再让界面进入可编辑状态。幂等由 `taskId` + 标记键保证，归属与 `taskId` 约束由 `applyRepairResult` 自己处理。

**为什么之前漏了**：原逻辑只在"冷打开读到缓存里已有新模型"时才 apply，把"补读成功"当成了纯显示问题（只改 `canStartFlashSale`）。实际上"可编辑"这个状态本身就意味着结果已被采信，必须同时完成一次受约束的应用。**规则**：任何让界面进入"可编辑"的路径，都要保证该结果已经被持久标记为已应用。
