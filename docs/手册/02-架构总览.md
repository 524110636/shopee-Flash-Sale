# 02 架构总览

> **用途**：了解 popup／background／content／后端四者的分工，以及数据怎么流、消息怎么传、缓存怎么存。
> **何时读**：改跨层逻辑、排查「界面没反应」「进度丢了」类问题、需要理解某个状态从哪来。
> **来源**：原 `AGENTS.md` 的 Architecture／Data Flow／Message Protocol／Caching 段。

## 三层分工

扩展是 **Chrome MV3**，分三个独立运行环境，靠消息与 `storage` 通信：

| 层 | 文件 | 职责 | 运行时机 |
| --- | --- | --- | --- |
| **popup** | `entrypoints/popup/` | 界面 ＋ Zustand 状态机 ＋ 数据加载 | 用户点开扩展图标时；关掉即销毁 |
| **background** | `entrypoints/background.ts` | Service Worker：开卖循环、复制流程、alarm 调度、自动模式、消息中继、统计上报 | 常驻（但会被 Chrome 随时回收休眠） |
| **content** | `entrypoints/content.ts` | 注入卖家中心页面；统一悬浮进度面板；消息中继 | 卖家中心页面打开时 |
| **后端** | `backend/` | 账号、邀请码、试用、店铺绑定、防破解校验、统计 | 服务器常驻（PM2） |
| **管理网站** | `admin-web/` | 独立构建的管理员界面（用户／绑定／邀请码／统计），由后端托管在 `/admin/` | 管理员在浏览器打开时；**不进入扩展包** |

**管理网站与扩展的关系**：管理功能不在扩展里。popup 顶栏的「管理」按钮只是 `window.open()` 打开 `<后端地址>/admin/`；扩展不包含任何管理列表或写操作源码（旧的内嵌面板已移除）。依赖也完全独立——`admin-web` 用 React 18 + Ant Design 5，扩展用 React 19，两者不做版本统一。详见 [`11-配置与权限.md`](./11-配置与权限.md#独立管理网站admin-web)。

**popup 详情**（`entrypoints/popup/`）：
- `main.tsx` 把 `<App />` 挂到 `index.html` 的 root div；`index.html` viewport=420px
- `style.css` 只放 Tailwind 指令（`@tailwind base/components/utilities`）
- `App.tsx` 负责布局与条件面板切换（根级 `page` 决定功能首页 / 限时特卖工作页；工作页内用手动／自动页签切换；`copyMode='confirm'/'result'` 覆盖默认主界面）；管理入口与「无法打开管理网站」提示块位于**顶栏下方的公共区域**（不受店铺绑定状态／复制模式分支影响）
- `store.ts` 是 **Zustand 单一 store**，承载全部业务逻辑（含自动模式状态）
- `api.ts` 导出 `fetchProducts()` GraphQL 查询
- `types.ts` 定义所有共享 TypeScript 接口

**background 详情**：SPC_CDS Cookie 提取、开卖循环（`runEnableLoop`，用 `injectedFetch`）、复制流程（`EXECUTE_COPY`／`SCHEDULE_COPY`／`TRIGGER_SCHEDULED_COPY_NOW`）、自动模式（`START_AUTO_MODE`／`STOP_AUTO_MODE`／`GET_AUTO_MODE_STATUS`；alarms：`auto_mode_create`／`auto_mode_enable`／`auto_mode_heartbeat`）、消息中继。

**content 详情**：注入统一悬浮面板 `#__flash_sale_panel__`，把开卖进度、复制进度、自动模式状态合并到同一个容器。监听 `ENABLE_PROGRESS`／`ENABLE_COMPLETE`／`COPY_SCHEDULED`／`COPY_PROGRESS`／`COPY_COMPLETE`／`AUTO_MODE_UPDATE`。同时监听 `storage.onChanged` 作为消息失败时的备用路径（`_enableProgress`、`_copyCountdown`、`_autoModeStatus`）。

## 数据流

### 数据加载（在 popup）

```
用户输入 → App.tsx → store.ts actions → injectedFetch() →
  scripting.executeScript(MAIN world) → fetch() →
  响应 → store 状态更新 → React 重渲染
```

`injectedFetch()` 用 `scripting.executeScript({ world: 'MAIN' })` 把 fetch 注入页面主世界执行。**原因**：虾皮页面有 CSP，普通 `fetch` 打不通它的内部接口。

popup 版与 background 版的区别：
- **popup 版**：`tabs.query({ active: true, currentWindow: true })` —— 要求卖家标签页是当前激活页
- **background 版**：`tabs.query({ url: '*://seller.shopee.tw/*' })` —— 找任意卖家标签页，用户切到别的标签页也能继续跑

### 开卖循环（在 background）

```
Popup: 构建 items → storage.local(_enableParams) → 清旧 _enableProgress → isEnabling=true →
  START_ENABLE（fire-and-forget）→
  waitForBoot（storage.onChanged 等 _enableProgress.running=true，5s 超时 + 4s 重试）
Background: 重读 params → runEnableLoop() → 立即存进度 running=true →
  循环（在任意卖家标签页注入 fetch）→ storage.local(进度) →
  ENABLE_PROGRESS → runtime.sendMessage(popup) + tabs.sendMessage(content)
（popup 可关闭，循环继续；重开时 checkBackgroundStatus 直接读 _enableProgress）
```

### 复制限时特卖（在 background）

```
Popup: executeCopy() → 清 _copyTaskStatus → 发 EXECUTE_COPY（fire-and-forget）→
  waitForStorage() 监听 storage.onChanged('_copyTaskStatus')
Background: EXECUTE_COPY handler → 步骤1(关闭进行中活动) → 步骤2(取时段) →
  步骤3(建空活动) → 步骤4(本地保存数据) →
  存 _copyTaskStatus → storage.onChanged 触发 popup 完成
```

### 定时复制（两阶段 alarm）

```
阶段 1 — scheduled_copy alarm（活动开始前 5 分钟）：
  getSpcCdsFromCookies() → executeScheduledCopyFlow()（关闭进行中 → 取时段 → 建空活动 → 存数据）→
  存 _enableParams → 移除 _scheduledCopy → 建 scheduled_copy_enable alarm（活动开始后 5 分钟）
阶段 2 — scheduled_copy_enable alarm（活动开始后 5 分钟）：
  从 storage 读 _enableParams → getSpcCdsFromCookies() 刷新 SPC_CDS →
  runEnableLoop() → ENABLE_PROGRESS/ENABLE_COMPLETE 正常流转
```

**为什么分两阶段**：旧代码建完空活动立刻提交商品，活动未开始时 API 拒绝，全部 SKU 失败并触发零进展僵局检测而终止。

### `_copiedSaleData` 缓存验证

```
loadFlashSaleProducts(fsId) → 找到 _copiedSaleData 条目 →
  调 get_shop_flash_sale_item_id_list API → 用 Set 双向比对商品 ID →
  不一致：删条目 + 回退到正常 API 路径 | 一致：用缓存 →
  (v1.7.0) 之后一律再调 fetchProducts() GraphQL 刷新库存
```

### 自动模式（在 background）

```
START_AUTO_MODE: 验证场次 → 清残留状态 → 构建含 enableParams 的 status →
  logAutoMode → scheduleNextRound()
scheduleNextRound():
  调试模式：伪造 fakeTargetTime | 正常：找下一个场次（第一轮优先用选定场次）→
  phase='waiting_create' → 建 auto_mode_create alarm（targetTime - advanceMinutes）
auto_mode_create alarm: handleAutoModeCreate()
  关闭进行中活动 → 取时段 → 在 nextTargetTime 附近选最佳场次 →
  建空活动 → saveCopiedSaleData(新活动) → 存 status →
  logAutoMode → 建 auto_mode_enable alarm（targetTime + delayMinutes）
auto_mode_enable alarm: handleAutoModeEnable()
  GraphQL 刷新库存 → 同步到 _copiedSaleData →
  构建 EnableParams → runEnableLoop() → logAutoMode →
  sourceFlashSaleId = currentFlashSaleId（链式沿用）→ scheduleNextRound()
auto_mode_heartbeat alarm: sendAutoModeUpdate() → 同步到 popup/content
STOP_AUTO_MODE: 清 alarms + _enableParams + 存 stopped 状态 + 移除 _autoModeStatus
```

## 消息协议

| 方向 | 消息 |
| --- | --- |
| **Popup → Background** | `START_ENABLE`、`STOP_ENABLE`、`GET_ENABLE_STATUS`、`CLEAR_ENABLE_STATE`、`SPC_CDS_REQUEST`、`EXECUTE_COPY`、`SCHEDULE_COPY`、`TRIGGER_SCHEDULED_COPY_NOW`、`GET_TIME_SLOTS`、`GET_FLASH_SALE_ITEM_COUNT`、`CLOSE_FLASH_SALE`、`COPY_FLASH_SALE`、`APPLY_TEMPLATE_ITEMS`、`GET_SCHEDULED_STATUS`、`START_AUTO_MODE`、`STOP_AUTO_MODE`、`GET_AUTO_MODE_STATUS`、`SHIPPING_PREVIEW`、`SHIPPING_PRODUCT_LIST`、`SHIPPING_IDENTITY`、`SHIPPING_START`、`SHIPPING_STOP`、`SHIPPING_SYNC_ALARMS`、`SHIPPING_RESTORE_LOGISTICS`、`SHIPPING_ACK_INTERRUPTED`、`SHIPPING_GROUP_SAVE`、`SHIPPING_GROUP_REVOKE`、`SHIPPING_GROUP_STATUS` |
| **Background → Popup** | `ENABLE_PROGRESS`、`ENABLE_COMPLETE`、`AUTO_MODE_UPDATE` |
| **Background → Content** | `ENABLE_PROGRESS`、`ENABLE_COMPLETE`、`COPY_SCHEDULED`、`COPY_PROGRESS`、`COPY_COMPLETE`、`AUTO_MODE_UPDATE` |
| **Content → Background** | `STOP_ENABLE`（通过进度面板的停止按钮） |

**基于 storage 的可靠通道**：`_copyTaskStatus`、`_enableProgress`、`_enableParams`、`_copyCountdown`、`_copiedSaleData`、`_autoModeStatus`、`_autoModeLogs`、以及 shipping 的 `_shippingTask`／`_shippingPreview`／`_shippingPickList`／`_shippingIdentity`／`_shippingGroups`／`_shippingStartError`。当 `sendMessage` 响应不可靠（MV3 已知问题）时用它。content 的 `storage.onChanged` 监听 `_enableProgress`、`_copyCountdown`、`_autoModeStatus` 作为消息投递失败时的备用。

> ⚠️ **shipping 的预检结果必须从 storage 读，不能只看消息返回值**：seller 页的 content script 会同步
> `return false` 抢先应答，且这个响应早于 background 的异步预检结束。细节见
> [`07-前端与状态.md`](./07-前端与状态.md#为什么预检结果要落盘踩过的坑)。

## 商品备货与物流（features/shipping）

M02.1 在后台多了一条**独立**链路，与特卖三件套（开卖／复制／自动模式）并列但互不共用 storage：

```
SHIPPING_PREVIEW: 读商品分页 → 特卖排除调查 → 范围过滤 → 目标预览（零写请求，落盘归属锚 + 内容快照）
   ↓ 用户确认（带着 previewRequestId）
SHIPPING_START: 核对预览归属 → 核对确认内容（设置与集合） → 核对计划锚
   → 每次写前核验（归属 + 现行后端权限，返回同一份已核实上下文）
   → （可选）物流快照并关闭 → 分批改备货（批≤50／并发≤2）
   → 回读未确认项 → （可选）恢复物流 → 终态
SHIPPING_STOP: 只阻止后续商品写；物流恢复继续执行
SHIPPING_GROUP_SAVE／REVOKE／STATUS: 单次成对安排的保存／撤销／只读状态（第 31 节）
shipping_plan_check alarm: 台湾时区判定 → 冲突时等待 → 启动同一条 runner（旧单阶段计划）
shipping_group_check alarm: 单次组补检 → 窗口／错过／恢复义务判定 → 启动同一条 runner
```

- 模块分工与文件写权见 [`03-代码地图.md`](./03-代码地图.md#功能模块目录features)；前端状态见 [`07-前端与状态.md`](./07-前端与状态.md#商品备货与物流featuresshipping)。
- **双向互斥**：shipping 启动前查特卖／复制／修复是否在写；特卖开卖／复制／修复入口通过
  `findActiveRepairConflict()`→`findShippingWriteConflict()` 也能看见 shipping。缺任一侧都会出现"两边同时改同一商品"。
- **本功能不调用 `consume-trial`**：复用 `/validate` 的现有服务端校验，不新增收费规则。
- **预览记录是"参数与商品集合"的唯一依据**（返工 17.1／20.1）：启动消息只用来比对，
  执行参数与目标**只从记录构造**；多出预览外商品或改了天数／范围／排除／物流开关一律拒绝并要求重新预检。
  物流开关必须是 boolean（字符串 `"true"`／`"false"` 一律拒绝：按 JS 真值语义 `"false"` 会变成"开"）。
- **核验与发送共用同一份已核实上下文**（返工 17.2／20.2／23）：`verifyWriteAnchor()` 返回凭据 + 身份，
  业务请求只用它；发送前复查**先逐项核对归属再看凭据**，账号读不到（null）也算停；
  凭据刷新时**必须用新凭据重新核验服务端权限**（归属没变不代表权限还在），
  仅凭据刷新且权限仍允许才不算换店。
- **物流开关文案与行为必须一致**（返工 14.5）：勾选了「自动管理店铺物流」而渠道状态读不到时，
  预检就失败并提示"取消勾选后重新预检"，runner 也会停写。界面**不能**说"这不影响改天数"。

### 单次成对安排（第 31 节；第 53.4 节 U15 起是唯一主入口）

功能页**不再有模式页签**：一次确认**一组**"切 1 天 → 恢复常规天数"的安排，
取代旧的"两项独立计划"，也取代原来的「立即修改」单向入口（共用后台能力与记录都保留）。
旧 `_shippingPlans` 记录**保留不动**（不删、不改写），新流程走独立键。

```
shipping_group_check alarm（每 2 分钟，与 shipping_plan_check 分开）
  → 读 _shippingGroups（本地记录是事实来源，先恢复 alarm 再补检）
  → 归属核对（店铺／后端账号必须与本组锚一致，不一致只等待）
  → decideGroupAction：待开始 / 切现货中 / 等待恢复 / 恢复中 / 已完成 / 已错过 / 需处理
  → 认领阶段并**先落盘**，再用同一 runner 启动当轮任务
  → runner 真实终态回写组记录（不是"启动成功"就当成功）
```

- **执行方式固定单次**（`executionMode: 'once'`）：后台**主动拒绝** `daily`／`weekly` 等循环模式，
  不是只在界面隐藏；保存失败的校验发生在后台，界面只是提前提示。
- **启动窗口**：首次切 1 天必须满足 `startAt ≤ now < min(startAt+5分钟, restoreAt)`。
  过窗口且**从未发过写请求** → 标「已错过」，两阶段零写，**绝不补切现货**。
  5 分钟是固定容差，不做用户配置。
- **恢复对象只用已确认集合**：只有"本轮已确认达到 1 天"（`success` 或 `unknown`）的商品进入恢复；
  排除项、首阶段未确认可处理项、开始后新上架的商品都不扩大纳入。
  `unknown` 表示"可能已生效"，因此**义务必须保留**，不能被丢掉或报成完成。
- **未知结果不重发**：写响应与回读都不确定时标 `unknown` → 到点先核实再恢复；仍无法确认则标「需处理」。
- **阶段只前进**：迟到回调按 `groupId`／`phase` 判定，不得把已完成阶段改回去；
  重复 alarm／重复 UI 消息不得重复认领同一阶段（认领前先落盘）。
- **互斥**：已有运行／待恢复／需处理时不允许保存新组；未开始可整组撤销且零写，
  **一旦发出过商品写就不再允许直接撤销**，只停止后续切现货、保留恢复义务。
- **物流按每次批改各自收尾**：勾选自动管理时，每次批改结束立即恢复本次影响的渠道，
  **不会**从切 1 天一直关闭到恢复时刻；原本关闭的渠道不打开。
- **归属不符只等待**：换店／换账号（`currentOwnership` 与组锚不一致）时保留义务并等待用户切回，
  **不标「需处理」**——否则用户切回后仍看到需人工处理。

### 返工要点（第 34 节，2026-10-15）

- **旧每日／每周计划已停用**：`retireLegacyRepeatPlans()` 在**读取**（`readShippingPlans`／`clampPlans`／
  界面同步）与**保存**两侧强制降级，`checkShippingPlans` 会把迁移真正落盘。
  记录**保留**（`retired` + 原因 + 历史 `lastRunId`／`lastTaskId`），不删除、不改写历史。
  只改保存分支不够：任一入口能写回 `enabled` 的重复计划，旧任务就会重新跑起来。
- **截止落在真实写边界**：组启动时算出 `spotWindowDeadline` 作为**首写窗口**交给 runner
  （`writeDeadlineAt`），并把 `restoreAt` 作为**全程截止**（`hardStopAt`）。
  两者用途不同：首写窗口只管"第一批切 1 天必须落在窗口内"；已经正常开始的分批允许超过 5 分钟容差，
  但到 `restoreAt` 必须停止发送**新的**切 1 天批次（`onSpotBatchSent` 触发后由
  `canSendSpotWrite` 切换判据）。`submitChunk` 在**核验等异步准备之后、发请求之前的最后一步**
  再判一次，越过即整批未发送；分批过程中越界也停止后续批次。
  只判调度决策、或把闸门放在异步准备之前，都会漏掉"判定通过 → 耗时 → 越过截止才发出"。
  未发送的批次要经 `fillUnsent` 给**所有**还没有结论的目标项补上 `pending` + 原因，
  只补 `pending` 数组会漏掉"因 break 从未进入循环"的那些商品。
- **检查点接回的组必须保留恢复义务**：`restoreItemIds` **以 `confirmedSpotItemIds` 为唯一依据**，
  不能再按 `items` 上的 `spot` 状态过滤。设备在商品写请求进行中退出时，组是从**检查点**接回来的
  （发出过请求、结果没回来），这些商品在 `items` 里仍是 `pending`；若据此剔除，
  恢复对象会变成空集、整组报"没有需要恢复的商品"并结束，而商品还停在 1 天。
  同理 `applyTaskResultToGroup` 的义务集合也以 `confirmedSpotItemIds` 为准，
  并把"有义务但没有逐项明细"的项计入 `pendingItemIds`。
- **中断接回**：`recoverInterruptedGroup` 按关联任务（`groupId` + `groupPhase` + `spotTaskId`／`restoreTaskId`）
  把卡在 `cutting`／`restoring` 的组接回，读逐项结果与已发检查点，**不重放**未确认写。
  接回会把该任务 id 记进 `reconciledTaskIds` 并释放恢复阶段的认领
  （`restoreTaskId` 清空、`claimedStages` 去掉 `restore`），让补检能重新认领、逐项回读。
  另外：`handleShippingStart` 不再因为"存在 interrupted 记录"就一律拒绝。
  判据是"该记录是否仍代表本组当前那一段未完成"——**已被接回消费过的记录不再挡**
  （`reconciledTaskIds` 命中即放行），否则接回后的组会被自己的旧记录反复挡住、恢复永远起不来。
- **恢复前核实当前状态**（R4）：runner 的 `verifyCurrentDays` 逐项读权威详情——
  仍是 1 天 → 恢复；**已是目标 → `success` + `verifiedAlreadyTarget`，不重复写**；
  两者都不是 → `unknown`，留需处理、不覆盖；读不到 → `unknown`，不写。
  **不能**按记录 ID 无条件覆盖：用户可能在这之后自己改过。
- **两阶段结果不互相覆盖**（R5）：`mergeGroupItems` 只更新本阶段字段（`pending` 不算结论）；
  `groupIsComplete` 只认 `success`（或带回读证据的 `skipped`）；整组完成的判据是
  "**还有没有未了义务**"：应恢复项全部确认达标 + 物流收尾完成（从权威任务记录重读渠道义务）+
  **任务不在运行中**。不能按任务的历史终态字符串判（`completed`／`stopped`）：
  物流恢复失败会把任务落成 `failed`，用户修好后那条记录**仍是 `failed`**，
  据此判定会让组永远结不了案。`advanceGroupPhase` 终态不可回退。
- **无商品可恢复时也要看物流**：恢复阶段若发现恢复对象为空，
  **先**检查是否还有原启用渠道没恢复（`pendingLogistics`）。有 → 留 `needs-attention`
  并给出渠道原因；没有 → 才落 `done`。
  少了这一步会出现"商品都好了、渠道却还关着，组却已结束"，用户再也看不到这件事。
- **默认时刻按当时台湾日期现算**（第 53.3 节 U14）：`defaultScheduleTimes(now)` 是纯函数，
  **不能**做成模块级常量 —— popup／service worker 可跨天常驻，常量会拿昨天的日期
  算出一个已经过去的默认值，用户还没动手就已经存不下。
  默认只在**确实空白的**草稿上补（`seedDefaultSchedule`，且必须在 `syncGroup` **之后**：
  `syncGroup` 会把同店同账号"上次已完成配置"的时刻带进草稿，先补默认会把复用结果当空白覆盖掉）。
  用户改开始日期时恢复日期跟到次日，但**保留已有的恢复时刻**（"再次安排"带出的 02:15
  不能被写回 01:30）。
  第 56.2 节返工：**只有改恢复日期才锁日期**（`restoreDateTouched`）—— 早先连"改恢复时刻"也一起锁，
  于是"只改时刻 → 再改开始日"把恢复日留在过去（验收原生 popup 复现：
  开始 2100-01-02、恢复仍 2100-01-01 04:15，预期 2100-01-03 04:15）。
  时刻不需要额外标记：联动分支只在它为空时才补默认。
  开始时刻已过只提示并阻止保存，**不自动挪到明天、不补切现货** —— 悄悄改日期是未被决定的行为。
- **旧计划不能再被启用**（第 56.3 节）：闸门在 `savePlan` —— 带 `enabled` 的旧计划一律拒绝。
  界面已改成只读历史，但界面不是唯一入口（消息、旧版本页面、残留调用都会走到 store），
  而一条 `enabled` 的旧计划会被 `shipping_plan_check` 重新调度，绕过"切到 1 天后必须有恢复安排"。
  记录不删，历史照常可追溯。
  注意 `readShippingPlans` **只降级旧的每日重复，不碰一次性计划**：界面下线前存下的
  `enabled: true` 一次性记录仍会被调度，所以只读展示里保留了「停用这条旧计划」（复用既有 `removePlan`）——
  没有这个出口就与第 56.4 节"停止按钮随旧编辑区一起被删"是同一类缺口。
- **"有没有旧计划历史"不能用 `plans.length > 0` 判断**（第 59.2 节）：
  `SHIPPING_DEFAULT_PLANS` 的两张空白占位（日期空、`ownerShopId: null`、从未运行、未被迁移）也满足它，
  于是**从未设置过旧计划的人**会看到两条"未绑定，请重新保存"的假记录，而那个保存入口本轮已下线。
  store 的初始 `plans` 与无键兜底、`syncPlans` 都改为给 `[]`；呈现层再用
  `meaningfulPlans`（`rules.ts`）按**真实痕迹**过滤一次。**不能只按 `lastRunAt` 过滤** ——
  "已配置日期／归属但从未运行"的记录会被误丢。
  后台仍照旧提供自己的默认槽位，本轮只改界面所依据的状态，不动调度。
- **物流收尾不能靠组的当前阶段猜**（第 40.2 节 R5）：`reconcileGroupAfterLogisticsRestore`
  必须用**权威任务自己的 `groupPhase`／`taskId`** 判断这是哪一段的结果。
  早先从组当前阶段推断（`awaiting-restore`／`needs-attention` 一律当恢复段），
  于是首阶段（spot）渠道修好时，把那条任务的**切现货 success** 当成"恢复成功"
  写进 `restore` 字段，组误报 done、清空 active 并撤掉恢复 alarm ——
  商品还停在 1 天，**常规恢复义务直接丢失**（最严重的一条）。
  现在：首阶段渠道修好只收尾首阶段物流，保留 `awaiting-restore`、商品义务与恢复 alarm；
  恢复段商品确已达标且渠道收尾后才结束整组。
- **认领了但没创建任务也要能继续**（第 40.3 节 R3）：恢复段在**创建任务之前**失败
  （临时 503／权限暂拒／身份读取抛错）时，`startTask` 失败或抛错都会
  `releaseStageClaim` 释放本次认领、退回 `awaiting-restore`（首阶段退回 `scheduled`），
  让下一次补检重新核验；
  `recoverInterruptedGroup` 也会在"组已认领但手上任务不是本段"时释放认领。
  早先直接落 `needs-attention`，而"恢复段的中断任务"根本不存在（手上是更早的 spot 任务），
  接回无路可走 → 组永久停在需处理、商品停在 1 天。
  释放**不绕过校验**：身份／权限／窗口闸门仍在 `decideGroupAction` 里。
- **发出即算开始**（第 40.4 节 R2）：`onSpotBatchSent` 要在 `updateProductBatch`
  **被调用之前**触发，不能等 `await` 返回。早先放在 await 之后，
  首批响应慢时 `spotBatchSent` 仍是 false，其它批次继续受 5 分钟首写窗口限制：
  实测"第 4 分钟首批已发出、响应挂起跨过第 5 分钟"，125 件只写了 50 件、其余被误截。
- **保存先固定草稿归属**（第 40.5 节 R7）：`saveGroup` 在**第一次** `refreshOwner`
  之前就记下 `draftShopId`／`draftUserId`，此后任何一次核实与它不一致都**整次拒绝**。
  早先"捕获 A 草稿 → 首次刷新成 B（清空草稿）→ 取 shopBefore（此时已是 B）→ 第二次刷新仍 B → 放行"，
  最终提交的却是第一次捕获的 A 草稿（含 A 店排除）。第二次核对补不上第一次换店的漏判。
  `loadPickList` 的返回分支同样要比较"请求发起时的店铺"与"当前已核实店铺"，
  不一致就**整份丢弃**（迟到响应不得回灌新店）。
- **界面跟随真实状态**（R6）：`ShippingWorkPage` 订阅 `_shippingGroups`；
  已开始时「停止」走真正的停止机制（落 `stopRequested`，停后续切现货批次），
  而不是调用只对"未开始"有效的撤销。
- **跨店隔离**（R7）：`setOwner` 在归属变化时清空 `pickList`／草稿／上次配置；
  `reuseLastGroup` 与 `syncGroup` 核对同店同账号；「勾选当前结果」基于**完整匹配结果**而不是渲染上限。
- **候选列表按完整归属判定**（第 43.2 节 R7）：归属标记是**店铺＋账号**
  （`pickListShopId` + `pickListOwnerUserId`）。只比店铺会漏掉"同一家店换账号"这条路径：
  旧账号的候选仍被判为可信，用户能把旧账号的商品确认进新账号的安排（验收在真实 store 上复现）。
  判据统一为 `rules.ts` 的 `isPickListOwnedBy()`，store 的返回分支与排除弹窗**共用同一条**；
  弹窗必须实际调用它，不能退回只比店铺。
  列表请求另带**序号**（`pickListRequestSeq`）：只有最新一次请求有权写结果，
  先发起的迟到响应直接作废 —— 既不得回灌新归属，也不得覆盖用户刚刷新出的新列表。
- **排除弹窗的本地未确认勾选也带归属**（第 46.2／49.2 节 R7）：隐藏旧列表行**不等于**挡不住提交。
  弹窗的 `picked` 记下"勾选形成时的归属"（`draftOwnerKey`），归属一变就清空勾选并提示已失效；
  确认入口**再核对一次**（提交那一刻的判据，防止父组件换归属与点击落在同一批渲染里还没跑完 effect）。
  为什么不能只依赖父组件的 `confirming` 变化：`ShippingSchedulePanel` 的
  `excludedIds` 是 `parseExcludeIds(draft.excludeIds)` 的 memo，归属变化把草稿清成空串时，
  若原本也是空串，数组**引用不变**、重置 effect 不触发，本地勾选就留了下来（验收在真实父页面复现）。
- **失效必须有独立状态，不能只看"勾选是否为空"**（第 49.2 节 R7）：
  只把 `picked` 清空会引入一个更隐蔽的错 —— 清空之后的"没有勾选"和"本来就不排除商品"
  在数据上完全一样，确认入口于是把**失效**当成功提交，把本次安排悄悄改成"不排除任何商品"
  （验收实测：`confirmed: []` 且 `save.success: true`）。
  因此用独立标记 `draftInvalidated`：失效置位后，确认入口**拒绝且不调用 `onConfirm`**、弹窗不关闭、
  提示保持；只有用户在**当前归属**下重新操作才解除 —— 重新勾选，或主动点「清空选择」
  （后者是"我明确选择不排除商品"，必须放行，否则用户想表达空排除会被一直挡住）。
  区分点是**失效导致的自动清空** vs **用户在当前归属的明确选择**，不是禁止一切空选择：
  从未失效过、本来就不排除商品的空集合照常可确认。
- **启停脚本的实例归属**（第 40.6 节 R8）：实质逻辑在 `iso-env.ps1`，`.cmd` 只做双击入口。
  为什么不能写在 cmd 里：cmd 需要 `enabledelayedexpansion` 才能用 `!VAR!`，
  而本轮测试密码含 `!`，开启延迟展开会把 `!` 吃掉、破坏账号启动；
  且默认环境下 `!OCCPID!` 会被**原样**传给查询（实测输出 `ProcessId=!OCCPID!`），根本认不出自家实例。
  归属依据是启动时写入的 `instance.json`：**PID + 创建时间 + 专用数据库绝对路径 + 工作目录**，
  停止与"端口已占用"判断逐项对照；任一项不符即拒绝，绝不自动认领外来端口，也不按进程名批量结束。
- **写记录前先证明"监听者来自本次启动"**（第 43.3 节 R8）：上面四项只能证明
  "监听者与记录相符"，证明不了"记录最初就写对了"。启动失败或还没就绪时，
  若别的项目恰好占住同一端口且健康检查也通过，旧流程会把那个外来进程写成"本轮实例"，
  之后「停止测试环境」照着记录把它停掉 —— 停错服务。
  现在启动前先把本次启动进程写进 `launch.json`，健康通过后沿**父进程链**确认监听者在其子进程树内、
  且进程链里出现本轮专用库的绝对路径，才准写 `instance.json`（并带 `source: derived-from-this-launch`）；
  证明不了就明确失败（退出码 4），不写记录、不认领、不停外来进程。
  记录缺来源标记（旧流程写的）一律拒绝认领。
  命令行入口 `start-iso-backend.ps1` 也**转调同一受检入口**，不自己起进程（否则起的实例没有归属记录）。
  辅助后台用 Hidden 启动。



## 缓存

- 30 分钟缓存，存 `browser.storage.local` 的 `flashSaleCache` 键（类型见 `types.ts` 的 `CacheData`）
- 持久内容：`products`、`flashSaleList`、`flashSaleId`、`enableProgress`、`skuOverrides`、全局参数
- popup 打开时自动加载；抓取／开卖后自动保存
- 手动清除：「清除缓存」按钮（v1.6.4 起在底部「更多」折叠区），执行 `clearCache()` + `reset()` + `extractSpcCds()`

**storage 键命名约定**：下划线开头 = 内部状态（`_enableProgress`、`_copiedSaleData`）；无前缀 = 可缓存数据（`flashSaleCache`）。**原因**：`clearCache()` 只清后者；混用会导致清缓存把正在跑的进度一起抹掉。

## 虾皮接口速查

- **GraphQL**：`POST /api/marketing/v4/graphql/query/` —— 商品／SKU 详情（查询语句在 `api.ts` 的 `PRODUCTS_QUERY`）
- **限时特卖**：`/api/marketing/v4/shop_flash_sale/{get_shop_flash_sale_list, get_shop_flash_sale_item_id_list, set_shop_flash_sale_items, set_shop_flash_sale, get_time_slot_id, get_shop_flash_sale_item}`
- **必需请求头**：`sc-fe-session`（CSRF token，从页面 DOM／window 提取）
- **必需请求体字段**：`use_global_category: true` —— 缺这个会报 code 1001
- **价格规则**：必须是整数，且严格小于原价

### 备货／物流（REST，与上面 GraphQL 是两套契约）

| 用途 | 方法与路径 |
| --- | --- |
| 商品分页／回读 | `GET /api/v3/product/search_product_list_v2/`（`page_size=50,source=attribute_tool,cursor,version=4.0.0`） |
| 批量改备货 | `POST /api/v3/product/update_product/?version=3.1.0&source=attribute_tool`（数组 `[{id,category_path,pre_order,days_to_ship}]`） |
| 商品详情（按需） | `GET /api/v3/product/get_product_info`（`product_id,is_draft=false`） |
| 物流渠道列表 | `GET /api/v3/logistics/get_channel_list`（`data.list[].channel_id/enabled`） |
| 渠道开关 | `POST /api/v3/settings/update_channel_toggle`（`{command:'set_enable',enabled,channel_id,proceed_with_mass_toggle_on_item_channels:false}`） |

⚠️ **`status` 是两套不同契约**：这里在线 `=1`、下架 `=8`；特卖 GraphQL 的活跃是 `status=0`。
两边都可能以字符串返回，比较必须 `Number(...)`。不要互相套用常量。

**写结果的三种态必须分开**（2026-10-14 返工）：`topLevelSuccess`（顶层 code 0）、
逐项 `code`（**缺就记 `null`，不得默认成 0**）、`transportUnknown`（超时／不可解析 → 可能已写，**不得重发**）。
只有明确限流（HTTP 429／409／业务码 `1000100006`）才退避重试。详见
[`07-前端与状态.md`](./07-前端与状态.md#读不全就不写写未知不重发2026-10-14-返工)。
