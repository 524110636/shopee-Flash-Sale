# 06 商品与活动

> **用途**：一键修复 1 天备货 SKU、折扣移除与恢复、复制限时特卖、开卖循环、守卫与阈值、平台响应格式。
> **何时读**：改商品发布、折扣、复制、提交特卖相关逻辑；排查「修复失败」「折扣没恢复」「商品没提交上」类问题。
> **来源**：原 `AGENTS.md` 的 Copy Flash Sale Flow／Flash Sale Enable Flow／Enable Loop Guards／SKU Override／商品相关决策，以及 `CLAUDE.md` 的 one-day SKU 段。

## 一键修复

### 它做什么

为商品添加／更新一个专用 SKU「**批發客戶下訂-請勿下單**」，带 1 天出货设置。全流程在 **popup**（非 background）中运行，入口是 `store.ts` 的 `runOneDaySkuAndEnable()`。

### 完整流程

```
get_product_info（取商品详情）
→ 检测已有 1 天 SKU（有则跳过新建）
→ buildOneDaySkuProductInfo()（构建新的 model 列表）
→ 搜索折扣活动（discount/search）
→ 从折扣中移除（delete_abnormal_seller_discount_items）
→ 【防抖 2s】
→ 发布商品（update_product_info）
→ 5 倍价格检测 & 重试（重试路径同样：重新移除折扣 → 【防抖 2s】→ 重新发布）
→ 重新获取商品信息（最多 3 次重试、间隔 1s）
→ 【防抖 2s】
→ 恢复折扣含新 SKU（update_seller_discount_items，多折扣之间各间隔 2s）
→ 检查 failed_item_list / error_list
```

### 四个防抖节点（v1.8.6）

为避免虾皮 API 处理延迟导致请求异常，在**移除折扣 → 发布 → 恢复折扣**之间插入防抖：

1. 移除全部折扣后等 2s 再发布
2. 发布成功后等 2s 再恢复第一个折扣
3. 多个折扣活动操作之间各间隔 2s
4. 5 倍价格差重试路径：移除后等 2s 再重新发布

**实现细节**：涉及折扣的三个循环从 `for-of` 改为**索引循环**，用 `di > 0` 条件**跳过首次请求的延迟** —— 第一次操作前没必要等（前面刚等过），只有后续多次才需要间隔。

### 数据流 `buildOneDaySkuProductInfo()`

输入：
- `ShopeeProduct`（GraphQL camelCase）
- `ProductInfoPayload`（REST snake_case，来自 `get_product_info`）

处理：
1. 在 `std_tier_variation_list` 第一层追加／查找「批發客戶下訂-請勿下單」选项
2. 通过 `generateTierCombinations()` 生成新选项与**其他所有层**的笛卡尔积组合索引
3. 已有 model 经 `cleanModel()` 剥离响应格式字段，保留 `id`、`tier_index`、`price`、`stock_setting_list`、`pre_order_info`

### 多规格组合生成

`generateTierCombinations(newTier0Idx, tierVariationList)` 遍历第 2～N 层的所有规格选项，生成 `newTier0Idx × count(tier2) × count(tier3) × ...` 个组合。

**例**：第一层新增索引 4、第二层 8 个选项 → 生成 `[[4,0],[4,1],...,[4,7]]` 共 8 组。

### 100 组上限保护

虾皮限制每个商品最多 100 个 model。创建前检查：

```
nextModelList.length + tierCombinations.length > 100
```

超限抛出清晰错误。

**为什么**：超限时 API 会整体拒绝该商品更新，用户只看到「发布失败」不知原因。

### 库存提取

`extractSellableStock()` 同时处理两种格式：
- `stock_setting_list`（请求格式）
- `stock_detail`（响应格式）

从 `seller_stock_info[0].sellable_stock` 取可售库存。

### 折扣率检测

`getDiscountRatio(modelList)` 遍历现有 SKU 的 `price_info.input_promotion_price / input_normal_price`，返回**最高比率**（最轻折扣 = 最高折数，如 6.5 折 > 5.4 折 → 0.65）。用于给新增的 1 天备货 SKU 算折扣价（它们没有 `input_promotion_price`）。

### 折扣恢复列表构建

`buildDiscountRestoreList(modelList, productId, discountRatio?)` 把 `model_list` 转成 `discount_model_list`（`update_seller_discount_items` 请求体）：
- 已有 `input_promotion_price` 的 SKU 直接用现有折扣价
- 没有的（新增 SKU）在提供 `discountRatio` 时用 `normalPrice * discountRatio`

### 折扣率自动检测并同步全局（v1.8.7）

`runOneDaySkuAndEnable` 遍历商品时用 `collectedRatios` 收集每个商品的实际折扣率（`getDiscountRatio(originalModelList)`），包括**已有 1 天 SKU 的商品**和**修复后成功的商品**。

全部收集后计算全局 `discountRate`：所有商品折扣率一致时直接用该值，不一致时取平均值。

**为什么**：确保修复完成后向导显示的折扣是用户实际设定的（如 5.4 折 → 54%），而不是默认值 60%。

### UI 文案脱敏

`runOneDaySkuAndEnable` 所有**用户可见**的 `message` 字段统一为「正在优化商品 (X/N)...」。

原文案（`获取商品信息 X/N: 商品名`／`搜索折扣活动 X/N`／`移除折扣活动 X/N`／`发布商品 X/N`／`恢复折扣活动 X/N`）全部改掉；`App.tsx` 的 phase 标签（`检查 SKU`／`发布商品`／`查询折扣`／`移除折扣`／`恢复折扣`）统一显示「优化中」。

`console.log` 的 `[一键修复]` 日志**保持不变**（开发者调试用）。

**为什么**：这些技术步骤暴露给用户没有帮助，反而让用户误以为需要理解内部流程。

### 控制台日志

每一步都输出带 `[一键修复]` 前缀的日志，含商品名、动作、结果数据。

## 折扣移除与恢复

### 移除

`delete_abnormal_seller_discount_items`，多个折扣活动之间间隔 2s。

### 恢复

`update_seller_discount_items`。**必须检查响应中的 `failed_item_list`／`error_list`，即使顶层 `error: 0`。**

**为什么**：虾皮部分失败时仍返回顶层成功；只看 `error` 会漏掉「折扣没恢复成」，用户的商品在修复后失去原有折扣，直接影响售价。

### 已结束折扣过滤

`extractSellerDiscounts` 会过滤掉 `timeStatus === 3` 或 `endTime < now` 的已结束折扣。

**为什么**：对已结束的折扣执行移除/恢复会报错并打断整个流程。

## 复制限时特卖

### 流程

1. `enterCopyMode(flashSale)` —— 加载源活动商品数**与商品**到 store。
   **为什么必须载入商品**：模板应用依赖 `state.products`。不载入时 `state.products` 是空的或是上一个活动的残留，模板应用会失败或作用到错误商品 —— 直接导致 100% 失败。
2. `CopyConfirmPanel` —— 顶部三步提示（选择源活动 → 选择目标时间 → 创建复制任务），蓝底活动信息卡片 + 查看源活动商品
3. `executeCopy(targetTime)` —— 四步执行：
   - **步骤 1**：关闭进行中的限时特卖（`status=1`）
   - **步骤 2**：`get_time_slot_id/` 取可用时段
   - **步骤 3**：`set_shop_flash_sale/` 建空活动（带 `{ time_slot_id }`）
   - **步骤 4**：`saveCopiedSaleData()` 本地保存源商品数据（供 popup 显示）
   - （步骤 5 自动提交已在 v1.5.0 移除 —— Demo 按钮不再提交商品）
4. `SCHEDULE_COPY` —— 用 `chrome.alarms` 定时执行
5. `TRIGGER_SCHEDULED_COPY_NOW` —— 手动立即触发定时复制

### 为什么用手工复制而非服务端自动复制

试过用 Referrer 头让服务端自动复制（`from=sourceId`），在扩展的 `fetch` 环境下不稳定（时好时坏），会出现「新活动是空的」。手工拉取（`get_shop_flash_sale_item/`）再提交（`set_shop_flash_sale_items/`）虽多一次请求，但结果确定。

### 时段默认选择

`CopyConfirmPanel` 的 `useEffect` 默认选中 `slots[0]`（第一个可用时段）。移除了原来的「当前时间 +2 小时」最近时段启发式算法 —— 该算法可能跳过第一场选到第二场。

### 定时任务两阶段

见 [`02-架构总览.md`](./02-架构总览.md#定时复制两阶段-alarm) 与 [`01-红线.md`](./01-红线.md#alarm-恢复与已有时间复用)。

`executeScheduledCopyFlow()` 设置 `infiniteRetry: true`，让开卖循环不因 10 轮上限而停止。

### 手动触发与等待超时

`TRIGGER_SCHEDULED_COPY_NOW` 手动立即触发。

- **等待超时是 120 秒**（不是默认的 60 秒）—— 为 `EXECUTE_COPY` 的自动提交重试留时间
- **超时后后台仍继续执行**，不会因为 popup 等不到结果而中止
- 用户可**重新打开 popup** 查状态（读 `_copyTaskStatus`）

### 定时任务存活检测

`GET_SCHEDULED_STATUS` 消息：store 的 `checkScheduledCopy` 发消息到后台，后台从 storage 读 `_scheduledCopy` 参数并用 `chrome.alarms.get('scheduled_copy')` 检查 alarm 是否仍注册，返回 `ScheduledTaskStatus`（`exists`、`alarmActive`、`params`、`alarmScheduledTime`、`remainingSeconds`）。

**状态卡的显示与失败回退**：

- 卡片**仅在** `hasScheduledCopy && scheduledTaskStatus?.exists` 时渲染
- **若后台无响应**（如 Service Worker 未就绪），catch 块**只**把 `alarmActive` 置为 `false`，**不清空 `_scheduledCopy` 数据** —— 定时任务本身还在，不能因为查不到状态就把它当没创建
- `checkCopyTaskStatus` 与 `executeCopy(SCHEDULE)` 成功路径都会触发 `checkScheduledCopy`

`ScheduledTaskCard` 用 1 秒 tick 展示实时倒计时 + 四步进度（复制模板 → 创建任务 → 等待开始 → 手动开启）。

### 强制刷新列表

`fetchFlashSaleList` 有 `force` 参数；`force=true` 时跳过虾皮 API「返回数量减少」的缓存保护逻辑。用户点「刷新」时传 `force=true`，删除活动后也能实时更新。

保护逻辑在非主动刷新时（`!force`）继续生效 —— **原因**：防范服务端缓存不一致导致列表回退。

### 复制后自动加载商品

`executeCopy` 在确认新活动 ID 出现在列表后追加 `loadFlashSaleProducts(newId)`，从 `_copiedSaleData` 读复制时保存的商品数据（含 SKU 覆盖参数）。用户返回主界面直接可见已加载商品，不再出现「该活动中没有找到商品」。

### 已结束活动处理

- 活动列表卡片的 `onClick` 在 `isEnded` 时直接 `return`，不再调用 `loadFlashSaleProducts`
- 已结束活动用虚线边框 + `opacity-50` 弱化，移除 `cursor-pointer`
- 复制按钮不受影响（独立 `onClick` + `stopPropagation`）
- 「开启限时特卖」按钮下方有已结束活动检查，`now >= currentSale.end_time` 时显示红色提示：「该活动已结束无法开启，请点击「复制」复制此活动而不是选中此活动」。纯 UI 层判断，不依赖 `error` 状态，不干扰其他错误提示。

**为什么**：用户点已结束的活动只会得到困惑的空白，不如直接不可点。

### 复制后通知

`exitCopyMode` 检测到成功复制时，把 `CompletedCopyInfo` 存 Zustand 状态 + `browser.storage.local`。主界面显示绿色通知卡 + 「立即查看」按钮，自动跳转到新活动。

### `_pendingFlashSaleData` 内存传递

复制流程建完新活动后，商品数据**同时**存 Zustand 状态（`_pendingFlashSaleData`，非 storage）让 `loadFlashSaleProducts` 立即读到，绕过 storage 竞态。

**为什么**：`storage.onChanged` 的投递有延迟；新建空活动后马上读会读到滞后状态。

### 复制完成后的通知（`_completedCopyInfo`）

`exitCopyMode` 检测到成功复制时，把 `CompletedCopyInfo` **同时**存 Zustand 状态与 `browser.storage.local`。主界面显示绿色通知卡 + 「立即查看」按钮，点击调 `loadFlashSaleProducts(_completedCopyInfo.newFlashSaleId)` 跳转到新活动。

**为什么两份都存**：状态供当前会话渲染，storage 供 popup 重开后仍能看到「上次复制完成」的提示。

## 开卖循环

`runEnableLoop`（在 `entrypoints/background.ts`）的步骤：

1. 从参数构建 `EnableItem[]`，过滤掉 0 库存 SKU
2. 立即保存 `running: true` 的初始进度（让 popup 重开时看到正确状态）
3. POST `set_shop_flash_sale_items`，带 `use_global_category: true`
4. 从 `response.data.failed_items` 解析失败项
5. 重试失败项（`NOT_ENOUGH_STOCK` 错误时**自适应减半**库存，最小 1）
6. 小批量时（每批 ≤10 个失败项）跑诊断查询
7. 用 `EnableProgress` 接口跟踪进度（轮次/成功/失败数）
8. 致命错误（找不到卖家标签页）自动停止循环

## 守卫与阈值

| 守卫 | 阈值 | 作用 |
| --- | --- | --- |
| `_enableRunning` | — | 防并发循环；函数入口检查，**始终在 `finally` 复位** |
| `_enableStopRequested` | — | 允许通过 `STOP_ENABLE` 干净停止 |
| **零进展僵局检测** | 连续 **10** 轮 0 成功 | 停止循环，捕获不自行恢复的持久 API 错误 |
| **低失败僵局检测** | 失败 SKU **≤5** 且连续 **10** 轮数量不变 | 自动停止 |
| **SPC_CDS 周期刷新** | 每 **3** 轮 | `getSpcCdsFromCookies()` 重新读，防 token 过期（`code 1001 spex common error`） |
| 致命错误 | — | 无卖家标签页则立即停止 |
| storage 读取重试 | 5 次尝试 | 处理 SW 冷启动时序 |

**为什么 `_enableRunning` 必须在 `finally` 复位**：一旦某次异常跳过复位，后续点「开启」会毫无反应（被自己的锁挡住），且没有任何报错。

**为什么刷新 SPC_CDS**：长循环会撞上 token 过期，表现为**所有** item 同时返回 `code 1001`。若不刷新，零进展检测会在 10 轮后终止整个任务。

## 平台响应格式

### `get_shop_flash_sale_item/`

返回两种可能格式（都要处理）：

- `data.items` —— SKU 级数组，含 `item_id`、`model_id`、`stock`、`purchase_limit`、`promotion_price`
- `data.item_info` —— 商品级数组，含 `itemid`、`price`、`stock`、`images`
- `data.model_info_str` —— JSON 字符串，SKU 常规价：`{"itemId":[{"modelid":123,"price":99,...},...]}`

`model_info_str` 缺失时用 `item_info[].price` 兜底。

### `model_info_str` 解析陷阱

格式是 `{ itemId: [ { modelid, price, stock, ... }, ... ] }`（**数组**，不是嵌套对象）。

解析：先 `JSON.parse` 得 `Record<string, Array<...>>`，再构建 `priceLookup: Record<string, Record<string, number>>` 供后续查找。

**旧代码误当作** `{ itemId: { modelId: { price } } }`，导致全部 430 条 `promoPrice` 缺失。

### `promoPrice` 来源

`configItems[].promotion_price` 才是实际促销价；`model_info_str[].price` 是商品**原价**。

`loadFlashSaleProducts` 正常 API 路径直接用 `ci.promotion_price` 作为 `promoPrice`，不再从 `priceLookup` 取。修复后 430 条命中率从 0 → 430。

### Per-SKU `discountRate` 反推

`loadFlashSaleProducts` 在 `await fetchProducts()` 完成后，遍历每个 SKU 用 `Math.round(promoPrice / originPrice * 100)` 反推 `discountRate` 填入 `skuOverrides[key]`。复制数据加载路径（`_copiedSaleData`）同样处理。

**为什么**：确保 `SkuTable` 的折扣%列与限时价列同时显示实际值，而不是一个有一个空。

### `_copiedSaleData` 缓存一致性校验

`loadFlashSaleProducts` 找到缓存后、使用前，先调 `get_shop_flash_sale_item_id_list` API 取当前活动实际商品 ID 列表，与缓存商品 ID 做 `Set` 双向对比：

- 不一致 → 删掉该活动条目 + 重置 `copiedData=null`，回退到正常 API 路径
- 一致 → 用缓存（保留 per-SKU 参数优势）

**为什么**：修复「用户手动替换商品 ID 后界面仍显示旧复制商品」。

### `_copiedSaleData` 缓存库存刷新（v1.7.0）

缓存路径（商品 ID 校验通过后）不再直接 `return`，而是追加 `await fetchProducts()` GraphQL 调用，把新鲜 `normalStock`／`totalNormalStock` 合并入缓存商品，再 `set({ products })`。

**为什么**：两个「查看商品」入口（`ProductViewModal`、`SkuTable`）都要显示实时库存。

## 价格与提交规则

- **价格必须是整数** —— 这是**本项目的约定**：折扣率是整数百分比，若允许小数会引入额外的舍入分支，同一批 SKU 容易出现单价不一致。代码侧用 `Math.floor(price * discountRate / 100)` 保证结果为整数。
  > 平台对小数价格的**具体处理**（拒绝还是按分位截断）未经验证，此处不作断言；如需依赖该行为请先实测。
- **必须严格小于原价** —— 等于或高于原价不算促销，接口会拒绝；这是平台规则，不是本项目的额外限制。
- 请求体**必须**带 `use_global_category: true` —— 缺这个报 code 1001（`spex common error`），表现为**所有** item 一起失败，而不是个别失败；排查时容易误判成凭据过期。
- 价格计算：`Math.floor(price * discountRate / 100)`
- **`promoPrice` 优先级最高**：设置时直接用它，不算折扣率。**原因**：绕过整数折扣率的两次取整损失（原价 230、限时价 8 → 走折扣率 `Math.round(8/230*100)=3%` → `Math.floor(230*3/100)=6`，丢了 2 元）
- **`promoPrice` 与 `discountRate` 互斥**：设置折扣%时清空 `promoPrice`；设置限时价时只存 `promoPrice`（不反算折扣率）。**原因**：两者同时存在时优先级规则会让其中一个失效，用户改了一个却发现没生效。互斥保证「最后一次输入说了算」。

### SKU 覆盖固化

**复制活动时**：`executeCopy()` 补齐每个 SKU 的 `skuOverrides[key]`（含 `discountRate`、按当前折扣计算的 `promoPrice`、`stock`、`purchaseLimit`）。

**顺序约束（重要）**：补齐必须发生在**过滤当前商品之前**。先补齐、后过滤，被保留下来的商品才都带覆盖项。顺序反了会出现「先过滤掉的 SKU 没覆盖、留下的 SKU 部分没覆盖」，全局折扣行仍会吃进去。

`loadFlashSaleProducts()` 读旧 `_copiedSaleData` 时，在遍历 `copiedData.products` 的过程中同样补齐缺项（兼容旧缓存）。

**原因**：业务规则是「复制源活动的所有商品都等同手动编辑过」；不固化的话，未显式编辑的 SKU 会继续吃全局折扣行，被后续改全局参数时静默改价。

### 覆盖提示

`App.tsx` 在「开启限时特卖」标题与全局折扣/库存/限购输入行之间显示：`已有 X 个商品 / Y 个 SKU 手动修改过，不会使用下列折扣`。统计仅基于当前 `products` 中实际存在且命中 `skuOverrides` 的 SKU。

商品列表顶部另有汇总行（`已手动编辑 X 个商品 / Y 个 SKU` + 「查看详情」按钮）。

**详情父弹窗的搜索规则**（沿用 `ProductList` 的 `includes` 思路，范围扩展）：

| 匹配情况 | 展示内容 |
| --- | --- |
| 商品标题 / 商品 ID 命中 | 该商品**全部**已覆盖 SKU |
| 仅 SKU 名称 / SKU ID 命中 | **只展示匹配的**那个 SKU |
| 都不命中 | 「无匹配商品或 SKU」 |

**层级约束**：覆盖详情父弹窗用 `z-40`，`SkuTable` 用 `z-50`。点父弹窗里的「查看 SKU」只调 `setSelectedFailedProduct(product)`，**不要关闭** `overrideDetailOpen` —— 关了会丢失搜索上下文。
