### 最近更新（2026-10-14）

- **排版（U1）**：`PopupEditorModal` 的「要求版本」「下载地址」改为统一垂直结构（标签在输入框上方）+ `grid` 两列顶部对齐，窄窗口自动堆叠。**为什么**：原先一个标签并排、一个在输入框上方，两个控件不在同一水平位置。
- **查看统计（U2）**：新增 `popup_views` 表与两个接口；`recordId` 只作为**可选**字段加进公开策略条目（旧客户端与旧无 ID 缓存继续展示，不因缺字段被判非法）。计数三条硬条件见 [04-后端系统](04-后端系统.md#查看统计的计数口径)；扩展侧身份就绪与可见性复查见 [07-前端与状态](07-前端与状态.md#查看上报v1151)。
- **版本指引（v1.15.1）**：管理页顶部可折叠指引，**按用户实际做事的顺序**排（先备份旧包 → 发布更高要求 → 用旧包确认被挡 → 改两处版本并构建 → 下载解压加载、核对实际版本、确认解除）。示例必须给出**三个不同的值**（当前旧包 → 要求 → 新包，例如 1.15.2 → 1.15.3 → 1.15.3）：只有「要求」与「新包」相同才说明升到了要求版本，用同值示例会让用户以为改了版本却没真的升级。行号（`package.json` 第 3 行、`wxt.config.ts` 第 18 行）会随源码漂移，**以「搜索 version 字段」为准**；改动源码版本后要同步更新页面上的示例值。

### 最近更新（2026-10-14 第二轮补充）

- **登录后才弹窗（U4）**：`PopupPolicyHost` 不再由 `main.tsx` 包住整个 `App`，改由 `App.tsx` **只在「认证结束 + 已登录 + 店铺绑定已加载」的就绪分支**挂载。**为什么**：原先宿主在最外层，App 的「检查登录／未登录／同步店铺」三处提前 `return` 都在它里面，导致未登录就显示检查遮罩挡住登录表单、也弹通知。移动后未登录时宿主根本不在组件树里 —— 不检查、不展示、不遮挡、不上报，也不触碰缓存与已读存储（缓存不会因未登录被当成撤回清掉）。同一个 popup 内登录会切进该分支重新挂载宿主，因此不需要额外的「先匿名打开后登录」触发。挂在就绪分支最外层保证页面切换不重建公告状态、同一次查看不重复上报。
- **列表手动刷新（U5）**：弹窗列表卡片右上角「新建弹窗」左侧加「刷新」（`ReloadOutlined`），只复用现有 `load()` 重拉总数／状态／每条 `viewCount`；`loading` 防重复点击；失败时**保留已有列表与人数**并给出错误与重试（不清空、不显示假 0、不动编辑状态、不调用任何写接口）。
- **同会话换账号去重（F3，v1.15.2）**：`popup-views.ts` 的 `reported` 去重键原先只有「后端 + 记录 + 修订」，与账号无关。这个集合是模块级的、宿主卸载不重置，于是同一 popup 里 A 报过之后，B 看同一条同修订会被跳过 —— **B 的查看被漏记**（用户独立复现）。修复：键末尾带上**当次上报使用的 userId**；失败清理删除的是**当次捕获的那个键**（不能按当前账号重算，否则换账号后删错键会误伤真正的账号）。

**未验证项（如实标注）**：统计的「离线漏记」边界只按服务器收到上报的口径说明，未做弱网长跑；用户实际安装新包解除强制的完整流程由用户亲测。

## 已知问题

### 即时复制后偶发仍显示源活动

复制创建新活动成功后 `flashSaleId` 已切换为新 ID（`set({ flashSaleId: newId })`），但在频繁创建/删除活动的场景下偶发仍显示源活动。

**怀疑原因**：虾皮服务端缓存/CDN 不一致导致 `get_shop_flash_sale_list` API 短时间内返回不稳定结果。

**状态**：需等虾皮系统稳定后重新复现。若确认是服务端问题，需考虑更激进的重试+去重策略（如合并本地 `_copiedSaleData` 到列表中）。
