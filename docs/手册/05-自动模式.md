# 05 自动模式

> **用途**：自动模式的阶段机、alarm 编排、心跳监控、SW 崩溃恢复、防重入、停止清理、持久化日志、调试模式。
> **何时读**：改自动模式行为、排查「自动模式在跑但店铺没动静」「循环断了」「重复建活动」类问题。
> **来源**：原 `AGENTS.md` 的 Auto Mode Flow 与自动模式相关决策条目。

## 它做什么

用户选定模板活动与场次后，自动模式按轮次循环：**到时间建空活动 → 刷新库存 → 提交商品 → 进入下一轮**。每轮完成后把 `sourceFlashSaleId` 指向刚创建的活动，下一轮沿用这一轮的商品与库存，实现链式传递，让库存随售出自动递减。

自动模式跑在 **background Service Worker**，无人看守（半夜、用户关着弹窗甚至关着浏览器）。

## 状态机

```
idle → waiting_create → creating → waiting_enable → enabling → idle
```

对应 `AutoModePhase`：`'idle' | 'waiting_create' | 'creating' | 'waiting_enable' | 'enabling' | 'completed' | 'stopped'`

| 阶段 | 含义 |
| --- | --- |
| `idle` | 未启动 |
| `waiting_create` | 已排定创建时间，等 alarm |
| `creating` | 正在建空活动 |
| `waiting_enable` | 空活动已建好，等提交时间 |
| `enabling` | 正在提交商品 |
| `completed` | 全部轮次完成 |
| `stopped` | 用户或错误停止 |

## alarm 编排

三个 alarm：

| alarm | 触发时机 | 做什么 |
| --- | --- | --- |
| `auto_mode_create` | 目标时间 **前** `advanceMinutes` | 关掉进行中活动 → 取时段 → 在目标时间附近选最佳场次 → 建空活动 → 存数据 → 建 `auto_mode_enable` |
| `auto_mode_enable` | 目标时间 **后** `delayMinutes` | 刷新库存 → 构建参数 → `runEnableLoop()` → 轮次 +1 → `scheduleNextRound()` |
| `auto_mode_heartbeat` | 每 5 分钟重复 | `sendAutoModeUpdate()` → 同步状态到 popup/content |

**为什么两阶段**：活动未开始时 API 会拒绝提交，一次性提交会全部 SKU 失败并触发僵局检测而终止。

`clearAutoModeAlarms()` 在停止、完成、出错时清除全部三个 alarm。

**每个 alarm 出口都会重建心跳**，保证即使某条路径异常退出，状态仍能被同步。

## 启动与调度

```
START_AUTO_MODE
  → 验证选定场次（是否存在、开始时间是否变更、是否已开始；任一不满足则拒绝启动）
  → 清残留状态
  → 构建含 enableParams 的 status
  → logAutoMode
  → scheduleNextRound()

scheduleNextRound()
  → 调试模式：伪造 fakeTargetTime = now + advanceSec + 3
  → 正常模式：找下一个场次（第一轮优先用用户选定场次）
  → phase = 'waiting_create'
  → 建 auto_mode_create alarm（targetTime - advanceMinutes）
  → 建重复的 auto_mode_heartbeat
```

## 场次选择

`TimeSlotModal` 调虾皮 API（`get_time_slot_id/`）获取本月所有可用场次，按 `start_time` 升序排列，显示实时状态（未开始／进行中／已结束）。用户选择后在 `AutoModePanel` 展示。

第一轮若存在 `selectedSlotId` 且验证通过，直接使用用户选定场次而非调用 `pickNextTargetTime()`。验证失败时自动回退到自动选择并写 warning 日志。

## 心跳与状态同步

`auto_mode_heartbeat` 每 5 分钟调 `sendAutoModeUpdate()`，把状态同步到 popup 与 content script。

`handleAutoModeHeartbeat()` 额外检查 alarm 是否还在（`chrome.alarms.get()`），发现丢失就触发重新调度。

## SW 恢复

MV3 的 Service Worker 会被 Chrome 随时回收（闲置几十秒就休眠）。**alarm 是唯一能把它叫醒的机制。**

SW 启动时的恢复流程：

1. 先 `clearAutoModeAlarms()` 清理陈旧 alarm
2. 再 `scheduleNextRound()` 重建

`scheduleNextRound()` 的恢复分支处理三种情况：

| 恢复时 phase | 处理 |
| --- | --- |
| `waiting_create` 且 `nextTargetTime` 仍有效 | **直接复用**已有目标时间建 alarm，跳过 `pickNextTargetTime()` → `injectedFetch()` → `executeScriptSafe()` 链 |
| `waiting_enable` | SW 在建完活动、提交前死掉：直接重建 `auto_mode_enable` alarm，**不重新建活动** |
| 其他 | 正常走选场次流程 |

进入 `waiting_create` 阶段时会清掉陈旧的 `auto_mode_enable`；调试模式同样清。

**为什么必须复用 `nextTargetTime`**：SW 被 alarm 唤醒时用户可能已关掉卖家中心页面，此时任何「注入页面取数据」的调用都会被 Chrome 拒绝（`Cannot access contents of the page`）。若恢复路径依赖它，自动模式会在**每次电脑空闲后**静默断链，用户以为还在跑。修复提交 `4a7fb97`。

## 防重入与停止

- `_autoModeStarting`（模块级互斥锁）防止并发处理 `START_AUTO_MODE` —— 挡住双击与消息重复投递
- `_autoModeStopRequested` 标志让运行中的循环能中止；各阶段入口都检查它

**位置**：`entrypoints/background.ts` 模块级标志 `_autoModeStarting`／`_autoModeStopRequested`。

**为什么**：`sendMessage` 在 MV3 下可能被投递多次，加上用户连点，会**并起两套循环**，同一场次提交两遍／活动互相覆盖。用户看不到任何报错，只看到店铺数据乱了。

**停止清理**：`STOP_AUTO_MODE` 清除 alarms + `browser.storage.local.remove('_enableParams')` + 存 stopped 状态 + 移除 `_autoModeStatus`。

**为什么也要清 `_enableParams`**：残留参数会让重启后的场次状态异常（读到一个早已作废的提交计划）。

## 持久化日志

`logAutoMode()` 把结构化条目写入 `_autoModeLogs` storage 键（最多 500 条，前插）。每条含：

- `iso` —— 可读时间戳
- `type` —— `info` / `warning` / `success` / `error`
- `message`
- 可选 `data` 记录

写入经 `_logLock` promise 链**串行化**，防止写竞争。

`sendAutoModeLog()` 把日志广播到 popup 与 content script 供实时显示。`EXPORT_AUTO_MODE_LOGS` 消息 handler 把所有日志格式化为文本并触发浏览器下载；`AutoModePanel` 有「导出日志」按钮。

**日志点覆盖**：alarm 触发、SW 启动、心跳、调度/恢复、创建/提交阶段、停止事件。

**为什么必须落盘**：自动模式跑在**无人看守**的时段，出问题时 Service Worker 的控制台**看不到**（尤其指纹浏览器）；不落盘就没有任何证据，只能靠猜。`_logLock` 串行化是为了避免并发写入互相截断，导致日志本身损坏、反而误导排查。

## 调试模式

`AutoModePanel` 有「⏩ 加速调试」checkbox。激活后 `scheduleNextRound` 跳过真实场次时间，伪造：

```
fakeTargetTime = now + advanceSec + 3
```

使定时调度在数秒内触发而非等待真实时间段。底部调试状态条显示剩余秒数。

> ⚠️ 这个调试开关**仍在生产包里**（见 [`12-历史与已知问题.md`](./12-历史与已知问题.md#已知问题)）。

## 跨轮次库存刷新

`handleAutoModeEnable()` 每轮传递商品参数前通过 GraphQL 重新拉取最新 `normalStock`／`totalNormalStock`／`originPrice`，同步写回 `status.enableParams.products` 和 `_copiedSaleData`。

**为什么**：轮次开始时的一次性快照会过时；不刷新就会用旧库存提交，出现「实际有货却报库存不足」。

## 商品过滤

自动模式启动（`filterActiveProducts()`）与每轮提交（`handleAutoModeEnable()`）各有**一处独立过滤**，检查商品是否仍上架。

**两处必须同步修改。** 两者的实际行为：

| 检查点 | 触发条件 | 保留范围 |
| --- | --- | --- |
| `filterActiveProducts()`（启动时） | GraphQL 返回的活跃商品数 < 原商品数 | 有活跃商品 → 只保留活跃的；**活跃数为 0 → 保留全部原商品**；GraphQL 抛异常 → 保留全部原商品 |
| `handleAutoModeEnable()`（每轮提交前） | `freshItems` 数量减少，或存在 `Number(status) !== 0` | 过滤后有剩余 → 删除已下架项并同步裁剪 `skuOverrides`；**过滤后为 0 → 保留原商品**；过滤逻辑抛异常 → 保留原商品继续 |

两处都：

1. 用 `Number(p.status) === 0` 判断（虾皮 API 可能返回字符串 `"0"`）
2. 记录 status 原始值样本（含类型）便于追踪误判
3. 调 `logAutoMode()` 记录三个路径（全部过滤／部分过滤／API 异常）

`handleAutoModeEnable()` 另有**最终防线**：若 `enableParams.products` 仍为空，记完整诊断信息并抛错中止，不让空参数进入提交。

**这条兜底的作用范围有限**：它只防止「活跃检查环节误判」把商品列表清空，**不使任何其他检查失效** —— 凭据、身份与绑定校验（`validateShopAccess`）、商品状态校验、提交时的平台校验全部照常执行。

**为什么这么设计**：这是真实事故（2026-05-22，`145668f`、`ab1b72a`、`670156a`）——商品被全部判定为已下架，参数变空数组，整个自动模式当场崩溃且无痕迹。改成「保留原列表 + 记日志」是为了让无人看守时**留下证据、不要在无提示的情况下整个断掉**，而不是允许提交不合规商品。

**注意区分两类原因**（不要混为一谈）：
- **字符串 `"0"` 兼容** —— 判定逻辑写错，已用 `Number()` 修好，依据明确。
- **`freshItems` 为空 / API 返回不完整** —— 数据没拿到，属另一种情况。

**具体是哪一种引发了 2026-05-22 那次事故：历史未证实**，现有依据不足以判定，本手册不作断言。

> 与红线一致：这条兜底**只**防止商品列表被清空，**不使**凭据、身份绑定、商品状态或提交校验失效。

详见 [`01-红线.md`](./01-红线.md#商品过滤)。

## 未打折 SKU 复核

`AutoModePanel` 能检测未打折的 SKU，让用户在启动前决定跳过。`background.ts` 的 `runEnableLoop` 通过 `skipSet` 过滤掉被跳过的 SKU（`skipSkuKeys` 参数）。

**原因**：未打折的 SKU 提交进限时特卖会被平台拒绝或产生异常价格，事先剔除比事后处理错误便宜。

## 与其他写任务的互斥

自动模式（以及开卖、复制、一键修复）与「商品备货与物流」是**双向互斥**的：
两边都必须在真正发第一条店铺写请求前检查对方是否在写。

- 自动模式／开卖／复制／修复 → 走 `findActiveRepairConflict()`（内部先查 shipping，再查修复）。
- 备货与物流 → 走 `findOtherWritesForShipping()`（查 `_autoModeStatus.isRunning`、`_enableProgress.running`、
  `_copyExecuting`、`_oneDaySkuRepairTask`、`_scheduledEnable`、`_wizardFlowParams`）。

**只拒绝新的冲突动作，不强停已经在跑的任务，也不建队列。** 缺任一侧都会出现"两边同时改同一商品"。
