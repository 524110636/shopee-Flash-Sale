# 01 红线

> **用途**：做错会出事、必须遵守的硬约束。改动前必读，违反前先说明影响。
> **来源**：原 `AGENTS.md`／`CLAUDE.md` 中的硬约束段，合并去重，逐条补上原因。
> 这不是全部技术事实的清单——只有「做错会出事」的才进本文件。其他内容见各主题手册。

## 后台循环与通信

**要求**：开卖循环必须跑在 background Service Worker，不能放 popup。关键状态经 `storage.local` 传递，不依赖 `sendMessage` 的返回值。

**原因**：开卖一批可能几百个 SKU、要重试十几轮，跑几分钟到几十分钟；放在 popup 里，用户一关弹窗循环就死，出现「部分 SKU 上了特卖、部分没上」的店铺数据不一致。MV3 下 `sendMessage` 的响应经常拿不到（返回 `undefined`），用它传关键结果会出现「复制成功了但界面卡在等待」，用户重复点击就会建出多个活动。

**适用**：`runEnableLoop`、`EXECUTE_COPY`、`SCHEDULE_COPY`、自动模式各阶段。

**相关**：[`06-商品与活动.md`](./06-商品与活动.md#开卖循环)、[`02-架构总览.md`](./02-架构总览.md#消息协议)

## Cookie 来源（SPC_CDS）

**要求**：background 中不依赖 popup 传参的 handler（alarm、定时任务）**必须**用 `getSpcCdsFromCookies()` 从浏览器 Cookie 读 SPC_CDS；**禁止**从 `browser.storage.local` 读。

**原因**：popup 从不把 SPC_CDS 写进 `storage.local`（Zustand 只在内存里保存），所以从那里读**永远是空**。早先的定时任务因此半夜静默失败——活动建了但一件商品都没提交，用户早上才发现活动是空的。定时／alarm 路径没有 popup 可以传参，只能从 Cookie 读。

**位置**：`entrypoints/background.ts`，`getSpcCdsFromCookies()`。

**相关**：[`06-商品与活动.md`](./06-商品与活动.md#开卖循环)

## 校验不得跳过

**要求**：`spcCds` 缺失时必须 abort 并返回错误，**不得** `console.warn` 后继续执行。

**原因**：旧代码在 `SCHEDULE_COPY`／`scheduled_copy_enable`／`scheduled_enable` 中 spcCds 缺失时仅打警告就跳过校验，等于把「无凭据请求必然失败」当成正常路径放过去，用户在无人看守时看不到任何报错。

**适用**：所有 `validateShopAccess()` 调用点。

**相关**：[`04-后端系统.md`](./04-后端系统.md#防破解校验)

## 可变权限必须服务端确认

**要求**：`isAdmin` 必须从数据库 `users.role` 查，**不得**用 JWT claim 作为权限判定依据。启动检查必须用后端返回值作 `autoModeEnabled`／`trialUsed`／`trialEnabled` 的来源。

**原因**（准确表述，不要夸大）：

- **JWT 本身是验签的** —— `backend/src/utils/jwt.ts` 的 `verifyToken()` 调 `jwtVerify(token, secret)`，签名不对或已过期会被拒。**正常验签不会接受随意改写的 token。**
- 真正的问题是**信任层级**：JWT 是前后端都要读的，其中携带的权限字段（`autoModeEnabled`／`trialUsed`／`trialEnabled`）是**签发那一刻的快照**。管理员事后改了数据库，旧 token 里的值仍然是旧的。
- **客户端那一份始终可被本机修改**：storage 里存的 payload 由浏览器持有，用户改本地存储就能改「界面上显示的权限」。因此**界面按什么显示可以信 storage，实际拦不拦必须问服务端**。
- 所以：可变的权限（是否管理员、能否用自动模式、试用用没用完）**一律以数据库当前值为准**，JWT claim 只当辅助信息。

**位置**：`backend/src/routes/auth.ts` 的 `/check-admin`（从 DB 查 `users.role`）；`backend/src/utils/jwt.ts`；`entrypoints/popup/store.ts` 的 `checkAuthOnStartup()`。

**相关**：[`04-后端系统.md`](./04-后端系统.md#安全加固)

## 试用校验与消耗分离

**要求**：`/validate` 只做**只读**检查，不得标记试用。实际消耗由 `POST /api/stores/consume-trial` 在操作**成功后**独立调用。

**原因**：早期 `/validate` 在检查时顺手标记 `trialUsed=1`，导致「用户点了但因为活动没开始而失败」也照样扣掉唯一的试用机会；用户什么都没做成，试用已经用完了。

**适用**：`background.ts` `consumeTrial()` 的 4 个调用点，均在 `runEnableLoop` 成功后。

**相关**：[`04-后端系统.md`](./04-后端系统.md#试用限制)

## alarm 恢复与已有时间复用

**要求**：SW 启动时必须先清理陈旧 alarm 再重建；`scheduleNextRound()` 恢复路径中若 `nextTargetTime` 仍有效，直接复用，**不得**再走 `injectedFetch()` → `executeScriptSafe()` 链。

**原因**：MV3 的 Service Worker 会被 Chrome 随时回收（闲置几十秒就休眠），alarm 是唯一能把它叫醒的机制；启动时不清理并重建 alarm，被打断的那一轮会**永远卡住**（活动建好了、商品永远不提交），用户看到「自动模式在跑但店铺没动静」。而 SW 被 alarm 唤醒时用户可能已关掉卖家中心页面，此时任何「注入页面取数据」的调用都会被 Chrome 拒绝（`Cannot access contents of the page`）——若恢复路径依赖它，自动模式会在**每次电脑空闲后**静默断链。

**位置**：`entrypoints/background.ts`，`clearAutoModeAlarms()`、`scheduleNextRound()`。

**相关**：[`05-自动模式.md`](./05-自动模式.md#sw-恢复)

## 互斥与停止信号

**要求**：`_autoModeStarting` 互斥锁防止并发处理 `START_AUTO_MODE`；`_autoModeStopRequested` 必须能让运行中的循环中止。

**原因**：`sendMessage` 在 MV3 下可能被投递多次，加上用户连点，会**并起两套循环**，同一场次被提交两遍／活动互相覆盖。用户看不到任何报错，只看到店铺数据乱了。

**位置**：`entrypoints/background.ts` 中模块级的两个标志 `_autoModeStarting`／`_autoModeStopRequested`。

**相关**：[`05-自动模式.md`](./05-自动模式.md#防重入与停止)

## 商品过滤

**要求**：`filterActiveProducts()` 与 `handleAutoModeEnable()` 内**两处独立过滤**必须同步修改；`status` 比较**必须** `Number(p.status) === 0`，不得直接 `===`。

**原因**：这是真实事故。`"0" === 0` 为 false，虾皮 GraphQL API 返回字符串 `"0"` 时全部商品被误判为已下架，参数变空数组，整个自动模式当场崩溃（2026-05-22，提交 `145668f`、`ab1b72a`、`670156a`）。

**两处过滤的实际行为（必须按此理解，不得扩张）**：

| 检查点 | 触发条件 | 保留范围 | 诊断 |
| --- | --- | --- | --- |
| `filterActiveProducts()`（启动时） | GraphQL 返回的活跃商品数 < 原商品数 | 有活跃商品 → 只保留活跃的；**活跃数为 0 → 保留全部原商品**；GraphQL 调用抛异常 → 保留全部原商品 | 全保留时记 warning 并打印 status 样本（含类型） |
| `handleAutoModeEnable()`（每轮提交前） | `freshItems` 数量减少，或存在 `Number(status) !== 0` | 过滤后有剩余 → 删除已下架项并同步裁剪 `skuOverrides`；**过滤后为 0 → 保留原商品**；过滤逻辑抛异常 → 保留原商品继续 | 过滤前记 status 样本；异常记 error + stack；最后有「最终防线」——若 `enableParams.products` 仍为空则记完整诊断并抛错中止 |

**这条兜底只覆盖「活跃检查这一个环节的误判」**：它只影响商品列表是否被清空，**不使任何其他检查失效**。凭据（`spcCds`）、身份与绑定校验（`validateShopAccess`）、商品状态校验、提交时的平台校验，全部照常执行，不因保留原列表而被绕过。

**`status` 字符串兼容与其他异常是两回事**，不能混为一谈：

- **字符串 `"0"` 兼容**：已用 `Number(p.status) === 0` 解决，有明确代码与事故依据。
- **`freshItems` 为空 / API 返回不完整**：属于另一种情况（数据没拿到，而不是判定逻辑写错）。当前实现的处理是「保留原列表 + 记 warning」。
- **具体是哪一种引发了 2026-05-22 那次**：**属历史未证实** —— 现有依据不足以判定是字符串 `"0"` 兼容问题，还是 `freshItems` 为空/API 返回不完整。文档旧述写成「一次 API 抖动」，同样缺少依据。本手册不对该次事故的确切触发因素作断言，只说已核实的现象（全部被误判为已下架）。

> **这条兜底绝不表示「可以提交不合规商品」**：它只影响商品列表是否被清空一个环节；凭据、身份绑定、商品状态、提交时的平台校验全部照常执行。

**位置**：`entrypoints/background.ts` 的 `filterActiveProducts` 与 `handleAutoModeEnable`。

**相关**：[`06-商品与活动.md`](./06-商品与活动.md#开卖循环)、[`05-自动模式.md`](./05-自动模式.md#商品过滤)

## 向导双层防重入

**要求**：向导「立即加入／定时／开始／调试」按钮须 `disabled={isEnabling || oneDaySkuFlow.running || !!oneDaySkuFlow.message}`；store 层 `addToExistingFlashSale`、`scheduleEnableForFlashSale`、`createNewFlashSaleAndAdd` 入口须防重入守卫。

**原因**：这些操作会创建真实的店铺活动；重复触发会建出重复活动或同一批商品被提交两次，用户难以自行清理。

**位置**：`entrypoints/popup/store.ts`；`entrypoints/popup/App.tsx` `selecting_flash_sale` 阶段。

**相关**：[`07-前端与状态.md`](./07-前端与状态.md#向导流程)

## 完成通知初始化

**要求**：`showComplete()` 必须先调用 `createPanel()` ＋ `buildProgressSection()` 再检查 `headerEl`。

**原因**：`ENABLE_COMPLETE` 可能在 `ENABLE_PROGRESS` 之前到达（零商品或立即出错）；先检查 `headerEl` 会静默返回，用户看不到任何完成或失败提示，以为插件没反应。

**位置**：`entrypoints/content.ts`。

**相关**：[`07-前端与状态.md`](./07-前端与状态.md#悬浮面板)

## SKU 编辑必须保留其他字段

**要求**：`SkuTable` 四个输入列编辑时，每个 `onChange`／`onBlur` 必须保留所有其他 override 字段。折扣%列清空 `promoPrice`（互斥设计）但保留 `stock`／`purchaseLimit`；库存与限购列保留 `discountRate`／`promoPrice`；限时价列保留 `stock`／`purchaseLimit`。

**原因**：override 是整条覆盖写入的，漏带字段等于把用户之前手填的价格／库存**静默抹掉**；用户不会察觉，直到开卖时按错误价格上架。`v1.3.0` 曾因活动库存 `onChange` 缺少 `promoPrice` 保留，导致编辑库存后已设置的限时价丢失。

**位置**：`components/product/SkuTable.tsx`；`entrypoints/popup/store.ts` `setSkuOverride`（每次编辑后须 `saveCache()`）。

**相关**：[`07-前端与状态.md`](./07-前端与状态.md#sku-编辑)

## SKU 数量上限

**要求**：新建 SKU 前必须检查 `nextModelList.length + tierCombinations.length > 100`，超限抛清晰错误。

**原因**：虾皮限制每个商品最多 100 个 model；超限时 API 会整体拒绝该商品的更新，用户看到的是「发布失败」却不知道原因。

**位置**：`entrypoints/popup/one-day-sku.ts` `buildOneDaySkuProductInfo()`。

**相关**：[`06-商品与活动.md`](./06-商品与活动.md#一键修复)

## 折扣恢复须检查失败列表

**要求**：`update_seller_discount_items` 响应中 `failed_item_list`／`error_list` 必须检查，即使顶层 `error: 0`。

**原因**：虾皮部分失败时仍返回顶层成功，只看 `error` 会漏掉「折扣没恢复成」，用户的商品在修复后失去原有折扣，直接影响售价。

**位置**：`entrypoints/popup/store.ts` 折扣恢复段。

**相关**：[`06-商品与活动.md`](./06-商品与活动.md#折扣移除与恢复)

## 开发后端不得回落生产

**要求**：`.env.development` 的 `VITE_BACKEND_FALLBACK_URL` 必须**留空**。

**原因**：后端地址在**构建时**烤进产物。兜底地址若不改，本地后端一停就**静默回落到生产库**，调试动作照样写进生产数据——而且不报错，用户完全不知道自己的生产数据被动了。

**位置**：`.env.development`、`.env.production`、`entrypoints/background.ts`、`entrypoints/popup/backend-api.ts`。

**相关**：[`10-环境与命令.md`](./10-环境与命令.md#开发期连本地后端)

## 开发版只隔离后端，不隔离店铺写操作

**要求**：任何人（含用户）都必须知道：切换 dev／prod 版本**只隔离账号、试用与统计**，**挡不住**虾皮店铺写操作。

**原因**：店铺操作由扩展直接打 `seller.shopee.tw`，用的是浏览器里的登录 Cookie，与扩展连哪个后端无关。已实测：`store.ts` 的 `update_product_info`／折扣接口、`background.ts` 的 `set_shop_flash_sale_items` 全部直连虾皮。要真正隔离，得另开一个 Chrome 用户配置登录测试小号。

**相关**：[`10-环境与命令.md`](./10-环境与命令.md#日常使用与开发调试)
