# 09 编码约定

> **用途**：写代码前对齐项目风格 —— 命名、目录、类型、日志、组件、storage 键、消息约定。
> **何时读**：新增文件、新增动作、新增状态字段、新增消息类型前。
> **来源**：原 `AGENTS.md` 的 Conventions（9 条）＋`CLAUDE.md` 的 Important Patterns 中属约定的部分。

## 命名与目录

- **用 `@/` 路径别名**，不要深层相对路径。别名映射到项目根，配置在 `tsconfig.json` 的 `paths` 与 `wxt.config.ts` 的 Vite alias。
  **为什么**：深层的 `../../..` 相对路径在重构挪文件时会**静默指向错误模块**，而 `@/` 不会。

- **组件命名**：PascalCase 文件名；业务文件放 `components/product/`，通用 UI 放 `components/ui/`。
  **为什么**：`ui/` 是 shadcn 生成区（会被生成器覆盖），业务代码混进去会在下次生成时**被静默覆盖丢失**。

- **shadcn/ui 模式**：组件用 `cva` + `cn()` + `React.forwardRef` + `VariantProps`。
  **为什么**：这四个是 shadcn 生成器的契约；缺任一项，新组件就无法被 `npx shadcn add` 正常接入或覆盖。

- **Tailwind 类名直接写在 JSX**，不用独立 CSS module。
  **为什么**：弹窗是注入到虾皮页面的独立 DOM，外部样式表容易被页面样式冲突；内联类名作用域确定。

## 扩展 API

- **用 `browser.*`**，不要写死 `chrome.*`（WXT 会 shim 到 `chrome.*`）。
  **为什么**：WXT 构建时会做跨浏览器适配；写死 `chrome.*` 会绕过这层，将来加 Firefox 构建时静默失效。

## 状态与动作

- **Zustand store 模式**：`create<AppState>((set, get) => ({ ... }))`，所有动作定义内联。
  **为什么**：动作全内联才能让 `set`／`get` 直接访问同一份状态；拆到外部模块容易出现「读的是旧快照」，表现为界面不更新。

- **异步动作**：`try/catch`，每个动作带 `console.log`／`console.error` 前缀。
  **为什么**：弹窗控制台是排查第一现场；没有统一前缀时多条并发流程的日志会互相穿插，无从分辨。

## 类型

- **所有类型定义放 `entrypoints/popup/types.ts`**，通过 WXT 打包共享给 popup、background、content。
  **为什么**：popup／background／content 是三个独立运行环境，靠**同一份类型定义**才能保证消息契约不写错；分散定义会出现一边改了另一边不知道。
- **2026-10-14 限定解释（M02.1 起）**：这条要求的本意是**跨运行环境的消息契名单一来源**，
  不是"所有工具的所有类型都必须塞进特卖 `types.ts`"。因此：
  - 需要跨 popup／background 传递的契约（如 shipping 的 `SHIPPING_*` 消息）在各功能模块内定义**一份**，不要复制第二份；
  - 纯功能内部的类型与状态（如 `ShippingTask`、`ShippingPlan`、shipping 局部 store）**归本模块**，
    放进特卖 `types.ts` 会让新增工具都去读特卖状态，正是解耦审查 D1／D5 要避免的。
  - 反过来，也不要为了"保持集中"把特卖的类型搬出去 —— 旧特卖 store 维持原样。

## 超时约定

- **popup 的 `injectedFetch` 默认超时 30 秒。**
- ⚠️ **`sc-fe-session` 是 CSRF 请求头名，不是超时值。** 旧文档写「`sc-fe-session` 10 秒 / background 15 秒」容易被读成超时，**不要这样理解**；`background.ts` 只有一个超时常量，用于**心跳保活**，与 `injectedFetch` 无关。

## storage 键

- **下划线开头 = 内部状态**（`_enableProgress`、`_enableParams`、`_copiedSaleData`、`_autoModeStatus`、`_autoModeLogs`、`_copyTaskStatus`、`_copyCountdown`、`_pendingFlashSaleData`、`_scheduledCopy`、`_consumeTrialLog`、`_firstUseWarningDismissed`）
- **无前缀 = 可缓存数据**（`flashSaleCache`、`flashSaleTemplates`、`backendAuth`、`backendUrl`）
- **功能专属键带功能前缀**（shipping 的 `_shippingTask`／`_shippingSettings`／`_shippingPlans`／`_shippingPreview`／`_shippingStartError`，alarm 名 `shipping_plan_check`／`shipping_keepalive`）。

**为什么**：前缀区分「内部状态」与「可缓存数据」，`clearCache()` 只清后者；混用会导致清缓存把正在跑的进度一起抹掉。
**功能前缀为什么更严**：停止／清理某个功能时绝不能顺手删掉另一个功能的状态或 alarm ——
旧特卖的 `_scheduledCopy`／`auto_mode_*` 与新 shipping 的 `_shipping*`／`shipping_*` **必须互不可见**。

## 长任务状态归属（每个新工具都要照做）

新增后台长任务时，**权威状态只有一份**，写在 background 调用的 storage 键里；
popup 侧只做**只读同步**（`syncXxxTask()`），不自己改状态、不在本地保留可写的第二份。

三条硬要求：

1. **popup 发起的动作返回时以 storage 为准，不看 `sendMessage` 返回值。**
   seller 页的 content script 也在同一个扩展的 `onMessage` 监听里，它会同步 `return false` 抢先应答
   （shipping 预检就因此拿不到结果，见 [`07-前端与状态.md`](./07-前端与状态.md#为什么预检结果要落盘踩过的坑)）。
   必要动作（如预检、商品列表、身份核实、启动被拒原因）要**落盘一份带 `requestId`／有时间戳的记录**，
   界面轮询读它。
2. **runner 的内存副本不能覆盖权威记录里的"用户意图字段"。**
   用户点停止写的是权威记录的 `stopRequested`；runner 每次落盘前必须回读并保留它，
   否则会用旧副本把 `true` 覆盖回 `false` —— 用户点了停止却继续改商品（本任务实测复现）。
3. **写请求的三种结果必须分开表达**，不能都用"抛异常 / 不抛异常"两态：
   - 成功（含逐项 code，**缺 code 不是成功**）；
   - 明确被拒绝且可重试（只限限流：HTTP 429／409、业务码 `1000100006`）；
   - **结果未知**（超时、断连、响应不可解析）→ 请求可能已生效，**不得重发**，必须回读定案。

   > 原因：shipping 首版把未知结果一律塞回重试批次，同一批最多被重发 5 次（返工 R2 复现）。
   > 备货天数是幂等字段，重发不会"多改一次"，但会让结果无法归因、并放大平台限流。

4. **落盘／日志前统一脱敏。** 底层请求 URL 与异常文本可能带 `SPC_CDS` 等查询参数；
   一律过 `redactSensitiveText()`，保留动作、ID、状态码与可读原因，只替换敏感值本身。

## 消息约定

- **`browser.runtime.sendMessage()` 用于 fire-and-forget**
- **`browser.storage.onChanged` 用于关键状态通知**

**为什么**：见 [`08-关键设计决策.md`](./08-关键设计决策.md#决策-06--基于-storage-的通信) —— MV3 下 `sendMessage` 响应不可靠，用它传关键结果会丢。

## 后端相关约定

- **不在 `backend/` 的源码、运行数据或部署目录散落临时 DB、海量测试目录、整套项目副本**（`OWNER_WORKING_RULES.md` 第 8 条）
- **不把凭据提交进仓库**：`.env`、`backend/.env`、`harness/账号密码.md`、`SSH_CONNECT.md` 均已被 `.gitignore` 排除
- 后端错误信息脱敏：不把 raw `e.message` 直接返回给前端
- **不给管理接口返回店铺凭据**：`/api/admin/bindings` 等管理响应不含 `spc_cds`；缺少 `shopId` 时前端显示「店铺信息待补全」，不回退展示凭据前缀
- **管理功能只在独立网站**：扩展不实现管理列表／写操作，popup 只保留「打开管理网站」入口；新增管理功能应加在 `admin-web/`，不要重建内嵌面板

### Drizzle 默认值必须用 `sql` 模板

**要求**：时间戳等需要数据库求值的默认值，写成 `.default(sql\`(datetime('now'))\`)`，**不要**写 `.default('CURRENT_TIMESTAMP')`。

**原因**：后者会被 Drizzle 当成**字面量字符串**写进 SQL，该列永远存字符串 `"CURRENT_TIMESTAMP"`，时间显示全部失效。曾因此导致 `users`、`invite_codes`、`verification_codes`、`analytics_events`、`store_bindings` 五张表的时间列全部是字面量（其中 `analytics_events` 85/85、`store_bindings` 18/18）。

**注意**：改 schema 只影响**新写入**的记录；库里已有的字面量不会被自动修正，界面把这类值显示为「时间待补全」。

## 文档约定

- **不写死行号** —— 行号必然漂移，用符号名或章节锚点
- **现行约束必须带原因** —— 只写要求不写原因视为未完成
- 引用私有／未跟踪资料时标明「克隆不保证存在」

## 验收证据目录：只读，复跑要在副本里

`artifacts/agent/*-review*/` 与 `artifacts/agent/*-acceptance*/` 是**验收方的证据**，不是开发产物。

**为什么这是一条硬约束（实测踩过）**：验收脚本惯常把结果写回自己的证据目录。
第 42 节验收的 `check-store.cjs` 末尾就有一行
`fs.writeFileSync(.../standards/store-results.json, ...)`。
开发复跑它来确认缺陷已修时，会把验收方记录的**两条失败**覆盖成"全部通过" ——
等于篡改了验收结论，而且覆盖的是别人负责的文件。

**正确做法**：复跑验收脚本前，先把脚本**复制**到自己的 `.agent-tmp/<任务>/` 下，
并把里面写证据的路径改成自己的目录。不得在验收方目录原地运行会回写证据的脚本；
“运行后恢复原样”不构成只读例外。意外覆盖时立即披露，停止继续覆盖，由验收方按原始正文和新证据复核。

不得把改过的验收证据留在原地当作"验收通过"。
开发自己的结论只能写在**自己的**证据目录（如 `artifacts/agent/<本轮体验包名>/`）与任务书交付节里。

## 验证用例不要依赖"跑脚本的时刻"

**为什么**：用"今天 + 某个钟点"构造的用例，只在你恰好早于那个钟点时才成立。
实测踩过（2026-10-15）：用例用"台湾时区的今天 23:00"构造"开始时间在未来"，
在 23:47 跑时"23:00"已过去，先触发的闸门从「恢复必须晚于开始」变成
「开始时间不能是已经过去的时刻」，断言的理由变了、用例失败。
**那是夹具缺陷，不是产品回归** —— 但它看着像回归，会浪费一整轮排查。

**做法**：
- 需要"未来时刻"时用**明天／后天**（`Date.now() + n * 86400000`），不要用"今天 + 钟点"；
- 需要"已过去的时刻"时反过来，并明确注明"这里故意用过去时刻"，让它只在该用例生效；
- 新增带日期／时间的用例后自查一句："如果我现在是 23:59 或 00:01，它还对吗？"

## 测试断言不要写成"能同时放行错误结果"的形式

**为什么**：一条断言如果对"错误结果"和"另一种也应该算错的结果"都放行，它就没有证明力，
却会给出"已通过"的假象。实测踩过（2026-10-16）：弹窗失效后确认必须被拒绝，
但断言写的是 `sent === null || !sent.includes('111')` —— 当界面把 `[]`（空集合）
提交出去时它也通过，于是"拒绝"这个要求事实上没被验证，问题漏到下两轮才被发现。

**做法**：
- 断言**唯一正确结果**，不要用 `||` 把"另一个也算错的结果"一起放行；
- 需要证明"某个回调没被调用"时，就断言**调用次数为 0**，不要改断言它的参数内容；
- 需要证明"某个动作没发生"时，断言**可观测的状态没变**（例如弹窗仍打开、记录未写入），
  而不是断言"没有出现我担心的那个值"。

## 扩展 popup 的尺寸不能用 `vw`／`vh` 表达

**为什么**：Chrome 工具栏 action popup 是**独立窗口，视口尺寸由内容决定**。
在根容器上写 `max-width: 100vw` 等于让容器去读"自己撑出来的视口"，形成循环。
实测（2026-10-16，第 53.2 节）：源根容器 `w-[500px] max-w-[100vw] min-w-0` 在原生 popup 里
`window.innerWidth` 只有 **25px**，排除弹窗被压成 **2px** 宽；去掉那个 `100vw` 后为 500px 正常。
高度同理 —— `vh` 历史上曾把弹窗压成一条。

**做法**：
- 尺寸只给**确定值**（`w-[500px] min-w-[500px]`／`min-h-[500px] max-h-[600px] + overflow-y-auto`），
  不要用 `vw`／`vh` 派生上限；
- 不要用 `overflow:hidden` 把被裁掉的内容藏起来充数；
- **这类问题在普通 tab 里测不出来**：在预先把窗口设成 500px 的 tab 中打开 `popup.html`，
  `100vw` 永远不生效（视口比内容宽），一定通过。
  必须用 `chrome.action.openPopup` 打开**真实 popup** 再量几何。
  真实 popup 是独立窗口，不在 Playwright 的 `context.pages()` 里，
  `connectOverCDP` 也看不到 → 用原始 CDP 连它自己的 `webSocketDebuggerUrl`
  （参考 `.agent-tmp/shipping-once-ui-20261015/probe-native-popup4.mjs`）。
  另注：Chrome 自带组件扩展也有 service worker 且会先出现，
  必须按 `typeof chrome?.action?.openPopup === 'function'` 挑出本扩展那个。

## 测"空状态"必须从真实"没有数据"开始，并在目标界面上断言

**为什么**：同一处缺陷连续两轮从"新用户不该看到旧计划"漏过去（2026-10-16，第 56.3／59.2 节），
原因有两个，都是夹具与断言的问题：

1. **夹具预置了数据**：直接用 `writeStorage({ _shippingPlans: [] })` 造"空"，
   而真实缺键路径（`get` 拿不到键）走的是另一条兜底分支 —— 那条分支才是给空白占位的地方。
   `[]` 与"键不存在"在代码里表现不同，只测前者等于没测。
   **做法**：要测"没有数据"，就**真的把键删掉**（`chrome.storage.local.remove(...)`）再走真实加载。
2. **断言打在了天然的空白位置**：关闭重开后的 popup 落在**首页**，而旧计划卡只在**工作页**。
   在首页断言"没有旧计划卡"永远通过，与修没修无关 —— 是空转断言。
   **做法**：先走到**会出现该内容的那一屏**再断言；写完自问一句
   "如果这个缺陷还在，这条断言会失败吗？" 不会 → 它没有证明力。

**配套检查**：做反向核对时，把修复**逐层**关掉（本次有两层：加载兜底与渲染过滤），
只关一层可能仍然通过 —— 那就说明还有一层在兜，需要两层都关掉才能确认"断言真的盯着这个行为"。
