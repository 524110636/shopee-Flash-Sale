# 07 前端与状态

> **用途**：store 状态形状、类型定义、向导流程、模板系统、SKU 编辑、登录门、悬浮面板。

## store 状态形状

全部业务逻辑在 `entrypoints/popup/store.ts` 的**单一 Zustand store**。状态分组：

| 分组 | 字段 |
| --- | --- |
| **SPC_CDS** | `spcCds`、`spcCdsVer`、`isConnected`、`isExtracting` |
| **店铺信息**（来自登录 API） | `shopId`、`accountId`、`shopUsername` |
| **商品** | `productIds[]`、`products[]`、`inputText`、`isLoading`、`error` |
| **限时特卖** | `flashSaleList[]`、`flashSaleId`、`flashSaleInfo`、`isLoadingFlashSales` |
| **开卖参数** | `maxRetries`、`infiniteRetry`、`discountRate`、`flashSaleStock`、`purchaseLimit`、`isEnabling`、`enableProgress` |
| **复制** | `copySource`（flashSale + itemCount）、`copyMode`、`copyTaskStatus`、`isCopying`、`savedTemplates[]`、`selectedTemplate`、`hasScheduledCopy`、`scheduledTaskStatus` |
| **1 天备货 SKU** | `oneDaySkuSelectedIds[]`、`oneDaySkuFlow`（phase／running／currentIndex／total／message／error／items[]／canStartFlashSale） |
| **首次使用** | `firstUse`（open／loading／products[]／selectedIds／searchKeyword／searchResults[]／fetchedTotal／hasMore／cursor） |
| **SKU 覆盖** | `skuOverrides: Record<string, SkuOverride>`，键为 `${itemId}-${modelId}`（字段：`discountRate?`、`promoPrice?`、`stock?`、`purchaseLimit?`） |
| **自动模式** | `autoModeActive`、`autoModeStatus`、`autoModeLogs`、`firstSelectedActivity`、`showAutoModeUpgradeModal` |

> 文档旧述把自动模式字段写成 `autoModeView`／`autoModeConfig`，**实测不存在**；真实字段以上表为准（对应 `store.ts` 中 `AppState` 的自动模式字段段）。
>
> `autoModeActive` 是**展示状态**（当前看的是自动页签还是手动页），**不是运行状态**。
> 判断任务是否在跑必须看 `autoModeStatus.isRunning`；`loadAutoModeStatus` 只恢复任务数据，不再强制切页。

## 首页 / 工作页导航（2026-10-12，2026-10-14 扩展为三个页面）

- `App.tsx` 根级 `page`（`'home' | 'flash-sale' | 'shipping'`）决定显示功能首页还是某个工具的工作页，**不持久化**：每次开弹窗都先到首页。
- 首页卡片来自 `components/product/feature-catalog.ts` 的 `FEATURES`（当前 `flash-sale` 与 `shipping`），分类为 `shop-operations`。
  `enterFeature` 按 `featureId` 分发，未知 id **直接 return**（不误跳特卖）；`viewTask` 同样按摘要 `kind` 分发，
  `kind === 'shipping'` 进备货工作页，其余仍走特卖工作页。
- 首页任务摘要由 `components/product/task-summary.ts` 的 `buildTaskSummaries()` 从真实状态派生；
  `autoModeActive` 不参与判断，只有 `autoModeStatus.isRunning` 为真才显示「自动模式运行中」。
- **商品备货与物流的摘要由本功能自己的规则产出**（`features/shipping/task.ts` 的 `buildShippingSummary`），
  不由 `task-summary.ts` 计算：`TaskSummary` 的种类字段只是导航标识（新增 `'shipping'`），
  真正的文案与状态判定归 shipping 模块，避免"改备货规则要改特卖摘要"。
- 摘要的 `statusReady` 必须等**全部**任务读取完成后才置真：`App` 初始化 effect 里用
  `Promise.all([loadAutoModeStatus(), checkBackgroundStatus(), checkCopyTaskStatus(), checkScheduledCopy(), checkScheduledEnable()])`，
  这几个 action 返回 `boolean` 表示读取成功；**任一失败就保持加载态**（显示「正在读取任务状态…」），不能伪称空闲。
- **定时复制与定时加入是两条独立链路**，摘要各出一条，互不遮蔽：
  - 定时复制 → `_scheduledCopy`（`hasScheduledCopy` + `checkScheduledCopy()` / `GET_SCHEDULED_STATUS`），文案「定时复制待执行」；
  - 定时加入 → `_scheduledEnable`（`scheduleEnableForFlashSale`）或 `_wizardFlowParams`（`createNewFlashSaleAndAdd`），
    由 `checkScheduledEnable()` 只读读取到 `scheduledEnableStatus`，文案「定时加入待执行」。
  **不要用 `_enableParams` 判断定时任务**：手动提交也会写它，会误报。
- **两条链路的存储变化都必须在常驻层监听**（`setupBackgroundListener` 末尾的 `storage.onChanged`）：
  `_scheduledEnable` / `_wizardFlowParams` → `checkScheduledEnable()`；`_scheduledCopy` → `checkScheduledCopy()`；
  `_completedCopyInfo` → 直接同步 `_completedCopyInfo`（含被清除即用户已读）。
  **为什么不能只靠组件**：`ScheduledTaskCard` 只在手动工作页挂载，用户一直停在首页时它的 30 秒轮询**不会执行**，
  于是「定时复制结束、`_scheduledCopy` 被 background 清除」没人发现，首页会一直显示「定时复制待执行」
  （规划方返工 R5 复现）。这类同步只能放在 popup 常驻的监听里，且**两条链路要一起覆盖**，漏一条就漏报一种任务。
- 隐藏的工作页用 `hidden` + `inert` + `aria-hidden="true"`，**保持挂载**以保留局部草稿；导航本身不调用 `reset`／`clearCache`／停止／提交。
  手动业务区也用同一个 `WorkPageLayer` 包（切换页签 = 隐藏，不卸载），否则 `ProductList` 的搜索框、
  `TemplateManager` 的模板命名、`SkuTable` 的 SKU 编辑草稿会在切到自动页时被清空。
- **根级工作弹层**（`overrideDetailOpen` 的「手动修改的商品和 SKU」、`selectedFailedProduct` 的 `SkuTable`、
  `UndiscountedSkuModal`、`FirstUseModal`／`FirstUseWarningModal`）都必须包在 `WorkPageLayer` 里，
  否则返回首页后弹层继续覆盖首页、遮罩还会拦住鼠标点击。
- 公开仪表板/管理员网站外链、帮助、账号设置等公共入口在首页与工作页都可达；管理网站打开失败提示渲染在根层，不藏在隐藏页。

### 卡片图标字段（`FeatureDefinition.Icon`）

`Icon` 是 **`lucide-react` 组件**（`LucideIcon` 类型），渲染成 `<svg class="lucide lucide-…">`，**不是 emoji 字符串**。
`lucide-react`（v1.14.0）本来就是仓库依赖，直接复用，不需新增包。

**为什么不用 emoji**（用户 2026-10-13 明确要求，规范文档由规划方另改）：emoji 在不同系统/字体下字形和宽度不一致，会撑破卡片对齐，也无法统一颜色；SVG 图标可跟随主题色（`text-shopee-brand`）且可访问性可控。

### 根容器高度（不要用 vh）

根容器用 `w-[500px] min-h-[500px] max-h-[600px] overflow-y-auto`：

- **禁止再用 `max-h-[95vh]`／`h-screen` 这类视口单位**。Chrome 扩展弹窗的视口高度由内容决定，`vh` 会与自身形成循环 —— 实测会被压到只剩一条（用户复现：勾上 `max-h-[95vh]` 后弹窗只剩一点）。
- `min-h-[500px]` 保证内容少时高度稳定（否则空列表时弹窗会明显偏矮）。
- `max-h-[600px]` 是目标上限：内容超出时在**根容器内单一区域滚动**，顶栏 `sticky top-0` 保持可见，避免出现「双层滚动」。

**为什么集中在一个 store**：同一份状态被多个面板（主界面／自动模式／向导）读写，若各组件各存一份，会出现「这边改了那边不刷新」；集中一处才能保证关弹窗再开、进度不丢。

**动作全内联的原因**：动作全定义在 `create<AppState>((set, get) => ({...}))` 内，才能让 `set`／`get` 直接访问同一份状态；拆到外部模块容易出现「读的是旧快照」，表现为界面不更新。

## 商品备货与物流（features/shipping）

本功能**不使用**特卖 `store.ts`：它有独立的 `features/shipping/store.ts`（Zustand）与独立 storage 键。
理由见 [模块解耦审查](../../.claude/tasks/2026-10-14-07-模块解耦审查.md) D1：特卖 store 已承载 Cookie／登录／
特卖商品／SKU／复制／模板／自动模式等多类职责，继续往里加会让"改 shipping 参数"影响特卖的重置与持久化。

| storage 键 | 内容 | 由谁写 |
| --- | --- | --- |
| `_shippingSettings` | 用户设置（模式／天数／范围／排除／物流开关） | popup（**即时落盘**） |
| `_shippingPlans` | 旧的至多两项定时计划（含 `ownerShopId`／`ownerUserId` 归属锚与真实终态）。**第 31 节后保留不删不改写**，新流程不再创建新计划 | popup 保存、background 推进与回写终态 |
| `_shippingGroups` | **单次成对安排的权威记录**（第 31 节）：`active` 当前组 + `lastFinished` 上次完成组；含修订号、归属锚、两阶段时刻、常规天数、排除集合、物流选项、阶段、已认领阶段、已确认达到 1 天的商品、逐商品两阶段结果、待处理项 | popup 保存／撤销、background 推进与回写真实终态 |
| `_shippingTask` | 后台权威任务记录（含逐商品结果与物流恢复义务） | background |
| `_shippingPreview` | 最近一次只读预检结果（含 `requestId`、确认时的 `shopId`／`ownerUserId` 归属锚，以及 `settings`／`itemIds` 内容快照） | background |
| `_shippingPickList` | 排除选择器用的商品列表（带 `requestId`） | background |
| `_shippingIdentity` | 最近核实到的店铺／账号归属（保存计划前现读） | background |
| `_shippingDiagnostics` | 写前核验失败的最小脱敏诊断（最多 20 条，**不含凭据**） | background |
| `_shippingStartError` | 最近一次启动被拒原因 | background |

alarm：`shipping_plan_check`（2 分钟补检旧计划）、`shipping_group_check`（2 分钟补检单次组）、`shipping_keepalive`（运行期保活）。
**不得**用 `shipping_*` 命名之外的名字，也不得清理特卖的 `_scheduledCopy`／`auto_mode_*`。
两个补检 alarm **分开管理**：语义不同（旧计划是"某天某时刻跑一次"，单次组是"成对两阶段"），
用一个开关互相关闭会让另一类任务静默停摆。

### 单次成对安排的界面（第 31 节，第 53.4 节 U15 改为单入口）

- 功能页**没有模式页签**：主路径只有一条 —— 定时把参与商品切到 1 天、到点恢复常规备货
  （`ShippingSchedulePanel`，三步卡片）。原来的 `立即修改` 页签（任意 1–10 天单向修改）已移除。
  - **共用能力保留**：`handleShippingStart`、runner、API、历史 settings／task／plan 数据都没删，
    只是不再从本页新建单向修改任务。需要尽快开始时，把开始时间设为当前时间后几分钟。
  - **旧页签里的出口必须可见**：`TaskResultPanel`、中断结果核对（「已核对结果，结束本轮」）、
    「恢复物流」原先都在页签分支内。取消页签时若随之一并藏起，已发生的任务与待恢复渠道就无人处理，
    因此它们**按条件**渲染在同一个工作页上（没有异常时不铺开）。
- **新空白安排带默认时刻**（第 53.3 节 U14）：今天 `23:30` 切 1 天、所选开始日期的**次日** `01:30` 恢复。
  - 默认值必须是**按当时台湾日期现算**的纯函数（`defaultScheduleTimes(now)`），
    不能做成模块级常量 —— popup／service worker 可能跨天常驻，常量会拿昨天的日期算出一个已经过去的默认值。
  - 只在**确实空白的**草稿上补（`seedDefaultSchedule`，在 `syncGroup` **之后**调用）。
    顺序不能反：`syncGroup` 会把同店同账号"上次已完成配置"的时刻带进草稿（这是"再次安排"的契约），
    先补默认就会把复用结果当成空白安排覆盖掉。
  - 用户改**开始日期**时，恢复日期跟到次日（`restoreDateTouched` 为 false 时）。
    **只有改恢复日期才锁日期**：改恢复**时刻**不锁（第 56.2 节返工 ——
    早先连时刻一起锁，"只改时刻 04:15 → 再改开始日"会把恢复日留在旧的过去日期，
    验收在原生 popup 上复现为"开始 2100-01-02、恢复仍是 2100-01-01 04:15"）。
    联动时**保留**已有的恢复时刻 —— 「再次安排」会带出上次时刻，无条件写回默认会把用户设的 02:15 改成 01:30。
  - 开始时刻已过（`isStartTimePassed`）：明确提示"开始时间已过"并阻止保存，
    **不自动挪到明天、不补切现货**；首写窗口／截止保护在后台照旧。
- 一级页面只放「设定排除商品」按钮与已排除数量；列表在二级弹窗里，
  支持 ID 检索、任意多选、销量降序、前 5／前 10 快捷勾选、全选当前结果、清空、取消／确认。
- **快捷前 N 基于完整店铺列表**，不是当前检索结果也不是界面可见的前 50 项；
  未知销量**不冒充 0**，且不参与快捷排名（同销量按 ID 稳定排序）。
- 弹窗勾选先落在**本地草稿**上：取消／关闭／Escape 一律不提交，确认才写入本次配置；
  重新打开按已确认集合初始化，取消不会留下"以为取消了其实没有"的状态。
- 顶部状态区显示**真实阶段与下一动作**（来自后台 `_shippingGroups`，不是界面猜测）：
  待开始／切现货中／等待恢复／恢复中／已完成／已错过／需处理。
  页面**订阅** `_shippingGroups` 的变化，因此后台推进时无需切页或重开弹窗即可看到新阶段（第 34.7 节 R6）。
- 「停止」在**已开始后**走真正的停止机制（落 `stopRequested`、停后续切现货批次、保留恢复与物流义务）；
  只有"未开始"才走撤销（零写）。把两者混用会让按钮点了等于没点。
- **旧计划区是只读历史**（第 56.3 节）：`PlanHistoryItem` 只**展示**记录，不再有启用勾选／日期／天数输入／保存按钮。
  **没有真实记录时整块不渲染**。
  - **`plans.length > 0` 不足以判断"有历史"**（第 59.2 节）：`SHIPPING_DEFAULT_PLANS` 的两张空白占位
    （日期空、`ownerShopId: null`、从未运行、未被迁移）也满足它。早先加载兜底给的就是这两张占位，
    于是**从未设置过旧计划的人**看到两条"未绑定，请重新保存"的**不存在**记录，
    而那个"重新保存"入口本轮已下线 —— 提示指向一个不存在的地方。
    判据改用 `meaningfulPlans`／`isMeaningfulPlan`（`rules.ts`）：只要**任一真实痕迹**
    （`date`／`enabled`／`retired`／`missed`／`lastRunAt`／`lastResult`／`lastTaskId`／`lastRunId`／归属非 `null`）。
    **不能只按 `lastRunAt` 过滤** —— "已配置日期／归属但从未运行"的禁用记录恰恰没有它，会被误丢。
  - store 的初始 `plans` 与 `loadFromStorage` 的无键兜底都改为 **`[]`**（不再给默认槽位），
    `syncPlans` 在键不存在时也同步成 `[]`（否则会保留一份"已经不存在的历史"）。
    这样"页面挂载后、加载回来之前"那一瞬也不会闪出占位。
    后台仍照旧提供自己的默认槽位（调度语义不变）—— 本轮只改界面所依据的这份状态，
    有证据表明不该动调度就不动。
  - 为什么必须连表单一起删：验收的实际 DOM 动作是"填日期 → 保存"，得到
    `enabled: true, days: 1, retired: false` 并写了 `_shippingPlans`、发了一次 `SHIPPING_SYNC_ALARMS` ——
    那就是一条能绕过"切到 1 天后必须有恢复安排"的单向任务。只改标题或折叠仍可保存的表单都不算修好。
  - 闸门放在 `savePlan`：**`enabled` 的旧计划一律拒绝**（界面不是唯一入口，消息与残留调用也会走到这里）。
    记录本身不删，历史照常可追溯。后台同时拒绝循环模式的保存消息。
  - **遗留的启用中一次性计划必须有出口**：`readShippingPlans` 只降级旧的每日重复，
    **不碰**一次性计划，所以界面下线前存下的 `enabled: true` 记录仍会被 `shipping_plan_check` 调度执行。
    若只读展示里不给任何处置入口，用户就只能看着它到点发单向修改 —— 与第 56.4 节"出口被一起删掉"同类。
    因此对这类记录显示「启用中（旧版遗留）」并给出「停用这条旧计划」（复用既有 `removePlan`，
    只置 `enabled: false` 并让后台重建 alarm；不能新建／改期／启用，不新增能力）。
- **无 group 的运行任务保留停止出口**（第 56.4 节）：`status: 'running' && !task.groupId` 时显示「停止更新」，
  走原有 `stopTask`／`SHIPPING_STOP`。成对任务**不**走这个按钮（它们用组的停止／撤销规则，
  语义是"停后续切现货、保留恢复义务"），所以按 `groupId` 明确排除，避免误停配对流程。
- **跨店隔离**：切店／换账号时清空上一家店的候选列表与草稿，避免把别家店的排除集合带进新组；
  「再次安排」只在同店同账号时可用。
- 「再次安排」只带出上次的天数、时刻、排除与物流设置，**日期留空**并要求重新确认（不自动排下一周）；
  带出的恢复时刻在用户重新选开始日期时**保持不变**（见上方 U14 的联动说明）。

> ⚠️ **扩展 popup 的宽度不能写 `max-w-[100vw]`**（第 53.2 节 U13）。
> Chrome 工具栏 action popup 是**独立窗口，视口宽度由内容决定**，
> 根容器上的 `100vw` 等于去读"自己撑出来的视口"，形成循环：实测原生 popup 里
> `window.innerWidth` 只有 **25px**，排除弹窗被压成 2px（用户截图复现）。
> 只给确定的下限／上限（`w-[500px] min-w-[500px]`），高度同理不用 `vh`
> （历史上 `vh` 曾把弹窗压成一条）。**这类问题只在原生 popup 里出现**，
> 在预先设成 500px 的普通 tab 中打开 `popup.html` 是测不出来的 ——
> 必须用 `chrome.action.openPopup` 打开真实 popup 再量几何（见 `probe-native-popup4.mjs`）。

  详情折叠里说明错过开始／已开始恢复的政策与"关机期间无法执行"。

> ⚠️ **不要把原型的橙色抄进产品**：原型是讨论稿，用的是虾皮品牌橙；
> 产品必须与扩展现有主题一致（`tailwind.config.ts` 的 `shopee.*` 与 `style.css` 的 CSS 变量）。

### 为什么预检结果要落盘（踩过的坑）

popup 发 `SHIPPING_PREVIEW` 后，**seller 页里的 content script 也在同一个扩展的 `onMessage` 监听里**，
它会同步 `return false`，按 MV3 语义这成为消息响应，于是 popup 拿到 `false` 而不是预检结果
（[`08-关键设计决策.md`](./08-关键设计决策.md) 的"sendMessage 响应不可靠"）。
更麻烦的是这个抢先响应**早于** background 的异步预检结束，所以"重试读一次"也会拿到空。
因此：background 把结果带 `requestId` 落盘一次，界面 `awaitPreviewRecord(requestId)` **轮询**读它。
改动消息契约时不要退回"只看返回值"，否则用户点预检会看到"后台未返回预检结果"。

### 停止语义

用户点「停止更新」写的是**权威记录**的 `stopRequested`，而 runner 手里的 `current` 是内存副本。
runner 每次落盘前会先回读权威记录并保留 `stopRequested` —— **不能省这一步**：
省了就会用旧副本把 `true` 覆盖回 `false`，用户点了停止却继续改商品（本任务隔离验证实际复现并已修复）。

### 读不全就不写、写未知不重发（2026-10-14 返工）

这四条是本功能最容易"看起来成功其实出事"的地方，改动前务必对齐：

1. **任何读取不完整都不进入写阶段。** 商品列表分页不全、特卖排除调查（含活动列表翻页）任一环节失败、
   非热销缺销量／浏览字段、SKU 模式确认不到 → 预检与**开跑前检查**都直接停，零商品写请求。
   `gatherTargets()` 是预检与开跑前检查的**唯一实现**，禁止另写一份宽松版（两套规则必然漂移）。
2. **写结果未知不重发。** 超时、连接断开、响应无法解析都算"可能已经写成功"。
   `api.updateProductBatch` 用 `transportUnknown` 表达这一态，runner 只标 `unknown` 并交回读定案；
   **只有明确被限流**（HTTP 429／409／业务码 `1000100006`）才退避重试。
3. **缺逐项 `code` 不得当成功。** 解析时缺 code 记 `null`，runner 按 `unknown` 处理并回读核实。
   以前默认成 0，于是平台只回 `{id:101}` 就被记成"改成功了"。
4. **物流关闭结果未知要留恢复义务。** `closed === 'unknown'` 与 `closed === 'success'` 一样进待恢复清单；
   恢复时先回读确认它确实处于关闭状态再打开（避免把用户自己关的渠道打开）。
   判断只有一处：`runner.needsLogisticsAction()`；`task.ts`／`runner-deps.ts`／UI 都复用它。

### 预览归属锚：手动任务必须凭"预览请求号"启动（2026-10-14 返工 14.1）

预检通过后后台把**确认这份预览时的**店铺与账号写进 `_shippingPreview`
（`shopId`／`ownerUserId`）。用户点「确认并开始修改」时，popup 把 `previewRequestId` 交给后台，
后台**现读**当前身份与预览记录比对：

- 记录缺失／请求号不匹配 → 拒绝；
- 记录缺归属（当时核实不到）→ 拒绝；
- 换了店铺或换了账号 → 拒绝，界面提示「请重新预检」。

两条硬要求，改动时不要"简化"掉：

1. **不接受 `SHIPPING_START` 里 UI 自报的 owner。** 用户能在本机改客户端那份数据，
   自报值等于没有校验；归属只能来自后台自己核实到的身份与它自己写下的预览记录。
2. **不拿启动时的身份去重新认领旧预览。** 否则用户换到另一个账号后，旧预览照样能被新账号执行，
   商品就改到别人的店里了。

界面侧的 `previewStale` 用 **store 里刚核实到的**归属（`refreshOwner()`）与预览锚比较，
不能用外壳传入的 prop 快照 —— 否则用户在别的页面换了店铺再回来，界面仍显示"可以开始"，而后台会拒绝。
`loadFromStorage()` 必须把 `_shippingPreview` 一起读回内存；只放内存的话，重开弹窗后失效提示与
开始按钮的禁用都会消失。

### 预览记录同时锁定"确认了什么"（2026-10-14 返工 17.1）

请求号只证明"这份预览存在"，**不证明"要执行的就是它"**。所以预检记录里除了归属锚，
还要存 `settings`（天数／范围／排除／物流）与 `itemIds`（确认时的目标集合）；
启动时 `startShippingInner` 用它逐字段比对，**并用后台记录构造任务**，不信启动消息里的内容。

规则（纯函数 `rules.compareShippingConfirmedContent`）：

- 天数／范围／排除／物流开关必须**完全一致**；
- 商品集合只允许**减少**（开跑前被排除规则命中而掉出属既有规则），
  **多出一个预览外商品就拒绝** —— 否则确认过的范围会被悄悄扩大；
- 比对失败写一条 `stage: 'start-content-check'` 诊断（差异类型 + 脱敏摘要 + `writeSent: false`）并拒绝。

**比较与执行必须用同一份规范化设置**（返工 20.1）。`normalizePreviewSettings()` 是唯一的规范化入口：

- `toggleLogistics` **必须是真正的 boolean**，字符串 `"true"` / `"false"` 一律拒绝。
  这不是吹毛求疵：`if ("false")` 在 JS 里为真，一旦按真值语义处理，
  用户确认的"不操作物流"会被执行成"关闭并恢复渠道"。
- **执行参数与目标只从后台记录构造**（`executionSettings` / `executionItems`），
  消息里的对象只参与比对。以前只比对、执行仍用原消息对象，
  于是同一份请求号配上另一套内容照样能写出去。
- 目标取已核对 ID 的**子集**并去重；记录里没有而消息里有的商品一律忽略。
- 诊断记下**原值类型**与规范化值（`describeContentValues`），
  这样复验能一眼分清"类型不对被拒"还是"值不同被拒"。

界面在 `startTask` 里也会先做同一次比对，把"设置或目标已与预检时不同，请重新预检"直接显示出来，
不必等后台拒绝；`ShippingWorkPage` 的 `previewContentStale` 负责同一提示并禁用开始按钮。
`updateSettings` 必须把预览**连同请求号／归属锚／内容快照一起**作废 ——
只清 `preview` 会留下"界面没有预览、后台还认这份记录"的错位。

> 计划任务走**同一段**核对：每轮预检的快照由 `checkShippingPlans` 作为 `previewRecord`
> 内联传入（计划结果不落 `_shippingPreview`，那是手动预览用的键），
> 因此计划也享受同样的类型校验与内容比对，而不是只对界面来的请求生效。

### 每次写之前都要核验：归属 + 现行后端权限（2026-10-14 返工 14.2／14.3）

`runner.verifyWriteAnchor()` 是**唯一实现**，商品批改与物流关闭／恢复共用：
任务执行路径在 `logistics-close-precheck`／`close-channel`／`first-batch`／`between-batches`／`readback`
各边界调用，单独恢复物流路径在 `restore-channel` 调用。

判定规则（任一不满足即抛 `ShippingVerificationError`，**该异常不能被逐商品 catch 吞掉**）：

- 读身份**抛错** → 停写（不是"这件商品失败"继续下一件）；
- 读到但**核实不到店铺**（`null`）→ 停写；
- 店铺／账号与任务锚**不相等** → 停写（"非空"不等于"还是原账号"，必须相等）；
- **现行后端权限**（`validateAccess`，action `shipping_update`）被拒或**读取失败** → 停写。

为什么要每个边界都查：接受任务时校验过**不代表**整个执行期有效。用户中途被撤权后，
旧实现会照样把整批商品改完、把物流恢复打开。

> ⚠️ 布桩时的坑：`validateShopAccess()` 只在 **`!response.ok`** 时才读拒绝原因，
> 用 `200 + {allowed:false}` 布桩会被它当成通过（隔离脚本上一轮就是这样假通过的）。
> 拒绝必须按真实后端形状回 **403**。

失败时写一条 `_shippingDiagnostics`（阶段、任务／轮次标识、预期与实际店铺／账号、权限结果、
是否已发写、可读原因），写入前统一过 `redactSensitiveText()`。**永不保存 Cookie、token 或带凭据的地址。**

### 核验与发送必须用同一份平台上下文（2026-10-14 返工 17.2）

缺陷原型：核验时读一次 Cookie（会话 A），发请求时再读一次（会话 B）——
于是"按 A 核验通过、用 B 发写请求"，甚至把 B 的结果报成 A 已完成。

现在的做法：

- `verifyWriteAnchor()` 返回 **`ShippingVerifiedContext`**（一份凭据 + 用**这一份**凭据核实出的
  店铺与后端账号）。权限校验、商品批改、物流快照／关闭、回读、渠道恢复**全部**用返回的这一份，
  不再各自去读凭据。
- 生产注入 `buildRunnerDeps().verifiedContext`：读一次 Cookie → 用同一份读身份。
- 发送前再取一次上下文（`ensureContextStillVerified`），**先逐项核对归属，再看凭据是否刷新**（返工 20.2）：
  - 店铺读不到（`null`）→ 停；
  - 任务锚要求账号而当前账号读不到（`null`）→ 停（**不把 null 当"没变"**）；
  - 店铺或账号与锚**不相等** → 停；
  - 以上都过 → 归属未变；此时凭据刷不刷新都放行。
    **绝不能用"SPC_CDS 相同就 return 先前那份"短路** —— 卖家 Cookie 不变、后端账号被换，
    正好会被这一步跳过。
  - 也不要反过来做成"字符串一变就停"：SPC_CDS 轮换很常见，那会把正常刷新误判成换店。
- **凭据刷新时，还要用新凭据重新核验服务端权限**（返工 23）。
  归属没变**不代表**权限还在：旧上下文那次核验通过只证明"当时"允许。
  用 `current.credential` + `current.shopId` 再查一次 `validateAccess`，
  拒绝或读取失败都抛既有任务级错误停下（商品／渠道都不写，物流保留待处理，**不报**已恢复）。
  这一步不能省 —— 少了它，"刷新前允许、刷新后已被撤权"就会照样发写请求。
- 上下文变化导致停写时：商品写不发出；物流恢复保留待恢复快照且**不报"已恢复完成"**；
  诊断里记 `contextChange: 'blocked-write'` 与 `blockedBy`（`shop-changed`／`account-changed`／
  `identity-null`／`identity-read-failed`／`access-denied`／`access-read-failed`），
  并记 `credentialChanged` 这个 boolean（**不记** Cookie 原值）。放行的刷新记 `'same-owner-refresh'`。

### 计划归属锚（2026-10-14 返工）

计划保存时把**当时核实到的**店铺与账号写进计划（`ownerShopId`／`ownerUserId`）。
到点执行时：当前实际身份必须与计划锚一致，否则等待并说明原因。
**绝不能**用"触发那一刻登录的身份"去认领旧计划 —— 用户中途换店／换账号后，
计划会把商品改到别人店里。

计划的 `lastResult` 由 runner 结束回调按 `occurrenceId` 回写真实终态；
占用（`lastRunId`）与结果分开写，所以"启动成功"不会显示成"已完成"，旧轮次结果也不会覆盖新轮次。
界面通过 `storage.onChanged` 订阅 `_shippingPlans` 刷新（只看消息返回值会看不到后台回写的终态）。

### 中断后的出口

`interrupted` 会阻止开始新一批（结果未确认时不该继续写），但**不能永远卡住用户**。
界面提供「已核对结果，结束本轮」把记录推进到 `stopped`；物流义务未处理完时该按钮禁用。
它**不自动重放**任何未确认商品。

「一键修复商品并开启特卖」的向导阶段：

```
idle
→ preparing_sku / publishing_product / searching_discount / removing_discount / restoring_discount
   （这些阶段在 UI 上都显示为「优化中」）
→ editing_params          ← 修复完成，用户确认参数
→ selecting_flash_sale    ← 选择已有活动 或 创建新活动
→ starting_flash_sale     ← 提交
→ success / failed
```

### 一键修复的执行归属：现在跑在 background（2026-10-13 改造完成）

`runOneDaySkuAndEnable` 的修复循环（`preparing_sku` → `publishing_product` → … → `editing_params`）**已搬到
background**，popup 只负责启动、只读展示与编辑结果。

**分工**：

| 角色 | 做什么 |
| --- | --- |
| popup `store.ts` `runOneDaySkuAndEnable` | 本地校验 → 把商品快照与归属锚写 `_oneDaySkuRepairRequest` → 发 `START_ONE_DAY_REPAIR`（短消息，不等整批） |
| background `handleStartOneDayRepair` | 校验归属 + 只读 `validateShopAccess` → **先持久写"已接受"** → 异步跑 `runOneDaySkuRepairTask` |
| `entrypoints/popup/one-day-sku-runner.ts` | 真正的循环与完成结果读取（不 import Zustand/React/DOM，可被单测复用） |
| popup `syncOneDayRepairTask` | 只读 `_oneDaySkuRepairTask`；重开/返回首页/切模式都不重启任务 |

**为什么必须这样**：popup 会随用户关闭被回收。循环留在 popup 里，用户最小化再打开就只剩"任务不见了"，
**剩余商品也没在被处理**，但用户以为还在修。改造后关弹窗只影响界面，后台继续跑。

**关弹窗后仍能继续的流程**（都是 background）：一键修复、手动提交（`runEnableLoop`）、自动模式、定时复制/加入。

**为什么不能只恢复进度条**：只把 `_oneDaySkuFlow` 读回来显示、不恢复执行，会得到一条**不会动的假进度条**，
比不显示更糟。所以进度和结果都必须由后台准备。

**关键约束**：

- **先落盘再写商品**：`accepted` 记录必须写成功才开始发商品写请求，否则用户关弹窗后无法区分"还没开始"与"已经改过"。
- **写请求前先落检查点**：`writeSent=true` 的检查点表示该请求已发出；中断时据此说明哪些商品可能已被改动。
- **保存失败即停**：进度落盘失败时抛 `RepairCheckpointSaveError`，不再发新的写请求（不能无证据地改商品）。
- **迟到写入不得回退终态**：runner 每次 `save` 前读一次权威记录，已是终态就抛 `RepairStaleWriteError` 放弃（浏览器关闭时执行者还活着那一次写入曾把 `interrupted` 改回 `running`）。
- **失败也保留部分修改证据**：发布/恢复失败时 `workItem` 与 `items` 里保留已移除的折扣与活动名，供用户人工核对。
- **业务等待照旧**：移除折扣 → 等 2 秒 → 发布，恢复折扣前也等待，与原 popup 循环一致（去掉等待会让虾皮侧读到旧折扣）。
- **结果不依赖 popup**：完成时的商品/SKU 读取与折扣率计算都在后台做完并写入 `resultProducts`／`discountRate`。
- **结果幂等**：按 `taskId` + `_oneDaySkuRepairApplied` 只应用一次，重开弹窗不重设商品与折扣率，用户后填的价格/库存/限购不被覆盖。
- **中断不重放**：启动时／中断复检发现"本实例没有执行者"→ **立即**标 `interrupted`，保留检查点与"部分商品可能已修改"的说明，**不自动重放**发布/移除/恢复。心跳只作证据，判定不依赖它（`setTimeout` 会随 worker 一起消失）。
- **有界保活**：`REPAIR_KEEPALIVE_INTERVAL_MS`（20 秒）一次的短 storage 调用维持 worker，只刷**独立心跳键**；终态 `finally` 清理定时器与内存锁。不新增权限、不做常年保活。
- **写请求前核实归属**：`assertOwnership()` 在每个写请求前核对实际店铺／账号／凭据指纹；核实不到即停（fail-closed）。
- **启动互斥 + 参数绑定**：`_repairStarting` 同步占用，popup 传入的 `requestId` 必须与参数快照一致；被拒原因写 `_oneDaySkuRepairStartError`，不依赖消息返回值。
- **补上访问校验**：旧 popup 循环没有服务端 `validateShopAccess`；后台无人看守执行必须加（沿用 `wizard_flow`）。
  这可能让已过期/未绑定的账号**在修复前就**被拦下，属于有意为之。
- **界面归属三分**：`verifyRepairOwner` 区分 `match`／`mismatch`／`unknown`。写请求用 fail-closed 的 `isSameOwner`；界面则是"还没核实到"保持原状态、身份就绪后再同步一次，否则冷打开时用户自己的结果会被一直挡在门外。
- **界面就绪闸门**：`isRepairResultReady(task, fallbackProducts)` 判定**修复后**的数据 —— 本次新建 SKU 的商品必须真的读到专用 1 天 SKU，旧模型不能冒充结果；未就绪时"下一步"按钮禁用且 `goToFlashSaleSelection` 内部也拦（按钮不是唯一入口），并显示"商品数据待加载"。
- **补读成功即完成一次应用**：结果首次读取失败、后来补读成功时，`syncOneDayRepairTask` 必须在**开放编辑之前**调用一次 `applyRepairResult`（写 `_oneDaySkuRepairApplied` + 初始化商品/折扣率）。否则界面已可编辑却没有已应用标记，用户改完参数重开会被下一次同步再套用一次，把折扣重置成任务默认值。
- **编辑参数即时落盘**：`setDiscountRate`／`setFlashSaleStock`／`setPurchaseLimit`／`setMaxRetries`／`setInfiniteRetry` 改内存后立即 `saveCache()`。否则用户填完关掉弹窗就丢（曾出现折扣 37 变回 80）。
- **阶段不被复位**：`nextFlowPhaseAfterApply` 让已经进入选场次／提交的用户在再同步后仍停在原阶段，只有未推进时才回到 `editing_params`。
- **最小脱敏诊断**：连续返工后新增 `_oneDaySkuRepairDiagnostics`（最近 20 条），只记 taskId／requestId、阶段、任务锚 vs 实际锚、被拒原因、已确认／未知动作；`redactDiagnosticReason` 兜底打码。仅用于定位，不建历史任务系统。

### `editing_params`（修复完成）

展示修复成功的商品卡片（可点击编辑 SKU / 全局参数）。商品卡片列表下方、全局参数上方显示绿色引导：

> 修复完成，请点击上方商品列表修改限时特卖商品价格，库存，限购等信息(默认参数是你的折扣信息。)，然后点击下一步：选择限时特卖。

**为什么**：修复后折扣率已自动同步为实际值，但用户可能还想调价格/库存；不引导的话用户直接下一步，用的就是默认值。

### `selecting_flash_sale`（选择目标）

列出已有进行中/即将开始的活动，每个带「定时」与「加入」按钮；下方是时段选择（通过 `fetchTimeSlots` 获取）用于创建新活动。

顶部有两个时间输入框：
- `wizardAdvanceMin` —— 提前 N 分钟创建空活动
- `wizardDelayMin` —— 活动开始后 N 分钟提交商品

时段列表用 radio 选中模式 + 统一「开始」按钮。

### 三条提交路径

| 路径 | 函数 | 行为 |
| --- | --- | --- |
| 加入已有活动 | `addToExistingFlashSale` | 构建 enable items（含 `item_display_image` 从 `p.images?.[0]`、`stock` 上限 `Math.min`、零库存过滤、未打折 SKU 检测、活动结束检查）→ 存 `_enableParams` → 发 `START_ENABLE` → **走 Background `runEnableLoop`**（与手动模式一致的多轮重试与错误处理） |
| 新建活动（可定时） | `createNewFlashSaleAndAdd` | 两阶段：`advanceMin > 0` 时发 `SCHEDULE_WIZARD_FLOW` 给 background 定时创建（`wizard_create` alarm），再由 `scheduled_enable` alarm 定时提交；`advanceMin = 0` 时立即创建 |
| 定时加入已有活动 | `scheduleEnableForFlashSale` | 发 `SCHEDULE_ENABLE` 给 background → `scheduled_enable` alarm |

空活动的商品展示由 `_pendingFlashSaleData`（内存）与 `_copiedSaleData`（storage）预填。

### 调试按钮

`App.tsx` 的 `selecting_flash_sale` 阶段有「调试: 立即创建并提交（跳过等待）」按钮，传 `now` 作为 `slotStartTime` 并设 `advanceMin=delayMin=0`，强制立即创建 + 提交。该路径调用 `validateShopAccess(spcCds, 'wizard_flow')` 拦截试用到期用户。

> ⚠️ 这个调试按钮**仍在生产包里**（见 [`12-历史与已知问题.md`](./12-历史与已知问题.md#已知问题)）。

### 防重复点击

`selecting_flash_sale` 阶段的「立即加入」「定时」「开始」「调试」按钮：

```
disabled={isEnabling || oneDaySkuFlow.running || !!oneDaySkuFlow.message}
```

store 层 `addToExistingFlashSale`、`scheduleEnableForFlashSale`、`createNewFlashSaleAndAdd` 入口也有防重入守卫：

```

```

**为什么**：这些操作会创建真实的店铺活动，重复触发会建出重复活动。

## 首次使用流程

1. `FirstUseWarningModal` 先弹出（除非用户勾选「以后不再提示」，持久化在 `_firstUseWarningDismissed` storage 键），提醒用户在插件前**先把商品从其他促销活动移除**（多件优惠、免运、套装、加购），折扣活动除外
2. 确认后 `FirstUseModal` 打开
3. `FirstUseModal` 通过 `search_product_list` API（分页，`fetchShopProductsPage`）获取店铺全部商品，**每页 12 个、按销量从多到少排序**，支持关键词搜索
4. 用户勾选最多 **20** 个商品
5. 触发 `runFirstUseFlow`：把 `ShopProductListItem[]` 转成 `ShopeeProduct[]`（`modelList` 为空），设置 `oneDaySkuSelectedIds`，自动调用 `runOneDaySkuAndEnable`

`getHighestModelPrice()` 接受可选 `productInfoModels` 参数 —— 用于 `ShopeeProduct.modelList` 为空时（首次使用场景）从 `product_info.model_list` 取价格。

**为什么必须先移除其他促销**：叠加促销会让价格计算异常、发布被拒或产生非预期售价。

## 模板系统

- 保存/加载完整配置（折扣率、库存、限购、SKU 覆盖）
- 应用时的商品比对：黄色提示被移除的商品，蓝色提示新增的商品
- 模板存 `browser.storage.local` 的 `flashSaleTemplates` 键

### 导出

每个模板行有蓝色「导出」按钮，下载 JSON：

```json
{ "version": 1, "type": "flash_sale_template", "name": "...", "exportedAt": "...",
  "data": { "discountRate": 60, "flashSaleStock": 200, "purchaseLimit": 0,
            "skuOverrides": {}, "productInfo": [] } }
```

### 导入

空闲状态的「导入模板」按钮打开文件选择器，校验 JSON 格式（检查 `version`、`type`、`data` 字段），通过 `importTemplate` store action 保存。支持任意实例导出的 `.json`。

### 编辑

每个模板行的「编辑」按钮打开 `TemplateEditDialog`：

- 显示全局参数（折扣率%、活动库存、限购数量）与按 Item ID 分组的 SKU 覆盖
- 父行：▶/▼ 折叠开关、商品名、SKU 数、行内「Model ID + +SKU」快捷添加
- 展开的子行：折扣%、限时价、活动库存、限购数量可编辑 + 「移除」按钮
- 支持「全部展开/收起」（当前页）
- 每页 8 个 Item ID，带 ‹上一页/下一页›
- 底栏显示商品总数 + SKU 总数
- 保存调 `updateTemplate`

`updateTemplate(name, Partial<FlashSaleTemplate>)`：读 `flashSaleTemplates` → 找已有模板 → 合并字段（保留 `name`／`createdAt`，自动设 `updatedAt`）→ 写回。与 `importTemplate`（全量替换）不同，只改传入字段。

### 分组与分页实现

数据加载时把 `skuOverrides` 按 `itemId` 分组为 `ItemGroup[]`（`itemId`、`productName`、`models[]`），排序后分页（`PAGE_SIZE=8`）。展开状态用 `Set<string>` 追踪，`useMemo` 算当前页。新增 SKU 时自动加入展开集合并按 `modelId` 排序；删除最后一个 SKU 时自动移除整组。

### `enterCopyMode` 不再自动选模板

`selectedTemplate` 默认 `null`，用户需手动选择。

**为什么**：旧代码 `selectedTemplate: names[0]` 自动选第一个模板，其 `discountRate=60`／`flashSaleStock=200` 等默认值会进入 `executeCopy` → 存到 `_copiedSaleData`，导致加载复制活动时全局输入框显示模板默认值而非实际 flash sale 配置。

## SKU 编辑

### 四个可编辑列

| 列 | 写入字段 | 互斥规则 |
| --- | --- | --- |
| 折扣% | `discountRate` | 写入时**清空** `promoPrice` |
| 限时价 | `promoPrice` | 写入时**只存** `promoPrice`，不反算折扣率 |
| 活动库存 | `stock` | 保留 `discountRate`、`promoPrice` |
| 限购数量 | `purchaseLimit` | 保留 `discountRate`、`promoPrice` |

**每个 `onChange`／`onBlur` 必须保留所有其他字段。** 这是硬约束，详见 [`01-红线.md`](./01-红线.md#sku-编辑必须保留其他字段)。

### 批量编辑框

表格上方有浅蓝底批量编辑行：`折扣% | 活动库存 | 限时价 | 限购数量`。输入后 `onBlur` 或 `Enter` 应用到当前商品**所有** SKU。限时价批量编辑时同步清空折扣%字段（互斥设计）。手动模式与自动模式都适用。

### `onEdit` 回调

可选 prop，任何用户触发的 `onChange`／`onBlur` 修改都会调用。用于 `AutoModePanel` 的动态「已编辑」标记机制，不影响手动模式现有行为。

### `key` prop 现状

`<SkuTable>` 共 **6 处**渲染点，其中 **4 处**带 `key`：

| 位置 | 带 key |
| --- | --- |
| `App.tsx`（向导编辑 SkuTable） | ✅ |
| `App.tsx`（覆盖详情 SkuTable） | ✅ |
| `components/product/CopyConfirmPanel.tsx` | ✅ |
| `components/product/ProductList.tsx` | ✅ |
| `components/product/AutoModePanel.tsx` | ❌ |
| `components/product/ProductViewModal.tsx` | ❌ |

带 key 时切换商品 React 会销毁旧实例创建新实例，内部 `priceEditValues` 状态归零；缺 key 时可能残留旧商品编辑值覆盖新商品字段。后两处未加是当前实际状态（非笔误），改动那里时要留意状态残留。

### 覆盖持久化

`setSkuOverride` 每次编辑后自动调 `saveCache()`，把 `skuOverrides` 持久化到 `flashSaleCache`。

**为什么**：它早期只更新 Zustand 内存状态，关掉 popup 后编辑就丢了（下次打开时 `loadCache` 加载的是旧缓存）。

### 字段保留的来源提示

SKU 输入框 `placeholder` 显示全局默认值，用于区分「用全局默认」与「手动输入过」。

### 管理员入口

顶栏「管理」按钮只在 `backendApi.isAdmin()` 为真且不在自动模式时渲染，点击调用 `App.tsx` 的 `openAdminSite()`：打开 `<getBaseUrl()>/admin/` 新标签页。

- `window.open` 返回 null（被拦截）→ 提示里带上完整地址供手动复制
- **不做生产地址回落**：地址只来自用户在设置里配置的值／构建期默认值

（2026-10-12 起根层不再有翻转容器，但这条仍然成立：提示块必须留在根层，不能挪进首页或工作页的分支里。）

### `checkAuthOnStartup` 竞态修复

原 `setTimeout(() => refreshStoreBindings(), 500)` 改为 `await refreshStoreBindings()`。

**为什么**：消除 500ms 窗口期中 `isLoggedIn=true` 但 `storeBindings=[]` 的状态，防止用户快速点「绑定当前店铺」造成重复绑定。

### `storeBindingsLoaded` 门控

新增该标志，在店铺信息加载完成前显示 spinner，避免慢网络下先闪一下「未绑定」界面。

### 设置页安全

`AuthPanel` 设置视图中的后端地址输入框**仅在 `authUser.role === 'admin'` 时显示**。普通用户只看到「测试连接」按钮（调 `healthCheck()`）；成功显示绿色「后端连接正常」，失败显示红色错误详情。未登录状态下同样隐藏地址输入框。

## 弹窗策略宿主（v1.15.0 起，v1.15.2 调整挂载位置）

`entrypoints/popup/PopupPolicyHost.tsx` 包住**登录后已就绪的功能区**（由 `App.tsx` 在认证结束、已登录、店铺绑定已加载的分支里挂载），首页与工作页都在它里面。

### 为什么挂在这一层（v1.15.2 改动）

**v1.15.0 的做法是在 `main.tsx` 包住整个 `App`**，理由写的是「未登录也要被强制升级挡住」。**用户实测后明确改了这个前提**：匿名时登录表单上就压着通知，账号人数却是 0 —— 用户要求改成「登录后进入功能界面才出现」。

现在宿主只在就绪分支挂载，因此：

- **未登录／恢复身份中／登录失败／退出登录**：宿主根本不在组件树里 → 不检查、不展示、不遮挡登录表单、不上报，也**不触碰 `_popupPolicyCache` 与 `_popupNoticeAck`**（缓存不能因未登录被当成撤回清掉）。
- **同一个 popup 内登录**：`isLoggedIn` 变化会让 App 切进这个分支、重新挂载宿主，所以**不需要**额外的「挂载后再次检查」触发；先匿名打开再登录也会弹。
- **页面切换**（首页 ↔ 工作页）：宿主是就绪分支的最外层，切换发生在它内部，公告状态不重建、同一次查看不重复上报。

调用链：`main.tsx` → `<App />`；就绪分支 → `<PopupPolicyHost><功能区 /></PopupPolicyHost>`。

**保持不变的边界**：策略整轮 5 秒检查**从挂载那一刻（= 功能就绪）开始计时**，不含认证／绑定初始化时间；强制不可取消、按实际加载版本判定、后台任务与 alarms 不受影响。

### 阻挡与不阻挡的边界

| 项 | 行为 |
| --- | --- |
| 未登录／恢复中／绑定等待 | 宿主未挂载：不显示任何弹窗或检查遮罩，登录表单可正常输入与提交 |
| 检查期间 | 显示「正在检查通知…」遮罩，底层 `inert`（避免策略未定就点了业务按钮） |
| 强制升级命中 | 内容包一层 `inert` + `aria-hidden`；遮罩自己吃掉点击与键盘；**不响应 Escape、无关闭按钮**；「下载最新版本」只 `window.open`，**不写已升级标记、不调 `runtime.reload`** |
| 通知 | 「我知道了」才写确认记录；直接关掉 popup **不算已读**；关闭后恢复原界面与编辑草稿 |
| 优先级 | 强制升级命中时**只显示强制**，且**不把通知标为已读**（版本达标后未确认通知仍会出现） |
| 弹窗策略刷新／显示／点击下载／关 popup／撤回 | **都不发停止、取消、重置消息，不清 storage、不清 alarms** |

### 版本判定只看实际加载的包

`getActualVersion()` 读 `browser.runtime.getManifest().version`。比较用 `compareVersions()` **逐段按数字**（缺失段补零）。

**为什么不能按字符串比**：`'1.14.10' < '1.14.9'` 为 true，但数字上 10 > 9，按字符串比会把**已升级**的包判成旧版本。

下载点击、zip 文件名、`backend/package.json` 的后端版本、已读标记**都不作为升级完成依据**。

### effect 必须可重复执行（2026-10-13 返工）

`PopupPolicyHost` 的检查 effect **不能**用 `started` ref 拦住第二次 setup。

**为什么**：React 开发模式 StrictMode 会跑「setup → cleanup → setup」。旧写法第一次 setup 起了请求、cleanup 把结果标记为取消，第二次 setup 又被 ref 拦住 —— 两边夹击，界面**永远停在「正在检查通知」**（Codex 已独立复现，即使 HTTP 200 也转圈）。

正确做法：允许重复执行，只丢弃**已卸载**那次的结果（`let active = true` + cleanup 里 `active = false`）。**不要用删除 StrictMode 来掩盖**。

### 整条链只有一个 5 秒总上限（2026-10-13 二次返工）

`checkPolicy()` 用**一个** `withDeadline(..., POLICY_TIMEOUT_MS)` 包住「地址解析 → 取策略 → 判版本 → 读已读」。

**两个都要做到，缺一即不合格**：

1. **整轮 ≤5 秒，不是每段 5 秒。** 上一版给地址解析和后续检查各加了 5 秒，串起来就是 10 秒（B1）；更早的版本只在 `checkPolicy` 里加限，然后宿主**又** `await ensureBackendUrl()`，那一步在限外，storage 卡住就永远到不了终态。
2. **超时也必须保住已知强制策略。** 外层 deadline 抢先返回时，要在**剩余预算**内读同后端缓存并走**同一套判定**（`evaluate()`）；否则断网等于自动解除升级阻挡（B2）。

配套约束：
- `PolicyDecision.backendUrl` 把地址一并带出，宿主**不再自己解析**（否则又是限外等待）。
- `fallbackBackendUrl()` 提供**同步可得**的地址（不读 storage），storage 完全卡死时也有地址去读缓存。
- 读缓存、读已读等本地操作都有 `LOCAL_TIMEOUT_MS` 上限，且只用**剩余预算**。

### 失败原因必须可分类

`PolicyErrorKind` 区分 `address`／`timeout`／`network`／`response`／`storage`／`ack`，界面提示对应文案。

**为什么**：都笼统提示「连接问题」会让排查无从下手 —— 地址配错和网络超时是完全不同的两件事。

### 无效成功响应不能解锁（2026-10-13 返工）

`parsePayload()` 要求**两个字段都存在**（显式 `null` 才算「该模式无生效内容」），并逐条校验 `mode`／`revision`／`requiredVersion`／`downloadUrl`。

**为什么**：旧实现把 `undefined` 也当 `null`，于是 HTTP 200 的 `{}` 被当成「服务端明确撤回」，**把已知强制缓存删掉** —— 断网期间服务端返回半截 JSON 就等于解除阻挡。只有**同时** `notice: null` + `forcedUpdate: null` 才算有效撤回。

### 自有图片必须按后端地址解析（2026-10-13 返工）

`resolveAssetUrls(html, backendUrl)` 把正文里的 `/popup-assets/xxx` 补成完整 URL，在 `sanitizeForRender()` 之后执行。

**为什么**：扩展页面的 origin 是 `chrome-extension://<id>`，相对路径会被解析到扩展自己目录，表现为图片 `ERR_FILE_NOT_FOUND`、`naturalWidth === 0`。图片实际在后端，必须拼上**读取该策略的后端地址**。只改写自有资源路径，外部 http(s) 链接原样保留。

### 二次安全渲染

服务端已用白名单清洗，`popup-content.ts` 的 `sanitizeForRender()` 再用 `DOMParser` 收紧一次（纵深防御）。

**为什么不用正则**：正则匹配 HTML 必然漏，必须让浏览器解析成 DOM 再按节点白名单删；事件属性（`on*`）、非白名单标签、`javascript:` ／ `data:` 协议在这里被二次拦掉。

### 缓存与已读按后端地址隔离

storage 键 `_popupPolicyCache` 与 `_popupNoticeAck` 都是 `{ [backendUrl]: ... }` 的结构，切后端不串。

**网络失败不等于撤回**：

| 情况 | 行为 |
| --- | --- |
| 有效成功响应且两字段都显式为 null | 清除该后端缓存条目（表示已撤回） |
| 有效成功响应且有生效内容 | 替换缓存 |
| 非 2xx / 非 JSON / 缺字段 `{}` / 非法条目 | 沿用该后端最后有效缓存 + 提示连接问题；**不能被解释为撤回** |
| 无缓存且失败 | 结束检查（≤5 秒）、沿用原界面 + 连接提醒，**不凭空造出强制升级** |

### 后端地址解析的坑

`PopupPolicyHost` **不能**直接拿 `backendApi.getBaseUrl()`：那个模块变量要等 `checkAuthOnStartup` 读了 storage 才会变成用户自定义地址，而策略检查在挂载时就要发请求，早于那个时刻。用户配了自定义后端时会拿默认地址去问策略，表现为「明明发布过却什么都不弹」。

所以 `popup-policy.ts` 的 `ensureBackendUrl()` 自己按与 `store` 相同的规则解析一次，并缓存结果供确认／重置复用。新增调用方请用 `ensureBackendUrl()`。

### 查看上报（v1.15.1）

`popup-views.ts` 的 `reportPopupView()` 负责「这条弹窗真的显示了」的上报，只由 `PopupPolicyHost` 在**实际渲染的条目**上调用。

**为什么只在渲染分支里调用**：强制优先时被遮住的通知、已确认后不再显示的通知、版本已达标而未显示的强制，都不应该计入。这由渲染分支决定，而不是由上报模块去猜。

**身份就绪的时序问题（必须处理）**：popup 打开时「策略检查」与「从 storage 恢复登录身份」是两条并行异步流程，策略检查通常更早。所以不能只看调用瞬间的 `getToken()` —— 那会把每次冷启动的首次展示都误判成匿名、漏记一人。

正确做法：`backend-api.ts` 的 `onAuthReady()` 订阅身份就绪；未就绪时先订阅，等身份就绪且**该弹窗仍在显示**时补报一次。

- 补报前必须**复查可见性**（用 ref 读当时的显示状态）。用户已经点了「我知道了」就不能追溯成某账号查看；否则会出现「关掉的弹窗反而涨人数」。
- 同类约束：`onAuthReady` 在 `loadAuthFromStorage()` 与 `saveAuthToStorage()` 成功路径上触发；回调里复制一份监听者再遍历 —— 回调中取消订阅会让直接遍历漏掉后面的监听者。

**统计请求绝不能影响主流程**（都是硬要求，都有用例）：

| 要求 | 实现 |
| --- | --- |
| 不进入 `checkPolicy()` 的 5 秒预算 | 单独模块，独立 `VIEW_REPORT_TIMEOUT_MS` 上限 |
| 失败不阻断弹窗 | 全程吞异常；不重试轰炸、不新增队列／alarm |
| 不触发登出 | 服务端对未登录/无效 token 返回 **200 + `counted:false`**，不是 401 |
| 不解除已知强制、不改缓存／确认 | 上报只发一个 POST，不读写 `_popupPolicyCache` ／ `_popupNoticeAck` |
| 旧缓存没有 `recordId` 时照常展示 | `recordId` 作为**可选**字段解析；缺失只跳过统计，不判为非法条目 |

上报的 `revision` 用公开条目里收到的那一个（`entry.revision`），并且**必须由服务端校验**：它要恰好等于当前生效槽的全局修订。所以「重新发布后旧修订」与「不存在的修订」都不会被计入（F1）。

**去重键必须带账号 ID（F3）**：`reported` 是模块级集合，宿主卸载不会重置它，而用户可以在同一个 popup 里退出再换账号登录。若键只有「后端 + 记录 + 修订」，账号 A 报过一次之后，B 看同一条同修订会被直接判定「报过了」而跳过 —— 服务端永远收不到 B 的展示，人数就少一位。所以 `reportKey()` 末尾带上**当次上报使用的 userId**（用 `userId` 而不是 token 全文：token 会刷新／换发，用全文会把同一个人算成两个键、反而重复上报）。

**失败清理必须删「这一次」的键**：`postView()` 把计算好的 key 一起接过去，失败时删的是它自己那个 key。不能失败后按当前账号重算 —— 期间账号可能已经换成别人，删错键会让真正的那个账号下次被误判成「报过了」。取消旧宿主的迟到回调保持有效（`cancelled` 标记）。

## 悬浮面板

统一面板 `#__flash_sale_panel__`，含三个区段：

| 区段 | 变量 | 内容 |
| --- | --- | --- |
| 自动模式 | `autoSectionEl` | 运行状态、倒计时 |
| 开卖进度 | `progressSectionEl` | 成功/失败数、轮次、进度条、停止按钮（由 `buildProgressSection()` 懒构建） |
| 复制 | `copySectionEl` | 定时倒计时、步骤进度 |

旧的 `createProgressUI()`（会销毁其他区段）已移除。`showComplete()` 完成后 3s 自动隐藏进度区段；仅当没有其他区段可见时才移除整个面板。手动开卖、向导开卖、自动模式**共用同一个面板**。

样式：半透明 + `backdrop-filter` 模糊。

**陈旧 DOM 清理**：`createPanel()` 在创建前先移除残留的 `#__flash_sale_panel__`。

**storage 备用**：初始化时从 storage 读 `_enableProgress` 与 `_copyCountdown`，不等消息就能显示 UI；`storage.onChanged` 监听器在消息丢失时实时更新。

### 自动模式实时倒计时

`renderAutoSection()` 渲染 `#__auto_countdown__` 元素，`updateAutoCountdown()` 每秒更新，显示距 `nextActionTime`（操作触发时间）或 `nextTargetTime`（场次开始时间）的剩余分钟:秒。自动模式停止时自动清除计时器。

### 最小化/恢复

统一面板与复制 UI 都有 `−` 最小化按钮（右上角）：

- `toggleMinimize()`／`toggleCopyMinimize()` 把面板收缩为右侧窄条，只显示 `◀` 箭头 + 一行倒计时/状态摘要
- 点击箭头还原
- `panelMinimized`／`copyMinimized` 标志跟踪状态
- `updateMinimizedContent()`／`updateCopyMinimizedContent()` 刷新收缩内容
- `toggleMinimize()` 保存/恢复 `wasCopyVisible`、`wasAutoVisible`、`wasProgressVisible`，防止展开后复制区段保持隐藏

### 失败详情图片

`renderFailedDetails()` 用 `normalizeImageUrl()` 给虾皮返回的原始图片 ID（如 `tw-11134207-820l6-mna42fatmeiqd7_tn`）补上 `https://cf.shopee.tw/file/` 前缀。函数兼容已有完整 URL（`http://`、`https://`、`data:` 开头原样返回）。

**为什么**：漏拼前缀时限时特卖列表全是**裂图**，用户以为商品图丢了、不敢开卖。

### `showComplete()` 初始化

`showComplete()` 先调 `createPanel()` + `buildProgressSection()` 再检查 `headerEl`。

**为什么**：`ENABLE_COMPLETE` 可能在 `ENABLE_PROGRESS` 之前到达（零商品或立即出错），先检查 `headerEl` 会静默返回不显示任何面板。

## 界面约定

### 按钮颜色语义（四色体系）

| 颜色 | 用途 | 例 |
| --- | --- | --- |
| 蓝色 outline | 普通操作 | 查看、刷新、复制、导入/加载模板 |
| 绿色实心 | 主确认 | 开启限时特卖、创建复制任务、保存模板 |
| 红色 outline | 停止/危险 | 停止、清除缓存 |
| 灰色 | 次要/取消 | 取消、关闭 |

hover 规则：`hover:bg-{color}-50 hover:text-{color}-600 hover:border-{color}-300`。

**危险操作禁止用蓝色** —— 颜色是唯一的操作后果提示。

### 异步按钮统一反馈

所有触发异步操作的按钮：点击后 100ms 内文案切换为 loading（「加载中」「清除中」「执行中」），`disabled` 防重复点击，请求完成后 `finally` 恢复。

涉及按钮：清除缓存、停止、手动触发定时任务、应用模板、删除模板、保存模板。

**两个例外**：
- **重新获取 SPC_CDS** —— 用 store 的 `isExtracting` 状态，**不套局部 loading**
- **开启限时特卖** —— 通过按钮切换（🚀 开启 → ⏹ 停止）提供反馈

**禁止在 loading 期间允许点击。**

**为什么**：不等反馈，用户会以为没点上而反复点，导致重复提交。

### 布局信息分层

主界面按优先级分三层：

1. **首屏**：当前活动上下文条 + 定时任务状态卡，置于 Header 正下方
2. **中层**：活动列表（紧凑折叠头）+ 商品列表 + 开启限时特卖参数区连为一体
3. **底层**：「更多」折叠区（`<details>`）收纳低频功能：商品 ID 输入、获取商品信息、加载列表、模板管理、手动触发定时任务、清除缓存

原有的两个独立折叠区（「高级操作」+「商品ID区」）已合并为单一「更多」入口。

> **设计历史 vs 当前实际**：文档旧述称折叠区摘要文字是「高级操作」且「仅在 `isConnected` 为 true 时渲染」。当前实际摘要文字是「**更多**」，且**未使用** `isConnected` 门控 —— 以源码为准。当时的门控设计原意不再追溯（详见 [`08-关键设计决策.md#决策-22`](./08-关键设计决策.md#决策-22--低频操作折叠v163)）。

### 活动上下文展示条

`Separator` 后渲染，显示条件 `flashSaleId && !copyMode`。从 `flashSaleList` 查找当前活动，`name` 为空时回退 `活动 #{id}`，status 按时间判断为「即将开始/进行中/已结束」。

样式用**品牌 token**（`bg-shopee-brand-light border border-shopee-brand/15` 等），文案不含「当前活动：」前缀，直接展示 `{name} · MM/DD HH:mm ~ HH:mm · {status} · N 个商品`。

### 引导条与复制按钮

- **引导条**：活动列表展示、且**没有**定时任务或进行中的复制时，显示一条**品牌色**信息条，提示用户点「复制」按钮。
- **复制按钮样式**：活动列表里的「复制」按钮用**实心品牌色**（`bg-shopee-brand text-white`），不是 outline；新建的活动额外带「**新/待开启**」badge。

**为什么**：复制是这个工具最常用的入口，但用户第一次打开时不一定知道要点哪里；实心色 + 引导条是把它推到视野里。

### 复制流程步骤提示

`CopyConfirmPanel` 顶部三步提示：`● 选择源活动 → ● 选择目标时间 → ○ 创建复制任务`。前两步加粗（已完成），第三步灰色（待确认）。纯展示，不控制流程。

### 错误提示就近化

`CopyConfirmPanel` 用局部 `viewError` 状态，失败时红色文字紧邻「查看」按钮显示。其他 inline 提示已存在：`applyMessage`（应用模板）、`saveSuccess`（保存模板）、`importMessage`（导入模板）、`slotsError`（时段选择）。

**为什么**：远程错误提示（页面顶部）在长列表里容易看不见，用户以为没反应。

### 主题色

主色调是 **Teal**（`#0D9488`）。CSS 变量全为 teal HSL（hue 173）；`tailwind.config.ts` 定义 `shopee-brand`／`brand-dark`／`brand-light`。所有组件引用 `brand`。

历史：早期用虾皮橙 `#EE4D2D`，v1.8.0 改为 teal。旧的 `border-l-blue-500 bg-blue-50/50` 等工具类已不再使用（部分文档仍写着，属历史残留）。

### 「使用说明」与「定制开发」

- 非管理员用户右上角有「使用说明」按钮，用 `window.open()` 打开飞书用户手册
- 旁边是渐变「定制开发」按钮（orange-400 → amber-500），点击弹出介绍虾皮定制开发服务的模态窗口
- 该模态窗口的联系区有「查看二维码」按钮，用 `browser.runtime.getURL()` 打开 `public/contact-qr.png`（作者微信二维码）的居中浮层
