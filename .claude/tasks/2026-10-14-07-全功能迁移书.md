## 3. 当前选定功能 M02.1：源实现到底做什么

### 3.1 入口与实际操作顺序

源入口：`popup.html` 商品改天数卡 → `popup.js` 打开 `shipping-console.html` → `bulk-shipping` 页签。用户选现货 1 天或预售 2–10 天，选全部／在线／下架／非热销范围、填手动排除商品 ID，可勾自动管理物流，点击手动更新；也可启用自动任务、配置至多两个日期／时间／目标天数、每日循环与自动任务排除列表。

手动链：`shipping-console.js:startBulkShippingUpdate` → `START_UPDATE`／兼容 `bulkShippingUpdate` → `apiClient.handleStartShippingUpdate` → `shippingUpdateManager.handleStartShippingUpdate` → 源满额赠步骤（已明确不迁移）／特卖排除调查 → 可选关闭物流 → 分页拉商品／过滤 → `runBatchUpdate` → 完成／停止后的物流恢复与结果。源调用顺序中的关闭物流发生在 `startUpdateProcess` 抓取商品前；目标建议先完成只读调查和目标预览再关闭物流，缩短店铺受影响时间。

**2026-10-14用户明确：不需要满额赠功能。** 此项从整个迁移范围删除，不是延期到M02.2；源满额赠／赠品处理仅属调查历史。目标不增加其入口、检测／查询、主商品／赠品特殊排除或修改恢复逻辑。平台活动限制按普通请求失败结果显示。当前实现合同以08正式任务书为准。

### 3.2 接口契约（静态源码确认，不是实时接口验收）

所有路径为台湾 `https://seller.shopee.tw` 下的源请求路径。目标应复用已有页面 MAIN-world 注入请求与Cookie读取，并沿用身份／权限检查；查询参数的 `SPC_CDS` 从当前 Cookie 取得，不写日志或文档。

| 用途 | 方法与路径 | 关键入参 | 源使用的结果 |
| --- | --- | --- | --- |
| 分页拉商品／回读天数 | GET `/api/v3/product/search_product_list_v2/` | `page_size=50,source=attribute_tool,cursor,version=4.0.0,SPC_CDS,SPC_CDS_VER` | HTTP成功且`code=0`，`data.list`和`data.page_info.cursor/total`；当前页失败源重试一次 |
| 排除商品选品／按销量排序 | GET `/api/v3/opt/mpsku/list/v2/get_product_list` 或 `search_product_list` | `page_number/page_size`或`offset`；`list_type=live_all,sort_by=sales,is_asc=false,need_ads=true`；搜索`keyword` | 商品列表／总数，分页单位不能混用 |
| 批量改商品备货 | POST `/api/v3/product/update_product/?version=3.1.0&source=attribute_tool` | 数组：`[{id,category_path,pre_order,days_to_ship}]` | `code=0`源判整批成功；`1000100007`按`data.result[].id/code`判逐项；目标还需回读未确定项 |
| 单商品降级修改 | POST `/api/v3/product/update_product_info` | `{product_id,product_info:{enable_model_level_dts:false,pre_order_info:{pre_order,days_to_ship}},is_draft:false}` | HTTP成功且`code=0`；会关闭商品按SKU备货，不能对这类商品静默降级 |
| 读取店铺物流 | GET `/api/v3/logistics/get_channel_list` | 当前Cookie查询参数 | `code=0,data.list[].channel_id/enabled` |
| 关闭／恢复一个店铺渠道 | POST `/api/v3/settings/update_channel_toggle` | `{command:'set_enable',enabled,channel_id,proceed_with_mass_toggle_on_item_channels:false}` | HTTP成功且`code=0`；每渠道单独结果，不是全部原子成功 |

批改示例：`[{id:123,category_path:'原返回值',pre_order:true,days_to_ship:7}]`。物流恢复只针对开始前已开启且本任务确已关闭的渠道，原先关闭的渠道不被打开。单商品降级与模型备货结构的冲突必须有明确结果，不借修复资格SKU绕过。

### 3.3 过滤、调度、结果和已知问题

- 源商品 REST列表：在线 `status=1`、下架 `status=8`；数值／字符串先按该端点转换。目标特卖 GraphQL 的活跃 `status=0` 是另一契约，不能套同一常量。非热销是销量前500与浏览前500的并集之外，原字段缺失的判定应沿源规则记录，不凭猜测宣称平台热销标签。
- 手动排除ID与特卖ID合并去重；最终写集合必须保留手动排除优先级。读取不完整、身份不明、活动排除调查失败时先停在预检，不能把失败解释成空列表后写全店。
- 源定时：`SET_AUTO_SETTINGS`保存`{autoMode,task1,task2,toggleLogistics,loopDaily,excludeProductIds}`，任务`{date,time,days}`；`automationManager`的`automation-heartbeat`每2分钟检查。定时只用全商品范围＋排除集合；源使用本机`new Date(date+' '+time)`，不是明确台湾时区契约。目标台湾业务以 Asia/Taipei 解释展示与触发时间。
- 源定时成功代表runner已启动：一次任务立即标`executed`，每日任务立即日期+1；后一任务可强停前一任务。这不能作为目标的完成定义。目标应记录计划次序／每次执行标识／真实终态，忙态等候或明确冲突结果，不能静默强停。
- 源状态由`stateManager`组织`shipping_backgroundState`／`automation_state`，写到`shippingState`／`automationState`等存储序列化；可重开UI读状态，不能把源只持久部分字段当完整中断恢复。目标独立任务持久状态承载进度与物流恢复义务。
- 源批次50、并发通常2；409／1000100006／频率错误缩批并退避，HTTP429可切单商品，最多5轮重试；失败原因带商品ID，不能累加重试次数冒充失败商品数。物流不支持的`1000100252`要单列未改成目标天数。
- 源物流关闭阶段部分失败仍继续改天数并标已关闭，恢复失败通常只日志提示。目标按渠道记录原状态／本次写入／恢复结果，恢复不完整必须在用户可见结果列待处理渠道，不报整体成功。
- `GET_SHIPPING_TASKS`是运行／计划详情，`SHIPPING_PROGRESS_UPDATE`／`SHIPPING_COMPLETED`等是消息；目标关键结果走 storage，原消息名不要求照搬。
- 文档写的隐藏`spotTime/restorePreorderTime`每日现货／预售周期未在当前 shipping 代码找到，不能作为已接通功能迁移；同名`calculateNextExecution(schedule)`属于配置采集，不是此周期。

## 4. 下一轮任务建议：一个可实际操作的基本流程

**建议首轮目标**：在功能首页新增「商品备货与物流」真实入口，接通手动批改、明确范围／排除、可选物流关闭恢复、至多两项一次／每日定时、后台运行／重开看结果。本范围已形成[08正式任务书](2026-10-14-08-商品备货物流与定时修改-任务书.md)，原开发已完成，当前代码独立隔离验收通过；按第25–26节接通体验环境，真实店铺与用户体验尚未验收。

### 建议模块与文件写权

新业务集中在`features/shipping/`：请求／过滤、任务契约、后台runner、调度／消息、独立界面状态；UI在`components/product/shipping/`。按实际职责分文件，纯规则可集中在一个小模块，不为每个函数建文件。后台入口只增加注册／依赖接线，首页只增加真实卡片与导航。目标现有`store.ts`只继续负责特卖，不承载shipping商品列表、runner和定时。共享Cookie／身份／页面注入能力由入口以依赖传入，不复制第二套授权。

### 建议固定验收条件

| 编号 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| S1 | 从实际静态开发包首页进入，预览范围／排除，再手动更新；覆盖现货1天与预售2–10天 | 调用真实产品代码＋本机夹具；目标及排除准确，备货结果回读一致，部分失败逐商品说明 |
| S2 | 请求开始后关闭popup并重开；重复点击开始；停止后重开 | 后台继续；不重复创建任务；停止不再发未发送商品写入，已发送请求保留结果；重开读到进度／终态 |
| S3 | 物流开关未选／选中、某渠道关闭失败、恢复失败、用户停止 | 未选零物流写入；记录原状态并按实际已关闭恢复，失败／待恢复可见，不打开原本关闭渠道 |
| S4 | 设置1／2项计划、每日循环、跨午夜、worker回收后触发、两任务重叠 | 台湾时间触发；每一计划每一轮至多执行一次；启动不算完成，忙态不强停别的任务，恢复不盲目重写商品 |
| S5 | 身份／Cookie失效，分页失败，排除API失败，字符串状态，429及部分失败 | 失败可定位且脱敏；写前身份确认；调查失败不写全店，不沿用错误页的部分列表；重试只处理未确认成功项 |
| S6 | 相关回归：特卖首页／修复／自动调度／SKU覆盖保留、通知门控 | shipping不修改旧storage／alarm；原后台任务不被新功能停止；强制通知保持旧任务执行约定 |

开发交付必须说明实际入口／包、连接后端、自己的PID/端口/DB归属、文件改动、验证范围和未验证项。先本机隔离且全部虾皮写请求拦截，profile无真实Cookie；共享生产包和日常扩展不重载、不构建覆盖。真实店铺手测前由规划方固定一店／商品／渠道／次数／时间，说明物流可能影响下单、已改天数停止不回滚，以及试用是否消耗；依实际业务复用既有授权。此调查／优先级选择不新增这些实际操作授权。

首轮可体验后由Codex给2–5步卡：准确静态测试包入口→选目标→启动并关闭／重开→查看结果；定时／物流的故障与并发在隔离环境验收，不要求用户制造真实店铺故障。用户未操作仍为待用户确认。
