## 4. 接通顺序

按 tasks.md 顺序先后端策略／图片→管理实际编辑发布→扩展根层显示／版本判定→模拟任务保持与隔离构建。不能只交空管理页、写死公告、固定本地图片或纯组件截图。

#### B1 地址读取仍可无限检查

**根因（两处，都要修）**：
1. 宿主在 `await checkPolicy()`（有 5 秒限）**之后**又 `await ensureBackendUrl()` —— 那一步在限外，storage 卡住就永远到不了 `setPhase('done')`。
2. `checkPolicy` 给地址解析和后续检查**各**加了 5 秒，串起来是 10 秒。

**改法**：整轮只留**一个** `withDeadline(POLICY_TIMEOUT_MS)`；地址随 `PolicyDecision.backendUrl` 一起带出，宿主不再自己解析；新增同步可得的 `fallbackBackendUrl()`（不读 storage）作为兜底；读缓存与读已读等本地操作有 `LOCAL_TIMEOUT_MS` 上限且只用**剩余预算**。

**复现→验证**：`popup-policy.test.ts` 新增「地址 storage 读取不返回」用例，断言 `checkPolicy` 耗时 < 6.5 秒且结论里有可用地址。改前该用例超时（10s），改后通过。

#### B2 网络超时清掉已知强制阻挡

**根因**：外层 deadline 抢先返回 `EMPTY_DECISION`，内层的缓存回落结果被整体丢弃。

**改法**：超时/失败分支在**剩余预算**内读同后端缓存，并用与正常路径**同一个** `evaluate()` 判定（避免两套优先级规则漂移）；读已读失败时也**至少保住已知强制策略**。

**复现→验证**：新增三个用例 —— 有缓存时超时仍阻挡（`requiredVersion` 保持）、无缓存时不凭空造强制、地址卡住 + 有缓存时仍阻挡。改前第一个用例 `forced` 为 null，改后通过。

#### B3 已发布记录改类型占两个生效槽

**根因**：`toAdminRecord`/`toPublishedPayload`/发布/撤回都只看草稿 `mode`。一条「先按强制发布、再改成通知草稿、再发布」的记录，两个 `active slot` 都指向它；公开接口两模式都返回它，且通知槽返回的条目缺 `requiredVersion`，扩展严格校验判整份响应非法。

**改法**：新增 `published_mode`（生效快照类型，与草稿类型分开）；发布时在同一事务**先释放本记录占着的其他类型槽**再指向新槽；撤回按「实际挂着本记录的槽」定位；公开读取加**双层校验**（槽指向的记录其 `published_mode` 必须等于槽类型）。数据库自动补列并按当时 `mode` 回填。

**验证**：`verify-api.mjs` 新增 B3 段：发布强制 → 改通知草稿 → 确认强制仍生效且带 `requiredVersion` → 按通知发布 → 断言强制槽已释放、通知槽有效、响应结构完整。

#### B4 主动撤回状态变草稿

**根因**：状态用「当前有没有生效快照字段」判定，撤回把这些字段清空后就被当成从未发布。

**改法**：状态判定改用 `published_revision > 0`（单调递增、撤回不归零）—— 有发布历史且不在生效槽就是**已撤回**。

**验证**：`verify-api.mjs` 新增 B4 段：未发布=草稿 → 发布=已发布 → 撤回=**已撤回**（且标题/正文保留）。

1. “查看”表示该条生效弹窗已在真实扩展界面中显示并成功上报；不是请求过策略接口、管理预览、点了确认或下载，也不代表读完正文。
2. 每个稳定 `recordId` **累计按登录账号去重**。同账号重复打开、同账号多次安装／多设备、StrictMode 重复 effect 或并发请求，都只算一位；另一个账号算第二位。新记录独立计数。同一记录重新发布／改类型不清空累计人数，也不把同账号再算一位；页面注明「累计去重，含历史发布」，避免误解为当前修订人数。第一版不加按修订分析、点击率或升级完成统计。
3. 统计主体是项目后端登录账号（当前账号标识为邮箱），不是店铺／设备／IP。服务端从合法 token 验证用户并查当前账号有效性，客户端不能提交任意 userId／邮箱冒充别人。
4. 未登录／token 过期时不能知道具体账号，**不计入这项账号人数，也不为统计要求先登录**。弹窗仍按原规则展示。已有登录信息的恢复若晚于弹窗渲染，需要在身份就绪且该弹窗仍显示时完成一次上报；不能只依赖 effect 刚启动时未初始化的内存 `_auth`。真正未登录且随后关闭的展示不追溯成某账号查看。
5. 旧客户端、旧缓存中没有记录 ID 的内容仍按原规则展示和保留强制策略，略过统计；不能因新增统计字段把旧缓存判非法并解除阻挡。旧展示不补造历史人数，管理端 0 人要真实显示 0。
6. 统计以服务器已收到的展示上报为准。离线／关闭过快可漏记，界面说明这一边界；不新增后台队列／alarms／高频重试。统计网络／storage 错误有有限超时和脱敏捕获，但不能延长原整轮 5 秒检查、引发登出、阻止确认／下载、清强制缓存或影响后台任务。

- 在现有公开策略条目中只增补稳定 `recordId`（旧客户端兼容），保留 mode、全局递增 revision 及原解析／缓存约束；新客户端保留该 ID 供统计使用，不公开账号或草稿。

### U2 查看统计

**最终口径**（与第 8 节默认口径一致）：查看 = 该条生效弹窗在真实扩展界面里被显示并成功上报。按稳定 `recordId` 累计、按登录账号去重，含历史发布。不补造匿名或旧包历史。

**API 最终路径**（照建议实现，无偏离）：

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| POST | `/api/extension/popup-views` | 公开，可匿名调用 |
| GET | `/api/admin/popup-policies/:recordId/viewers` | 当前管理员 |

公开策略条目只**增补**可选 `recordId`；`mode`、全局递增 `revision`、原解析与缓存约束不变。

**唯一键与去重**：`popup_views` 表，唯一索引 `idx_popup_views_record_user (record_id, user_id)`。写入用 `ON CONFLICT DO NOTHING`，并发插入也只留一行 —— 不靠「先查再插」。首次查看时间由服务端记，重复上报**不刷新**它。

**计数三条硬条件**（缺一不可，`backend/src/utils/popup-views.ts`）：

1. `published_revision > 0` —— 从未发布的草稿不能被刷人数；
2. `published_mode` 与上报 `mode` 一致 —— 否则一条记录给两个类型计数；
3. 该记录**此刻确实占着该类型的生效槽** —— 撤回后记录行还在（累计要保留），但已不在生效槽。只看前两条会让撤回之后晚到的上报继续加人（本轮实测到这一条，已修）。

**人数必须 JOIN `users`**：查看表里的行在账号被删除后会留下，若人数只数查看表行、明细用 INNER JOIN，会出现「说 2 位、明细只有 1 条」。两处已统一为同一 JOIN。

**身份与权限**：账号只来自服务端 token + 当前数据库状态，请求体里的 `userId`／邮箱一律不采信。未登录／无效 token 返回 **200 + `counted:false`**（不是 401，避免扩展登出）。明细只给当前管理员；普通用户 403、匿名 401。**已被删除的旧管理员 token** 读列表与明细都是 403（查库判定，不用 token 里的旧快照）。

**扩展侧**：`entrypoints/popup/popup-views.ts`（独立模块）+ `entrypoints/popup/backend-api.ts` 的 `onAuthReady()` 只读接线。只上报**实际渲染的那一条**；旧无 ID 缓存继续展示且跳过统计；统计请求独立 3 秒上限，不进 `checkPolicy()` 的 5 秒预算，失败静默、不重试、不清缓存、不触发登出。

**迁移幂等**：`popup_views` 与唯一索引用 `CREATE TABLE/INDEX IF NOT EXISTS` 增量建立，不删表不重建；重复初始化不丢已有统计。

**管理端**：标题下绿色「共 X 位用户查看过」可点击，打开明细窗口（账号、首次查看时间、分页 20 条、空态 0 人、失败可重试），注明累计去重含历史发布。撤回后人数与明细保留。截图：`u2-viewers-modal.png`。

**实测结果**：0 → 1 → 仍 1 → 2；同账号重复与 6 路并发都只算 1 位；另一 `recordId` 独立计数；撤回后人数保留、晚到上报被拒；**重启后端后回读人数与明细仍在**（专门一步：停后端 → 再起 → 回读）。

### F1 上报必须校验实际发布修订

**先复现再修**（同一信号）：在隔离后端跑 `verify-api.mjs` 的 F1 段，修复前 **12 项失败**，与独立复现一致 —— 真实修订 1 时上报 999999 得 `counted:true`、人数 1→2；省略 revision 得 `counted:true`、人数 2→3；重新发布到修订 2 后上报旧修订 1 仍 `counted:true`。

**根因两条**，都要修：

1. `backend/src/routes/popup.ts` 把缺失的 revision 兜底成 `0`（`typeof ... === 'number' ? ... : 0`），校验层再也分辨不出「没给」和「给了 0」。**改为原样透传**，不在路由层做任何数字兜底。
2. `validateViewTarget(recordId, mode)` 既不接收也不比对修订。**改为接收 `revision` 并新增第四道校验**。

**最终判定（四条，缺一不可，`backend/src/utils/popup-views.ts`）**：

1. 纯格式关：`typeof revision === 'number' && Number.isSafeInteger(revision) && revision > 0` —— 缺失／`null`／字符串／布尔／小数／0／负数／`NaN`／`Infinity`／超安全整数范围全部返回 `reason: 'bad-revision'`（在查库之前返回）。
2. `published_revision > 0`（草稿不计）。
3. `published_mode === mode`（类型必须与生效快照一致）。
4. 该记录**此刻确实占着该类型生效槽**，且 `槽位.revision === 上报 revision`；不等返回 `reason: 'stale-revision'`。

**为什么第 4 关比对「生效槽 revision」而不是记录自己的 `published_revision`**：槽位的 revision 才是公开接口发给客户端、用户实际看到的那一个。用记录自己的发布次数会漏掉「同类型另一条记录发布后槽位前进了、但本记录自己的次数没变」这种情况，旧修订就能一直刷人数。两者在单记录场景恰好相等，所以只有比对槽位 revision 才既覆盖真实场景又不误伤。

拒绝是**温和**的：一律 **HTTP 200 + `counted:false` + 明确 reason**，不返回 401/400，扩展侧不因此登出、不清强制缓存、不影响已显示的弹窗。
