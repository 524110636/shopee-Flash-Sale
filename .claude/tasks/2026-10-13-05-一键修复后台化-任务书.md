## 4. 固定实现要求

### A. 最短完整流程

普通勾选/首次使用→当次 requestId 与选中商品快照→后台接受并持久确认→后台串行修复与结果准备→popup 关闭时继续→重开还原→完成进入编辑参数→用户选场次确认提交。

关键状态走 storage，不等待长 sendMessage 返回，不根据 undefined 结果自动再启动。接受前是“正在启动”，不能提前宣称正在修复。后台自己的同步启动锁加任务标识必须覆盖重复消息和多个 popup；同店铺写任务冲突时明确忙态，不偷偷终止别人的任务。

### B. 业务不变

保留已有任意 1 天备货 SKU 则跳过新增、100 model 上限、现有纯函数、原 2 秒等待/3 次重取与 1 秒间隔、5 倍价格错误重试、折扣列表失败检查、实际折扣率同值/平均算法。保留部分发布/折扣恢复失败的逐项信息，不把错误吞成全成功。修复完成不创建活动、不 START_ENABLE、不消费试用。

### C. 持久进度与编辑结果

一份当前/最近任务记录包含身份锚、taskId/requestId、阶段、当前商品、总数、逐项状态、更新时间、关键副作用前后检查点、部分修改证据、完成商品/SKU与折扣结果。不能只保存百分比或修复结束才保存。保存关键证据失败，不继续发新写请求。

后台完成必要结果读取，不依赖 popup 尾部 fetchProducts；结果读取失败明确区分“修复已完成但数据待加载”。重开读取、首页查看、切模式不重新启动。结果按 taskId 幂等应用，不重复覆盖用户后填价格、库存、限购、模板与场次；跨店/账号旧结果不混入。保留原缓存规则，不用兼容 shim 或第二套 runner。

### D. 生命周期与中断

使用 Chrome 文档允许的 task-scoped 扩展 API 保活，正常关 popup 后超过空闲周期仍有真实进度；任务终态 finally 清理锁/保活。不要新增 debugger/offscreen/权限或常年保活。

worker 意外重启时先协调旧任务再处理新启动，running 但无执行者的记录标为中断，保留检查点及“部分商品可能已修改”的说明，不自动重放发布/移除/恢复，不伪装继续或全成功。用户明确核查旧任务影响之前，不静默用新任务覆盖其未解决的中断证据；简单确认即可，不搭建自动恢复框架。

需保持 Chrome 和登录 seller 页面可用；切到别的标签页不应依赖 popup active-tab，但关掉 seller 页/失去权限需要明确失败。退出浏览器不继续执行。正式静态包无需 WXT 开发终端；本轮不保证停 npm run dev 后开发版还能加载，也不保证本地校验服务关闭后新写仍获放行。

### E. 后台必要安全边界

凭据从现有 Cookie/认证存储读取，不存到任务记录，不输出带 SPC_CDS 的完整 URL。实际 shopId 与任务 shopId、当前认证账号与 owner 必须核实，在关键写阶段保持一致，切换归属后停止新的写请求。

旧 popup 修复循环本身没有服务端 validate；本次后台无人看守执行不能复制这个缺口。复用现有只读 `validateShopAccess`（可沿用 wizard_flow）并传实际店铺锚，拒绝未绑定/过期等访问；这可能让原本先修复再被拦的账号提前收到提示，应明确说明。校验只读，修复不扣试用，原正式提交成功扣除的契约不变。

### 关键实现决策（与 design.md 的对应）

1. **先落盘再写商品**：`createRepairTask` 的 `accepted` 记录写成功后才 `runRepairInBackground`。
2. **写前检查点**：移除折扣／发布／恢复折扣各自在请求前 `checkpoint({ ..., writeSent: true })`；`patchRepairTask` 里 `writeStarted` 只增不减。
3. **保存失败即停**：`saveTask` 抛错 → `RepairCheckpointSaveError`，循环抛出，不再发新的写请求。检查点保存失败**不会**被逐商品 `catch` 吞掉（显式 re-throw）。
4. **结果在后台准备**：`fetchRepairResultProducts` 走 GraphQL；读失败只记 warning，`status` 仍为 `completed`（"修好了但数据待加载"），popup 重开时用 `refreshRepairResultProducts` 补取。
5. **心跳判中断**：`heartbeatAt` 由保活定时器（20 秒）与每次进度保存刷新；`resolveOrphanedTask` 在 `now - heartbeatAt >= 75 秒` 且无执行者时标 `interrupted`；`reconcileOrphanRepairTask` 在 worker 启动时跑，并在记录仍活跃时安排一次复检。
6. **中断不重放**：`interrupted` + `writeStarted` 时 `handleStartOneDayRepair` 直接拒绝新任务，保留证据；用户点「已核对商品，重新开始修复」才清除（`acknowledgeInterruptedRepair`）。
7. **结果幂等**：`shouldApplyRepairResult(task, appliedTaskId)` + `appliedAt`；已应用过只补 `items`，不重设 `resultProducts`/`discountRate`。
8. **补访问校验**：`validateShopAccess(credential.spcCds, 'wizard_flow', request.shopId)`，凭据现从 Cookie 读。
9. **有界保活**：`setInterval` 20 秒一次短 storage 读 + 心跳写；`finally` 清理。

### BR3 补读成功即完成一次结果应用

**根因**：`syncOneDayRepairTask` 的补读分支只把 `canStartFlashSale` 改成 true，**没有完成一次受约束的结果应用**。于是界面已可编辑、却没有 `_oneDaySkuRepairApplied` 标记；用户填折扣 31（缓存确实为 31）后关闭重开，下一次同步因为"还没 applied"又 apply 一次，把折扣重置成任务默认 80。

**修法**：补读成功后**立即** `await get().applyRepairResult(task)`（写标记 + 初始化商品/折扣率），再让界面进入可编辑；补读仍失败则保持"待加载"。幂等由 `taskId` + 标记键保证，归属与 `taskId` 约束由 `applyRepairResult` 自身处理。读取失败不提前标 applied，也未新增缓存体系。

### BR4 移除结果未知必须停止本商品

**根因**：第三轮新增的移除错误捕获把 `unknown` 返回成 `failedName: null`，调用方据此认定"全部移除成功"、`discountRemoved = true`，继续发布并恢复折扣，最后报完成 —— **新捕获引入的业务退化**。

**修法**：`removeFromDiscounts` 返回 `{ failedName, failedStatus: 'failed'|'unknown' }`；两者都停止本商品（不发布、不恢复），只是提示不同（未知 → 请人工核对；平台拒绝 → 请手动处理）。逐活动结果与检查点 `outcome` 保留，`discountRemoved` 只在确有活动被确认移除时为真。不新增自动补偿、重放或回滚；**后续商品仍按原业务继续处理**。

### 诊断摘要整理（合并同路径）
