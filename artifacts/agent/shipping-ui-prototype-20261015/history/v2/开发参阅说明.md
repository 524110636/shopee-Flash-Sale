# 备货循环界面原型：讨论与开发参阅

用户已认可主布局，选择方案A：常规备货天数使用下拉框，完整支持2–10天。本次按用户批注补二级排除商品弹窗，并加入用户已确认的关机／断网处理说明及周末建议。HTML仍仅为界面原型，尚未下发正式实施任务，不代表产品已实现这些新增运行规则。

双击「备货循环界面原型.html」即可离线打开，不需后端、安装依赖或启动服务。页面不发网络请求，不读取登录凭据，不写浏览器持久存储，不会创建或执行商品／物流任务。

## 给用户看的变化

- 第一步改为2–10天的原生下拉选择；8天只是演示初值，选2天或10天都会联动恢复标识及确认文案。
- 三个独立步骤卡片：设置常规备货 → 成对安排两次切换 → 确认启用。模块间距统一20px。
- 开始／恢复日期及时间都可更改，跨天显示“次日”或间隔天数，不固定周日。
- 排除商品及物流设置折叠，默认物流关闭；手动修改保留独立页签，本原型只给出其范围说明，尚未设计该页。
- 点击启用／暂停仅切换本页演示状态，不伪造商品执行成功；执行记录保持为空。

5. 本页模拟启用后锁定设置、显示首次安排；真实产品的运行／等待／失败／待恢复、暂停与关闭语义，以正式任务和原业务契约为准。该模拟不等于已设计或实现真实任务暂停能力。
6. HTML验证恢复晚于开始，并对每日／每周时段重叠给演示提示；这些交互规则尚未作为新产品契约生效。日期跨天标识、选择2–10天和预览联动可以直接评审。

## V2：用户批注与补充要求（2026-10-15，已确认范围）

主布局获用户认可。主页面不再展示商品ID输入框或商品选择列表；折叠设置内只放「设定排除商品」按钮及已排除数量。点击打开独立二级模态弹窗，支持按商品ID检索、任意多选、按销量从多到少排序、勾选销量前5／前10、取消／确认。弹窗不嵌入一级页面内容区。

本原型使用20个明确标识的演示商品，不读取真实店铺。快捷勾选按全店已知销量排名，保留已有选择并去重，不受当前检索条件影响；未知销量不伪造为0参与快捷排名。同销量按ID稳定排序。检索或排序不会丢失其他已选商品；取消和Escape不提交草稿，确认才更新主页面数量。快捷选择保存的是具体商品ID，不是一个随销量变化动态替换的“前N规则”。本组两次动作都应遵守同一组已确认排除ID。

### 直接复用哪些现有能力

- 目标项目`components/product/shipping/ShippingWorkPage.tsx`的`ExcludePicker`已有ID／名称检索、销量排序、多选和排除ID合并；目前是一级展开区，需改为二级弹窗，补前5／前10快捷入口。
- `features/shipping/store.ts`的`loadPickList`和`SHIPPING_PRODUCT_LIST`已有只读商品列表链；`features/shipping/background.ts`把`sold`规范为nullable字段，未知销量已有明确语义。正式实现应复用这条链，不另建商品读取或授权实现。
- 现选择器只显示排序／筛选后的前50项。新弹窗需保证任意商品可检索／选择、跨列表页保持选中、全店排名基于完整读取结果，不能把首屏50条当全店。
- 参考项目`D:/shopee_xm/虾皮插件-客户/shipping-console.js`的`openExcludeModal`／`renderExcludeProductList`已有独立排除弹窗和持久于会话中的选中集合，列表请求使用`sortBy: 'sales'`；可参考交互。此次核对未发现其现成前5／前10入口，不能把这一新增快捷逻辑说成已迁移。源项目只读，不复制赠品／满额赠流程。

### 用户已确认的长期计划与恢复规则

1. 周一保存周末计划，中途多次关机、重启、断网，计划与商品排除设置不得丢失或要求重新创建；设备恢复、浏览器启动后重新检查持久记录并恢复必要调度，不靠popup内存或长setTimeout。
2. 执行时设备仍关机／浏览器退出，或缺少网络／有效登录／后端条件，本地扩展不能按时完成真实任务。不能以“后台运行”承诺设备关机也执行；不隐含新增云端代跑、远程凭据或开机自启动服务。
3. 错过「切到1天」就跳过该轮，不在以后补切历史现货任务；未切现货的轮次也不能误执行一轮全店恢复。
4. 已经切到1天而错过恢复时间：设备／网络恢复后，核实原店铺、原账号、现行权限、本轮实际结果，优先恢复常规备货。保留本轮商品与阶段记录，不因换日或推进下一轮而丢弃恢复义务。
5. 写入结果未知的商品先核实；仍无法判定则提示处理，不盲目重放。不因“恢复”绕过旧身份／权限／确认快照、重复写保护或同店互斥。
6. 网页提醒采用浅暖色提示卡，放在循环状态之后、步骤之前：建议尽量在周末使用、避免其他时段；同时提醒执行期间保持设备开机、浏览器运行并联网。周末只是使用建议，不锁死自定义日期，也不宣称周末能保证不中断。详细恢复规则折叠展示，减少一级信息密度。

### 现有基础与新增验收分开

现有`features/shipping/background.ts`通过`storage.local`保存设置／计划，worker启动会读回记录并调用`checkShippingPlans`，保存计划会同步alarm；每2分钟补检并用轮次标识防重复。原第19节已有实际alarm、跨日和浏览器中断不重放的隔离证据，继续有效。

但原`rules.resolvePlanDue`按当前台湾日期、独立计划判定；错过以前日期不补历史，当前日期迟到仍可能执行。它没有实现本次新的“成对循环＋错过开始跳过／已开始优先补恢复”完整契约。因此这是用户新增的运行行为，须在正式任务中明确，不可只换UI或声称旧代码已满足。

正式任务的新增验证至少包括：周一保存未来任务并经历多次真实浏览器退出重启、离线启动后联网、到点前恢复后正常触发、错过开始不补切、已经切现货后跨日／多日恢复仍优先补恢复、结果未知先核对、账号不符等待、重复alarm／重复联网事件不重复写、排除ID及恢复天数始终保持。必须区别设备／浏览器重启与普通worker被回收；不能把正常2分钟调度误差误判成设备离线错过，正式任务需固定过期判定和调度容差。

平台事实来源：[Chrome alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms)建议每次worker启动核验必要alarm；设备休眠不会被alarm唤醒。[Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage)是扩展持久状态接口。本次未针对真实关机或真实店铺重跑产品验收；这些新增规则仍是待开发范围。
