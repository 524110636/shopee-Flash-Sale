## Context

首页任务已由用户最终确认通过，已实查本地备份 `09600f8`、分支「弹窗功能与扩展功能卡片」，开工时工作区干净。当前 `runOneDaySkuAndEnable` 在 popup store 中串行读取商品、移除折扣、更新商品、恢复折扣，最后加载成功商品并进入 `editing_params`；方法名含 Enable，但修复结束并不自动提交活动。

首次使用的 `runFirstUseFlow` 选品后用 300ms 定时器触发同一方法。关 popup 会销毁 store/定时器/循环；仅缓存进度不能修复执行中断。现有纯函数 `one-day-sku.ts` 可复用，background 已有 Cookie、注入请求、访问校验、storage 进度机制，不能导入 popup Zustand store 执行修复。

Chrome MV3 正常约 30 秒空闲回收 worker，扩展 API 调用可重置空闲计时；单请求和 fetch 有时限。现有 4 分钟 session-heartbeat 是会话维护，不能当连续修复的 worker 保活证明。官方依据： https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle 。

## Goals / Non-Goals

**Goals:**
- 已被后台接收的修复任务不依赖 popup；关闭弹窗后继续，重开还原真实进度、失败详情和可编辑结果。
- 保持两种入口和原商品/SKU/折扣步骤，成功后仍由用户编辑参数、选择活动并确认提交。
- 有限期执行、真实终态、任务去重、店铺/账号安全及副作用检查点；异常回收不能伪装运行或自动重复发布。

**Non-Goals:**
- 不让任务在浏览器退出后继续，不承诺停止 WXT 开发服务器后开发版仍可加载，不修复开发终端依赖。
- 不做断电/重载后无缝自动续跑、不新增通用任务调度器、历史任务中心、暂停/取消/自动补偿系统。
- 不顺带修复旧 SKU 编辑、其他复制/自动模式问题，不改后端/管理员网站/依赖/权限，不部署或操作真实店铺。

## Decisions

### 1. 两种入口共用一条后台任务，启动确认走持久状态

普通勾选与首次使用均提取当次选中商品的快照、预期 shopId/账号标识和 requestId，发送短启动请求。移除首次使用对 300ms popup 定时器的执行依赖，不能等 popup 长连接维持任务。

后台先同步取得启动互斥，再读取并核对现存任务/账号/店铺；在第一条商品写请求前写出可观察的 accepted/running 状态。用户界面在接受前显示正在启动，不把消息未送达或返回 undefined 当成已启动/失败后重试。requestId 使同次请求重复投递可查询原任务，不新增一套循环；不同请求碰到活动修复时明确忙态。

关键状态以 storage 为准，消息结果仅辅助。启动 handler 不等待整批完成才返回，避免长事件响应和 popup 关闭耦合。不另建服务端任务系统。

### 2. 后台执行复用现有步骤，不自动开卖

将循环及结果准备搬到 background 或必要的非 WXT 入口模块；复用 `getSpcCdsFromCookies`、`injectedFetch` / `executeScriptSafe`、现有纯函数，不引入 `useAppStore`、DOM 或弹窗依赖。

完整保留：get_product_info；已有任意 1 天备货 SKU 则跳过新增；构建和 100 SKU 上限；折扣搜索/移除；2 秒等待；商品发布；仅原有 5 倍错误重试；最多 3 次重新取商品和 1 秒间隔；恢复折扣及逐条失败检查；逐商品失败结果；全局折扣率同值/平均规则。

完成结果包含成功商品 IDs、必要的最新商品/SKU 信息、实际折扣率及逐项状态。首次使用空 modelList 场景不能在重开后只剩商品 ID；后台完成必要读取并保存结果，不要求 popup 未关闭才能执行最终 `fetchProducts`。保留原读取限制，读失败明确区分“修复完成、结果待加载”和“修复仍在执行”，不得假装可提交。

结果仍衔接 `editing_params → selecting_flash_sale → 用户确认提交`，不因 popup 关闭/恢复偷偷创建活动或调用 START_ENABLE。

### 3. 一份可序列化任务记录与有限检查点

建议单一专用键 `_oneDaySkuRepairTask`（最终命名可按项目规范调整并同步手册），包含 taskId/requestId、ownerUserId/shopId、执行实例标识、运行/完成/失败/中断状态、阶段、当前商品/总数、更新时间、逐项结果、必要的已移除折扣/恢复信息和最终编辑结果。只保留一份当前/最近任务，不无限追加历史和原始 API 响应。

最少在任务接受、商品开始、移除折扣前/后、发布前/后、恢复前/后及终态保存；写请求结果不确定时保留 pending/uncertain 标识，不把“已发送”写成成功。必要结果/检查点保存失败时不继续发新的商品写请求。保存充分的部分修改证据，但不额外实现自动回滚。

任务记录、快照、日志不得新增 SPC_CDS、Cookie、JWT/密码副本；凭据只从现有 Cookie/认证存储读取，URL 和错误日志需脱敏，不能直接复制原 popup 带凭据 URL 的日志。

### 4. 限定保活与真实中断，拒绝盲目重放

选用符合 Chrome 官方生命周期规则的 task-scoped 保活：任务活动期间使用有界、短完成的扩展 API 调用维持 worker（例如约 20 秒一次），不依赖 popup port、普通定时器本身或 4 分钟 heartbeat。实际业务 API 有时限；任务结束/失败在 finally 清理保活及内存互斥。禁止常年保活、debugger/offscreen/新权限或额外网络心跳。

用关闭 popup 后超过一个空闲周期的真实扩展测试验证，不能“搬到后台就算完成”。后台意外重启时先协调旧状态再接收新启动：若持久记录仍 running 但新实例没有活跃执行者，标记 interrupted，停止自动写请求，保留最后检查点及商品结果，提示部分商品可能已改动需核对。首版不重放未知的发布/折扣写操作，也不把 running=false 伪装成全部失败/成功。

保持 Chrome 开着及登录的 seller 页面可用是执行条件。换到其他标签页不应因 popup 的 active-tab 依赖失败；后台取可用 seller 页。卖家页面关闭、登录失效、Chrome 退出/重载或进程终止不保证连续执行，应留下真实失败/中断信息。

### 5. 后台安全边界与最小互斥

仅靠 popup 里的 isEnabling/绑定 UI 不足以保护后台任务。启动与每个商品关键写阶段核对任务 owner 与实际 shopId，当前 Cookie 来自 `getSpcCdsFromCookies`；不得盲信客户端 shopId 或用旧 SPC_CDS 固定跑完整批。切店/切账号/缺凭据时停止新的写请求并记录原因，不尝试替新店继续旧任务。

后台新修复入口复用现有只读 `validateShopAccess`，传实际核实的 shopId，action 可沿用 wizard_flow；这是无人看守写操作必须补齐的边界，旧 popup 循环当前没有独立服务端 validate 调用，不能原样复制这个缺口。它可能使已过期/未绑定账号在修复前更早被拦截，应明确提示。修复检查和完成都不消费试用；正式活动提交成功后的现有消耗时点不变。

至少保持与现有手动提交的互斥，后台自己防重入；与同店铺自动或定时写任务冲突时，新修复/新写启动应明确拒绝或忙态，不偷偷停止既有任务。只接必要入口检查，不改旧调度参数、不构建全局队列。

### 6. popup 恢复与首页接线，不反复覆盖用户编辑

根层恢复新任务状态并监听 storage；初次未知时保留加载态。首页显示“商品修复中/已中断/修复完成待编辑”及只查看入口，不强制跳离首页；返回手动页可查看逐项结果。读状态/重开/切页不能重新发启动请求。

运行进度归后台，完成后的编辑配置归 popup/cache。终态结果按 taskId/revision 幂等应用，用必要的小型已应用标记避免每次打开弹窗都重设 discountRate、productIds、skuOverrides；用户随后手填价格/库存/限购和选择场次不能被 heartbeat/状态恢复覆盖。跨账号/店铺的旧结果不自动合并。保留现有缓存过期规则，结果不可用时明确提示/只读查看，不静默回到默认参数。

## Risks / Trade-offs

- [移除折扣后中断] → 持久保存动作检查点与折扣恢复信息，明确部分修改提示；不把迁移扩成自动补偿工程。
- [消息重复或多个 popup] → 同步启动锁、持久任务标识、一次请求复用；不靠每个 popup 的 running 状态。
- [worker 与启动协调竞态] → 启动前等待旧记录协调；不在新任务开始后用旧异步读覆盖状态。
- [结果在 popup 关闭时丢失] → 结果准备/持久化也属后台执行，popup 只应用结果。
- [重复恢复覆盖用户价格] → 按 taskId 一次应用、保留编辑归属及 SKU 其他字段。
- [测试开发版误当隔离] → 正式静态包 + 独立 profile + 本地后端/平台 stub；真实写请求放行必须为 0。

## Migration Plan

开发按任务书先接通完整后台修复→关闭 popup→完成→重开编辑流程，再做必要边界和回归。老 popup 循环在新入口接通后移除，禁止双 runner/默认回落。上线前不重载有运行/等待任务的扩展；旧内存任务先自然结束。开发回交后规划方独立验收，再发手测卡；真实商品修改由用户另行决定店铺、数量和动作，不能自动扩成全店。回退只针对本任务文件，保留持久任务证据，不覆盖 `09600f8` 后他人改动。
