## Goals / Non-Goals

**Goals:** 管理员实际编辑／上传／预览／发布→后端持久保存→静态扩展读取→通知确认或按实际版本阻挡→更新达标后解除。新增模块与现有任务执行解耦，形成可本地体验的完整流程。

**Non-Goals:** 卖家网页弹窗、系统通知、自动下载安装、商店发布、任务暂停／取消／自动恢复、版本防篡改、用户分组投放、通知历史中心、定时发布、生产部署。本轮不重开已完成首页／后台修复任务。

## Decisions

### 1. 根层展示与后台执行分离

在功能区根层保留统一策略宿主（小型独立组件／hook／纯判断模块），仅在真实登录和首次功能初始化完成后启用，覆盖首页和工作页；认证／首次绑定初始化等待不展示通知、强制或公告检查遮罩。复用现有初始化与状态监听；不能因阻挡而调用 reset、清 storage、STOP 消息、清 alarm，不能添加后台版本拒绝。常驻业务状态的读取与结果应用保持原有行为，交互区域阻挡或 inert；通知关闭恢复原界面和草稿。

原因：旧最外层宿主会遮挡登录表单并产生匿名已看却不能按账号计数的体验；最新用户要求先登录再展示。仅在首页卡片挂载会漏掉其他已登录功能分支；仅禁用一个入口会被其他按钮或键盘绕过；把版本条件加入 /validate 会使已安排任务在触发时失败。替代方案「网页弹窗」超出用户选择，「后端统一拒绝旧版请求」与后台照常执行直接冲突。

强制升级只覆盖已登录功能区中的绑定／账号设置等操作；退出或登录失效时回到原认证界面且不显示升级。独立管理网站不受扩展遮罩影响。按钮由用户点击打开新标签页，不在启动时自动导航，不调用 runtime.reload。

### 2. 多条管理记录与每模式一个生效槽

2026-10-13 用户实际体验后明确改变管理方式：默认列表页显示记录总数、标题、通知／强制更新类型、草稿／已发布／已撤回状态及操作。点击「新建弹窗」打开空白 Modal，含标题、富文本正文、图片和「强制更新」勾选框；默认未勾选，勾选后显示 requiredVersion 和 downloadUrl，两者发布必填。每次新建独立 ID，不复用旧编辑器内容；编辑已有记录与新建分开。列表操作至少包含编辑、发布、撤回，删除仍未纳入；2026-10-14 用户明确新增查看人数与账号明细，按本设计第 6 节实施。

管理端可以保留任意多条独立记录。投放仍沿用每 mode 同时至多一条生效的第一版默认，不增加多通知队列；发布另一条同类型时明确提示替换当前标题，并在一个事务内切换生效快照、保留旧记录为已撤回。撤回未生效旧记录不能误撤同类型当前记录；操作必须按 ID 定位，不再只按 mode 写固定行。取消新建窗口不改旧记录，上传后取消可能留下素材，沿用素材容量管理边界。

后端新增记录表或安全增量迁移，保留原两模式生效槽与公开 notice／forcedUpdate 单条响应契约可减少扩展接线变动。具体表名由开发决定；稳定记录 ID、草稿／生效快照隔离、事务发布与回读是必须结果。旧两模式的草稿、已发布快照及单调递增 revision 都要保留，旧记录内容不同也不能在迁移时互相覆盖。若保留生效槽，新增 publishedRecordId 关联；通知 revision 使用每后端／mode 全局递增发布计数，不随记录 ID 重置，已读缓存可继续用原语义。迁移重复运行幂等，不删库重建，不执行正式库迁移作为隔离验收。

管理 API 改为列表／创建／按 ID 编辑草稿／发布／撤回，具体路由由开发在交回写明（避免把旧 mode 路由冒充独立列表）。公开 GET /api/extension/popup-policy 与图片上传／读取入口继续复用；公开只含生效展示字段，no-store，不泄漏草稿或账号资料。管理写操作复用 authMiddleware + adminMiddleware，查数据库当前身份。

原因：原「每种类型一份可反复编辑的草稿」符合最初默认，但不能满足用户连续创建通知、保留旧内容的实际管理方式。这是用户新增范围，不能把它说成原开发遗漏。多条管理记录与多条同时投放是不同范围，第一版暂保留既有投放数量。

### 3. 富文本与自有图片

管理员可视化编辑标题、加粗、颜色、列表、链接和插图；复用维护中的编辑器，只在 admin-web 引入编辑器依赖。服务端使用可靠白名单清洗库，扩展侧也安全渲染；不以自写正则替代 HTML 清洗。保留段落／标题／列表／允许颜色，拒绝脚本、事件属性、iframe 和危险协议；链接仅 http(s)，新标签页使用 noopener/noreferrer。

图片首版只接受 PNG、JPEG、WebP，单张至多 5 MiB；服务端检查实际文件签名／大小，采用生成的资源 ID 与固定资源目录，不使用用户文件名拼接路径，不接受 SVG 或 HTML。单个弹窗正文最多 5 张上传图片，正文 UTF-8 最大 100 KiB；上限是第一版实施默认值，非用户逐项指定。失败显示明确原因，不发布半截内容；管理编辑器与扩展尺寸预览使用同一可允许的展示集合。

资源目录持久配置 POPUP_ASSETS_DIR，默认运行数据目录，隔离验收必须指向 .agent-tmp 中的任务目录；正文可以保存 /popup-assets/ 相对资源引用，但扩展渲染前必须基于当次策略所用后端地址解析为完整 URL，不能基于 chrome-extension:// 解析；后端地址切换不串缓存。正式上传素材不作临时垃圾清理；暂不搭建自动素材清理后台，仅报告容量并纳入备份／部署说明。原因：内置 contact-qr.png 只能随包发布，不能承担管理员随时上传的业务。

### 4. 实际版本是唯一解除依据

读取 browser.runtime.getManifest().version；requiredVersion 接受 Chrome 的 1～4 段数字格式（每段 0～65535，无非零前导零，整体不全零），数字比较并补缺失段为 0。当前版本 < requiredVersion 时阻挡；相等或更高时解除。版本配置在 package.json 与 wxt.config.ts 两处，打包交回必须核对产物 manifest；不以 backend/package.json 的后端版本、zip 文件名、下载按钮点击或已读标记判定升级。

发布强制模式时要求版本和 http(s) 下载地址齐全；地址不能为空或危险协议。第一版由管理员保证链接指向相应版本的包，不替用户抓取或自动验证任意下载页面。按钮只跳转，不写已升级标记；开发不得新增 /validate 版本门或停止后台任务。

依据：Chrome runtime.getManifest 文档 https://developer.chrome.com/docs/extensions/reference/api/runtime#method-getManifest 与 manifest 版本规则 https://developer.chrome.com/docs/extensions/reference/manifest/version 。

### 5. 显示顺序、确认与连接失败默认值

每次打开或同一 popup 完成登录、首次功能初始化就绪后，再读当前后端地址对应的最后一份有效策略，整轮地址解析／网络／storage／已读检查必须在 5 秒上限内进入明确终态；加载中显示短暂检查状态，阻止用户在策略返回前点击新业务。无需高频轮询或后台策略 alarms；本轮只承诺下次打开获取变化，不承诺管理员发布后所有已打开 popup 立即推送。

优先显示命中的强制升级，否则显示尚未确认的 notice，最后恢复正常界面。notice 点击「我知道了」才存确认 revision；直接关闭整个 Chrome popup 不视为已读。确认按后端地址＋notice 修订持久化到当前安装的 storage，切店不重复、重新安装不承诺同步。编辑草稿不重弹，重新发布生成新修订可重弹；撤回不展示旧内容。

缓存键独立于 flashSaleCache、模板及任务存储，后端地址不同分别保存。有效服务端明确同时返回 notice:null、forcedUpdate:null 才能清除旧生效缓存；缺字段的 {}、错误 mode、非有限修订、非法要求版本／下载地址属于无效响应，不能解锁；网络失败、非 2xx、非 JSON／结构错误不能被解释为撤回。获取失败时沿用同地址最后有效策略，并提示连接问题：已知强制要求继续阻挡；无有效缓存时结束检查、沿用现有界面并显示连接提醒，不把网络异常变成新强制升级。保持后台原有认证与网络失败处理，无缓存不代表业务请求能跳过原校验。

原因：通知服务故障不应中断用户原业务，已知强制策略也不能因断网被当成用户已升级。未登录阶段按最新规则不展示强制，登录后仍按有效缓存约束；无缓存时不能知道离线期间的新要求，这是第一版明确取舍；更严格离线阻挡尚未纳入。

### 6. 2026-10-14 查看统计、表单对齐与版本操作指引

用户已确认原基础功能通过，新增三项沿用本变更。每条记录标题下绿色可点击「共 X 位用户查看过」，点击只向当前管理员加载账号／首次查看时间明细；空态为 0，人多分页。默认口径为同 recordId 的累计去重登录账号，含历史发布，重复打开、多设备和并发不增加人数；新记录独立，撤回／替换／重新发布不清统计。本次不增加分修订报表、确认率／点击率／升级成功率。

公开条目补稳定 recordId，兼容旧客户端与旧无 ID 缓存；原 mode＋全局递增 revision 不变。只有真实显示的弹窗才异步上报，管理预览、策略获取、强制遮住的通知和已达标未显示强制不计。合法账号由服务端 token 和当前 DB 共同判定，不信请求体 userId／邮箱；新增 `(recordId,userId)` 唯一约束及服务端首次时间。现有公开接口不暴露账号；明细与人数只在当前管理员接口中返回。增量初始化不删表／删库，撤回不删统计。

账号初始化与策略初始化异步，不能在尚未恢复 `_auth` 时误以为长期未登录：已有登录身份与首次功能区就绪后才展示并上报。匿名／过期凭据不展示公告，也不计；迟到请求不能跨登录会话回填或覆盖登录界面。统计使用当次策略后端地址，单独有限超时，不进入 checkPolicy 原 5 秒预算、不触发退出、不改缓存／确认／后台执行。离线或关闭过快可能漏记，只承诺服务器收到的真实展示上报；旧包不补造历史记录，不新增后台发送队列或 alarm。

强制编辑字段采用一致的标签在上／输入在下结构，空间足够时两列且顶对齐，窄时堆叠；原因是当前 inline Typography 与 Input 混排导致两栏错位。以用户 953×900 实际页面及 1366×768 截图验证，不重写编辑器或整页风格。

管理页顶部增加「如何修改版本与测试升级」：当前根 package.json:3 的 version 与 wxt.config.ts:18 的 manifest version 两处同步修改；显示本次交回核对的行号、字段与复制示例，行号漂移时可搜索字段且交回时同步更新，不在手册固化行号。保留两处现有配置，不为此迁移版本来源。区分静态 development 构建、生产构建和需保持终端的 npm run dev；构建后核对输出 manifest 与 Chrome 实际版本，不改 backend/package.json 或生成 manifest 冒充升级。

最终手测固定后端要求并保持发布，真正保留旧包、构建和下载新包、在无任务测试扩展重新加载／安装后验证解除；不能通过降低要求或撤回完成。开发需交可下载的新包入口／目录和持续可用的隔离后端。修改日常包、生产部署和真实业务仍另行决定。完整验收矩阵 P14–P17 与文件写权见原 06 任务书第 8 节。

## Risks / Trade-offs

- [历史安装没有读取代码] → 先人工安装一次包含功能的新包；不声称能给所有 1.14.3 用户远程弹窗。
- [点击下载跳出扩展会关闭 Chrome popup] → 关闭不会停止既有后台任务；重开重新判断，下载本身不解锁。
- [真正重载／退出 Chrome 会改变 worker 生命周期] → 文案提醒先下载、任务完成后再重载；本轮不新增断点恢复，也不承诺重载期间持续执行。
- [管理员误填要求版本／链接] → 发布时校验格式和必填项、提供预览和撤回；交付核对实际包版本。下载网页内容与人工填写一致性由发布者负责。
- [HTML 或文件上传成为可执行内容] → 服务端鉴权、白名单清洗、签名／体积检查及固定路径；安全渲染用例必须覆盖。
- [已读／缓存受账号或后端切换影响] → 第一版按安装和后端保存，不承诺多设备阅读同步；任务身份校验仍走现有机制。

## Migration Plan

1. 开发在独立本地端口、DB_PATH、POPUP_ASSETS_DIR 与无真实 Cookie 的扩展 profile 接通完整流程；先提供管理员网站与新静态包实际路径。
2. 开发提供模拟后台任务持续推进证据；Codex 独立复核并准备 2～5 步安全体验卡，用户只在隔离管理端发布测试通知／要求，不操作真实店铺。
3. 生产后端、管理网站和素材存储部署，及首次向用户发新包均另行决定；无生效策略时新客户端行为与旧版一致。
4. 撤回强制策略后在线客户端下次打开解除；故障时可恢复旧后端／管理网站产物并保留新增表和上传素材。正式 DB、素材备份与恢复由实际部署任务落实，不能在开发测试中删改生产数据。
